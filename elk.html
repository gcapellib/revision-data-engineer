Un moteur de recherche avec index inversé

Chaque mot pointe vers la liste des documents qui le contiennent : on trouve directement les candidats, puis on classe par pertinence (score BM25).

Elasticsearch est un moteur de recherche et d'analyse distribué, construit sur Apache Lucene. Il stocke des documents JSON dans des index, interrogeables par une API REST. La stack ELK ajoute Logstash (collecter et transformer) et Kibana (explorer et visualiser) ; elle sert la recherche plein texte, l'analyse de logs et la supervision.

Analogie — l'index alphabétique à la fin d'un livre : au lieu de relire 800 pages pour trouver un mot, on lit la liste des pages où il apparaît.

Le fil du cours · ELK (Elasticsearch, Logstash, Kibana)

5 idées font tout le cours

Tout le cours répond à : comment retrouver en quelques millisecondes une information dans des milliards de lignes de texte ou de journaux ? Cinq idées expliquent Elasticsearch, Logstash et Kibana.

Idée 1 · Indexer à l'écriture pour chercher vite

Elasticsearch prépare la recherche au moment où il enregistre un document : il construit un index inversé, une table qui associe chaque mot à la liste des documents qui le contiennent. Une recherche lit cette table, pas les documents. Presque tout se décide donc à l'écriture.

L'erreur typique : Si l'on indexe sans penser aux recherches à venir, on ne pourra chercher que ce qui a été construit à l'écriture : corriger ensuite oblige à tout réindexer.

La bonne pratique : Lister d'abord les recherches à servir (par quels champs, filtres, tris), puis définir l'index en conséquence.

ch. 02 · ch. 03

Idée 2 · Le mapping décide de ce qui est cherchable

Le mapping donne le type de chaque champ. Un champ text est analysé (découpé en mots, mis en minuscules) pour la recherche plein texte ; un champ keyword est gardé tel quel pour filtrer, trier et compter. Le type d'un champ existant ne peut changer qu'en réindexant.

L'erreur typique : Si l'on laisse Elasticsearch deviner le mapping, un identifiant peut être indexé en text : il est découpé en mots, et l'on ne peut plus filtrer ni agréger dessus.

La bonne pratique : Déclarer le mapping soi-même avant d'indexer : les identifiants et les codes en keyword, les textes libres en text.

ch. 01 · ch. 02 · ch. 03

Idée 3 · Filtrer ou scorer

Une requête (query) calcule un score de pertinence : « à quel point ce document correspond ». Un filtre répond seulement oui ou non, et son résultat est mis en cache. La requête bool combine must (doit correspondre, avec score), should (bonus), filter (oui/non, sans score) et must_not (exclure).

L'erreur typique : Si l'on écrit des conditions oui / non dans must, Elasticsearch calcule un score de pertinence inutile et ne garde pas le résultat en cache.

La bonne pratique : Mettre les conditions oui / non (statut, date, catégorie) dans filter, et garder must pour la recherche de texte.

ch. 03

Idée 4 · Distribuer en shards, protéger par répliques

Un index est découpé en morceaux, les shards, répartis sur les machines (nœuds) du cluster. Chaque shard a des copies, les répliques, sur d'autres nœuds. Le nombre de shards principaux se fixe à la création de l'index.

L'erreur typique : Si un index de plusieurs téraoctets n'a qu'un seul shard, toute la charge repose sur un seul nœud et l'on ne peut pas répartir le travail.

La bonne pratique : Choisir le nombre de shards selon le volume prévu (souvent quelques dizaines de Go par shard) et garder au moins une réplique.

ch. 01 · ch. 04

Idée 5 · Un pipeline : collecter, transformer, visualiser

La chaîne ELK : Logstash (ou les Beats) lit les données, les découpe (grok), les enrichit et les envoie par lots (_bulk) ; Elasticsearch les indexe ; Kibana permet de les explorer et de construire des tableaux de bord. Elasticsearch n'est pas la source de vérité : on garde la source pour pouvoir réindexer.

L'erreur typique : Si Elasticsearch est la seule copie des données, un mapping raté devient irréparable : il n'existe plus de source à partir de laquelle réindexer.

La bonne pratique : Garder les données d'origine (base, fichiers bruts) et pouvoir reconstruire l'index à tout moment à partir d'elles.

Chapitre 01 · Modèle de données et cluster
① Pourquoi ② Quoi

Document, index, mapping, API REST

Le vocabulaire
  • Document : un objet JSON (une offre, une ligne de log), identifié par un _id.
  • Champ : une clé du document ; chaque champ a un type (text, keyword, integer, date…).
  • Index : une collection de documents de structure voisine (équivalent d'une table / collection).
  • Mapping : le schéma de l'index (types des champs).
Analogie — une bibliothèque : le document est une fiche, l'index le meuble de fiches, le mapping la règle qui dit quelles rubriques chaque fiche contient.
Dialoguer : l'API REST
  • PUT index/_doc/1 crée ou remplace, POST index/_doc génère un id, GET index/_doc/1 lit, DELETE supprime.
  • GET index/_search recherche ; POST _bulk ingère en masse.
  • Un même langage, plusieurs outils : Kibana Dev Tools, curl, clients Python.
Types de champ à connaître
  • text : texte analysé (découpé en mots) pour la recherche plein texte.
  • keyword : valeur exacte, pour filtres, tris et agrégations.
  • Par défaut, un texte reçoit les deux : titre (text) et titre.keyword.

③ Comment ④ Exemple

Le cluster : nœuds, shards, répliques

Vocabulaire
  • Cluster : ensemble de nœuds (serveurs).
  • Shard primaire : un morceau de l'index ; la répartition et le parallélisme.
  • Réplique : copie d'un shard sur un autre nœud ; tolérance aux pannes et lectures plus rapides.
  • Depuis la version 7 : 1 primaire, 1 réplique par défaut. Le nombre de primaires est fixé à la création.
SantéSignification
Verttous les shards (primaires et répliques) sont alloués
Jauneprimaires alloués, mais des répliques ne le sont pas (nœud unique avec 1 réplique)
Rougeau moins un primaire non alloué : données indisponibles
Index en 3 shards, 1 réplique
Diagnostic

GET _cluster/health ; GET _cat/shards?v ; GET _cluster/allocation/explain : pourquoi un shard n'est pas alloué (première commande à lancer en jaune ou rouge).

Chapitre 01 · Modèle de données et cluster
⑤ Pièges ⑥ Résumé

Pièges et résumé

Utiliser Elasticsearch comme source de vérité : pas de transactions multi-documents ; garder une base de référence.
Trop de petits shards : surcharge mémoire ; viser des shards de quelques dizaines de Go.
Réplique sur un cluster à un nœud : cluster jaune permanent.
Compter sur un nombre de primaires modifiable : il se fixe à la création (réindexer pour changer).
Confondre text et keyword : on ne trie pas et on n'agrège pas sur un champ analysé.
  1. Document JSON → index ; mapping = schéma ; API REST.
  2. text (analysé, recherche) contre keyword (exact, filtre, agrégation).
  3. Shards (répartition) + répliques (tolérance aux pannes) sur des nœuds.
  4. Santé : vert, jaune (répliques manquantes), rouge (primaire manquant).

Chapitre 01 · Modèle de données et cluster
Ce que le jury peut demander

Questions d'oral — chapitre 01

Le primaire porte une partie des documents et reçoit les écritures ; la réplique en est une copie sur un autre nœud, qui assure la tolérance aux pannes et partage les lectures. Une réplique n'est jamais placée sur le nœud de son primaire.

Tous les shards primaires sont alloués, donc les données sont disponibles, mais certaines répliques ne le sont pas, par exemple sur un seul nœud avec une réplique demandée. Il n'y a plus de redondance.

Un champ text est analysé : découpé en termes normalisés pour la recherche plein texte. Un champ keyword est conservé tel quel pour les filtres exacts, les tris et les agrégations.

Il n'offre pas de transactions multi-documents, les mises à jour sont coûteuses et les écritures ne sont visibles qu'après un rafraîchissement. On y place une copie indexée de données dont la référence est ailleurs.

Pour la recherche plein texte avec pertinence, les filtres et facettes sur de gros volumes et l'analyse de logs. Pour des transactions et une source de vérité, on garde une base relationnelle ou documentaire.

Chapitre 02 · Indexer : analyseurs, mapping et ingestion en masse
① Pourquoi ② Quoi

Index inversé, analyseur, mapping

L'index inversé

Pour chaque terme, la liste des documents qui le contiennent. Chercher un mot = lire une entrée, sans parcourir les documents.

texte
doc1 : « Développeur Python à Lyon »
doc2 : « Data engineer Python »
terme      → documents
python     → doc1, doc2
lyon       → doc1
engineer   → doc2
L'analyseur

Transforme un texte en termes : character filters → tokenizer (découpe) → token filters (minuscules, suppression d'accents, mots vides, racinisation). Le même analyseur doit servir à l'indexation et à la recherche.

Le mapping
  • Dynamique : Elasticsearch devine les types à la volée (pratique, mais piège : une chaîne devient text + keyword, une date mal lue devient text).
  • Explicite : on déclare les champs ; mode strict : refuse les champs inconnus.
  • Multi-fields : un même champ indexé de plusieurs façons (titre en text, titre.keyword exact).
  • Un type existant ne se modifie pas : il faut créer un nouvel index et réindexer.
http · mapping explicite
PUT offres
{ "mappings": { "dynamic": "strict", "properties": {
  "titre":   { "type": "text", "fields": { "keyword": { "type": "keyword" } } },
  "ville":   { "type": "keyword" },
  "salaire": { "type": "integer" },
  "publiee": { "type": "date" } } } }
Chapitre 02 · Indexer : analyseurs, mapping et ingestion en masse
③ Comment ④ Exemple

Écrire, ingérer en masse, rester cohérent

Le chemin d'une écriture
  • Le document va au shard primaire, puis aux répliques.
  • Il est écrit dans un tampon mémoire et dans le journal de transactions (translog) pour ne pas le perdre.
  • Un rafraîchissement (refresh, par défaut toutes les secondes) le rend cherchable : recherche quasi temps réel, pas instantanée.
  • Les données forment des segments immuables ; mise à jour = nouveau document + ancien marqué supprimé ; fusion (merge) des segments en arrière-plan.

Segments immuables : une mise à jour coûte cher (réécriture du document). On évite les mises à jour fréquentes champ par champ.

L'API _bulk et l'idempotence
  • _bulk : des milliers d'opérations en une requête (format NDJSON) : beaucoup plus rapide qu'un appel par document.
  • Idempotence : en fournissant un _id stable (par exemple l'identifiant métier), rejouer l'ingestion remplace au lieu de dupliquer.
  • Lire sans tout charger : générateurs Python et envoi par lots (Python).
python · ingestion en masse
from elasticsearch import Elasticsearch, helpers
es = Elasticsearch("http://localhost:9200")
actions = ({"_index": "offres", "_id": o["id"], "_source": o}   # _id stable
           for o in lire_offres())                                # générateur
ok, erreurs = helpers.bulk(es, actions, raise_on_error=False)
print(ok, "indexés,", len(erreurs), "erreurs")
Chapitre 02 · Indexer : analyseurs, mapping et ingestion en masse
⑤ Pièges ⑥ Résumé

Pièges et résumé

Laisser le mapping dynamique en production : un champ mal deviné bloque ou fausse tout.
Indexer un document à la fois : mille fois plus lent que _bulk.
Pas d'_id stable : un rejeu double les documents.
Analyseurs différents à l'indexation et à la recherche : on ne retrouve plus rien.
Attendre une visibilité immédiate : il faut attendre le rafraîchissement (~1 s) ou le forcer.
  1. Index inversé : terme → documents ; l'analyseur découpe et normalise.
  2. Mapping explicite (strict), multi-fields, immuable : réindexer pour changer.
  3. Écriture : primaire, répliques, translog, refresh (~1 s), segments immuables.
  4. _bulk + _id stable = ingestion rapide et rejouable.

Chapitre 02 · Indexer : analyseurs, mapping et ingestion en masse
Ce que le jury peut demander

Questions d'oral — chapitre 02

Une structure qui associe chaque terme à la liste des documents qui le contiennent, comme l'index d'un livre. Elle permet de trouver les candidats d'une recherche sans parcourir tous les documents.

Pour maîtriser les types : le mapping dynamique peut mal interpréter un champ (une date lue comme texte), et un type existant ne se modifie pas sans réindexation. Le mode strict refuse les champs imprévus.

Le document est d'abord dans un tampon et le translog ; il devient cherchable au rafraîchissement du shard, par défaut chaque seconde. On parle de quasi temps réel.

En donnant à chaque document un identifiant stable issu de la donnée (id métier). Rejouer l'import remplace les documents existants au lieu d'en créer de nouveaux.

Pour envoyer des milliers d'opérations par requête : on réduit les allers-retours réseau et la charge, et l'ingestion est bien plus rapide qu'un appel par document.

Chapitre 03 · Rechercher et agréger
① Pourquoi ② Quoi

Requête et filtre, bool, score

Contexte requête contre contexte filtre
  • Requête (must, should) : calcule un score de pertinence.
  • Filtre (filter, must_not) : oui/non, sans score, mis en cache : plus rapide.
  • Règle : texte → requête ; valeurs exactes, dates, nombres → filtre.
Le score BM25

Algorithme de pertinence par défaut : tient compte de la fréquence du terme dans le document (saturée), de sa rareté dans l'index et de la longueur du champ. Remplace TF-IDF depuis la version 5.

http · requête bool
GET offres/_search
{ "query": { "bool": {
    "must":     [ { "match": { "description": "python spark" } } ],
    "filter":   [ { "term":  { "ville": "Lyon" } },
                  { "range": { "salaire": { "gte": 40000 } } } ],
    "must_not": [ { "term":  { "type": "stage" } } ] } },
  "size": 10, "highlight": { "fields": { "description": {} } } }
Chapitre 03 · Rechercher et agréger
③ Comment ④ Exemple

Familles de requêtes, agrégations, ES|QL

Familles de requêtes
  • match : texte analysé · match_phrase : expression exacte · multi_match : plusieurs champs.
  • term / terms : valeur exacte (sur keyword) · range : bornes · exists.
  • fuzzy / fuzziness : tolérance aux fautes (distance d'édition).
  • Géographie : geo_distance. Pagination : from/size, search_after pour les gros volumes ; surlignage (highlight).

Éviter from très grand (pagination profonde) : utiliser search_after.

Agrégations
  • Buckets : regrouper (terms, date_histogram, range) — comme un GROUP BY.
  • Métriques : calculer (avg, sum, min, max, percentiles, cardinality).
  • Imbriquables : par ville, le salaire moyen.
  • "size": 0 : ne renvoyer que les agrégats.
http
GET offres/_search
{ "size": 0, "aggs": { "par_ville": {
    "terms": { "field": "ville" },
    "aggs":  { "salaire_moyen": { "avg": { "field": "salaire" } } } } } }
ES|QL

Langage de requête à pipeline d'Elastic : FROM offres | WHERE salaire > 40000 | STATS avg(salaire) BY ville | SORT ... | LIMIT 10. Plus lisible pour l'analyse.

Chapitre 03 · Rechercher et agréger
⑤ Pièges ⑥ Résumé

Pièges et résumé

Mettre un filtre exact dans must : score inutile et cache perdu ; utiliser filter.
term sur un champ text : le terme analysé n'est plus la valeur exacte ; utiliser .keyword.
Agréger sur un champ text : refusé ou coûteux ; utiliser keyword.
Pagination profonde avec from : mémoire et lenteur.
Interpréter le score comme absolu : il n'a de sens que relatif à une requête.
  1. bool : must / should (score) ; filter / must_not (oui-non, cache).
  2. BM25 : fréquence saturée, rareté, longueur du champ.
  3. match (texte) · term (exact) · range · fuzzy (fautes).
  4. Agrégations : buckets + métriques ; ES|QL pour l'analyse en pipeline.

Chapitre 03 · Rechercher et agréger
Ce que le jury peut demander

Questions d'oral — chapitre 03

En contexte requête, Elasticsearch calcule un score de pertinence ; en contexte filtre, la réponse est oui ou non, sans score, et les résultats sont mis en cache. On filtre les valeurs exactes et on réserve les requêtes au texte.

Par BM25 : il croît avec la fréquence du terme dans le document, avec un effet de saturation, et avec la rareté du terme dans l'index, et il est atténué pour les champs longs.

Match pour du texte libre : la requête est analysée comme à l'indexation. Term pour une valeur exacte, sur un champ keyword, sans analyse.

Avec la tolérance fuzziness : la requête accepte des termes à une ou deux modifications de caractères près. C'est utile pour la recherche saisie par un utilisateur.

À calculer des statistiques sur les résultats : regroupements par valeur ou par intervalle de dates (buckets) et calculs comme moyenne ou somme (métriques), imbriquables pour des analyses par catégorie.

Chapitre 04 · Kibana et Logstash
① Pourquoi ② Quoi

Kibana : explorer et visualiser

Rôle

Interface web au-dessus d'Elasticsearch : explorer, visualiser, surveiller, administrer. Aucune donnée n'y est stockée : elle interroge Elasticsearch.

Les écrans
  • Discover : explorer les documents, filtrer, chercher.
  • Dashboard / Lens : visualisations et tableaux de bord.
  • Dev Tools : console pour l'API REST.
  • Stack Management : data views, index, utilisateurs et rôles.
  • Data view : définit quels index Kibana lit (avec un champ date).
KQL (Kibana Query Language)

Syntaxe simple de filtre : ville : "Lyon" and salaire >= 40000 · message : *timeout* · not status : 200. Sert à filtrer dans Discover et les tableaux de bord.

Visualiser

  • Un tableau de bord assemble des visuels qui se filtrent entre eux.

Comparable à Power BI pour l'exploration, mais natif sur des données indexées et orienté logs et temps réel.

Chapitre 04 · Kibana et Logstash
③ Comment ④ Exemple

Logstash : un pipeline entrée, filtres, sortie

Anatomie

Un pipeline Logstash a trois étages : input (lire : fichier, Kafka, Beats, JDBC), filter (transformer), output (écrire : Elasticsearch, fichier). Chaque étage utilise des plugins.

FiltreRôle
grokextraire des champs d'une ligne de texte par motif
dissectdécoupage par délimiteurs, plus simple et rapide
datelire l'horodatage et le placer dans @timestamp
mutaterenommer, convertir, supprimer des champs
geoipajouter la localisation d'une adresse IP
csv / jsonanalyser ces formats
conf · web.conf (logs d'accès)
input  { file { path => "/data/access.log" start_position => "beginning" } }
filter {
  grok  { match => { "message" => "%{COMBINEDAPACHELOG}" } }
  date  { match => [ "timestamp", "dd/MMM/yyyy:HH:mm:ss Z" ] }
  mutate { convert => { "bytes" => "integer" } }
  geoip { source => "clientip" }
}
output { elasticsearch { hosts => ["http://es:9200"] index => "web-%{+YYYY.MM.dd}" } }
ECS

Elastic Common Schema : noms de champs standard (source.ip, http.response.status_code) pour que logs de sources différentes soient comparables dans Kibana.

Chapitre 04 · Kibana et Logstash
⑤ Pièges ⑥ Résumé

Fiabilité, pièges et résumé

Fiabilité
  • File persistante (persistent queue) : les événements survivent à un arrêt.
  • Dead letter queue : conserve les documents rejetés par Elasticsearch (erreur de mapping) pour les analyser.
  • Plusieurs pipelines (pipelines.yml) : isoler des flux aux besoins différents.
  • Sécuriser : TLS et identifiants dédiés avec droits minimaux.
Logs mal analysés : une ligne qui ne correspond pas au motif reçoit le tag _grokparsefailure ; surveiller ce tag.
Pas de filtre date : @timestamp est l'heure d'ingestion, pas l'heure de l'événement.
Index unique qui grossit sans fin : un index par jour ou une politique de cycle de vie (ILM).
  1. Kibana explore et visualise ; data view = index lus ; KQL pour filtrer.
  2. Logstash : input → filter (grok, date, mutate, geoip) → output.
  3. ECS normalise les noms de champs.
  4. File persistante, dead letter queue, pipelines multiples, TLS.
