Un système de gestion de versions

Chaque changement est un commit daté, signé, commenté. L'historique permet de comparer, d'annuler et de fusionner les travaux de chacun.

Git est un système de gestion de versions distribué : chaque développeur possède une copie complète du dépôt et de son historique. Il enregistre des instantanés (snapshots) du projet, identifiés par un hash. Les branches sont des lignes de travail parallèles, légères et peu coûteuses.

Analogie — un livre dont chaque auteur garde une copie complète avec toutes les révisions ; on propose des chapitres modifiés et on les fusionne dans la version commune.

Présenter Git en une minute

« Git est un système de gestion de versions distribué créé par Linus Torvalds en 2005. Chaque développeur a l'historique complet. Le cycle est modifier, indexer (add), enregistrer (commit) ; l'historique est un graphe de commits identifiés par un hash. On travaille sur des branches et on fusionne (merge) ou on rebase.

Le fil du cours · Git

5 idées font tout le cours

Tout Git répond à : comment garder l'historique complet d'un projet et travailler à plusieurs, sans jamais perdre ni écraser le travail des autres ? Cinq règles expliquent toutes les commandes.

Idée 1 · Un commit est un instantané, identifié par son empreinte

Git enregistre des instantanés complets du projet, les commits. Chacun est identifié par une empreinte (hash) calculée sur son contenu, et pointe vers son parent. L'historique est une chaîne : modifier un commit change son hash et celui de tous ceux qui suivent.

L'erreur typique : Si l'on croit qu'un commit est perdu après un reset, on refait le travail, alors qu'il reste retrouvable avec git reflog.

La bonne pratique : Après une erreur de reset, lancer git reflog pour retrouver le hash du commit, puis revenir dessus.

ch. 01 · ch. 02

Idée 2 · Trois zones : travail, index, dépôt

On modifie les fichiers dans le répertoire de travail, on choisit ce qui part dans le prochain commit avec add (l'index, ou zone de préparation), puis on enregistre avec commit. C'est ce qui permet des commits petits et cohérents.

L'erreur typique : Si l'on fige toutes ses modifications dans un seul gros commit « divers », personne ne peut le relire, et l'on ne peut pas en annuler une seule partie.

La bonne pratique : Faire un commit par intention (« corrige le calcul de TVA »), en n'ajoutant à l'index que les fichiers concernés.

ch. 01

Idée 3 · Une branche n'est qu'un pointeur

Une branche n'est qu'une étiquette qui pointe vers un commit : la créer ne coûte rien. HEAD indique où l'on se trouve. Merge relie deux historiques ; rebase rejoue les commits en ligne droite. Un conflit, ce sont deux modifications de la même ligne, à arbitrer à la main.

L'erreur typique : Si l'on résout un conflit en gardant sa version sans lire celle de l'autre, la modification du collègue est effacée sans que personne le remarque.

La bonne pratique : Lire les deux versions du conflit, garder ce qui respecte l'intention des deux, puis relancer les tests avant de valider la fusion.

ch. 02 · ch. 03

Idée 4 · Ne jamais réécrire l'histoire partagée

Sur une branche que l'on est seul à utiliser, on peut réécrire l'historique (amend, rebase). Sur ce qui a déjà été poussé et partagé, on annule avec revert, qui ajoute un commit inverse, plutôt qu'avec reset ou push --force.

L'erreur typique : Si l'on réécrit de force la branche principale (push --force), les commits que les collègues avaient déjà récupérés disparaissent du dépôt partagé.

La bonne pratique : Annuler un commit partagé avec git revert : un nouveau commit défait le précédent, et l'historique des collègues reste intact.

ch. 01 · ch. 02 · ch. 03

Idée 5 · Collaborer, c'est relire avant de fusionner

Le dépôt distant est la référence ; on travaille sur une branche, on ouvre une pull request, on fait relire et tester (CI) avant de fusionner. Les secrets n'entrent jamais (.gitignore) ; un secret poussé se révoque.

L'erreur typique : Si un fichier .env contenant un mot de passe est commité, toute personne qui clone le dépôt peut lire ce mot de passe, même après la suppression du fichier.

La bonne pratique : Lister .env dans .gitignore dès le début ; si un secret a été poussé, le révoquer et le remplacer, car il reste dans l'historique.

Chapitre 01 · Le modèle et les commandes de base
① Pourquoi ② Quoi

Commits, zones et historique

Un commit = un instantané

Un commit enregistre l'état complet des fichiers suivis (pas seulement la différence), un auteur, une date, un message et un parent. Son identifiant est un hash (SHA-1, 40 caractères hexadécimaux) calculé à partir du contenu : modifier l'historique change les hash.

Les états d'un fichier
  • non suivi (untracked) → git add → indexé (staged) → git commit → validé (committed).
  • modifié (modified) : suivi mais changé depuis le dernier commit.
  • .gitignore : motifs de fichiers jamais suivis (.env, pycache/, *.log).
Analogie — un photographe : on arrange la scène (index), on déclenche (commit), la photo est datée et numérotée dans l'album.
shell
git status                 # état des fichiers
git diff                   # changements non indexés
git diff --staged          # changements indexés
git add -p                 # indexer morceau par morceau
git commit -m "Corrige le calcul de la TVA"
git log --oneline --graph  # historique en arbre
git show a1b2c3d           # détail d'un commit

Chapitre 01 · Le modèle et les commandes de base
Ce que le jury peut demander

Questions d'oral — chapitre 01

add place les modifications choisies dans l'index (la zone de préparation) ; commit enregistre l'index dans le dépôt local sous forme d'un instantané avec un message. On compose donc précisément le contenu de chaque commit.

Un instantané des fichiers suivis, l'auteur, la date, un message et le lien vers son ou ses parents, le tout identifié par un hash calculé sur ce contenu. Changer quoi que ce soit change le hash.

reset déplace la branche vers un ancien commit et réécrit l'historique, ce qui est risqué sur une branche partagée ; revert ajoute un nouveau commit qui annule les effets d'un commit précédent et préserve l'historique.

Je le révoque et le remplace immédiatement, car il reste dans l'historique et dans les copies existantes ; je peux nettoyer l'historique (filter-repo) mais la révocation est la vraie protection. J'ajoute le fichier au .gitignore.

À lister les fichiers que Git ne doit pas suivre : secrets, dépendances installées, fichiers générés, journaux. Cela évite de polluer le dépôt et de publier des données sensibles.

Chapitre 02 · Branches, fusion et conflits
① Pourquoi ② Quoi

Une branche est un pointeur

Pourquoi des branches

Isoler un travail (fonctionnalité, correction) sans toucher à la ligne stable. Une branche est un simple pointeur vers un commit : la créer ne coûte presque rien. HEAD désigne la branche et le commit courants.

shell
git switch -c feature/export-csv   # crée et bascule
# ... commits ...
git switch main                   # retour
git merge feature/export-csv      # fusionne dans main
git branch -d feature/export-csv  # supprime la branche fusionnée

Chapitre 02 · Branches, fusion et conflits
③ Comment ④ Exemple

Merge, rebase et conflits

Merge contre rebase
  • merge : joint deux historiques par un commit de fusion ; historique fidèle, un peu plus touffu. Si la branche cible n'a pas bougé : fast-forward, le pointeur avance simplement.
  • rebase : rejoue vos commits au-dessus de la cible ; historique linéaire, mais les commits sont réécrits (nouveaux hash) : ne jamais rebaser une branche déjà partagée.

Règle d'or du rebase : on ne réécrit pas l'historique que d'autres ont déjà récupéré.

texte · fichier en conflit
<<<<<<< HEAD
prix = prix_ht * 1.20          # votre version (branche courante)
=======
prix = round(prix_ht * 1.2, 2) # version de l'autre branche
>>>>>>> feature/tva
Résoudre un conflit
  • Un conflit apparaît quand deux branches modifient les mêmes lignes.
  • 1. ouvrir le fichier, choisir ou combiner, supprimer les marqueurs ;
  • 2. git add fichier ; 3. git commit (ou rebase --continue).
  • Tester après résolution : le fichier compile ≠ le comportement est correct.
Chapitre 02 · Branches, fusion et conflits
⑤ Pièges ⑥ Résumé

Pièges et résumé

Branche qui vit trop longtemps : conflits massifs ; fusionner souvent, branches courtes.
Rebaser une branche partagée : les collègues se retrouvent avec des historiques divergents.
Résoudre un conflit en gardant tout les marqueurs <<<<<<< dans le code.
Travailler directement sur main : une erreur arrive en production.
Oublier de se mettre à jour avant de pousser : push refusé (non fast-forward).
  1. Branche = pointeur ; switch -c crée, merge fusionne.
  2. merge : historique fidèle ; rebase : historique linéaire mais réécrit.
  3. Conflit = mêmes lignes modifiées : choisir, add, commit, tester.
  4. Branches courtes et fusion fréquente.

Fiche — Branches

Créer / bascule

git switch -c nom · git switch nom.

Commit de fusion ou fast-forward ; historique fidèle.

rebase

Chapitre 02 · Branches, fusion et conflits
Ce que le jury peut demander

Questions d'oral — chapitre 02

Un pointeur léger vers un commit, qui avance à chaque nouveau commit. Créer une branche ne copie rien, ce qui rend le travail parallèle peu coûteux.

Merge conserve l'historique tel qu'il s'est produit en ajoutant un commit de fusion ; rebase rejoue les commits au-dessus de la cible pour un historique linéaire, mais en créant de nouveaux commits. On ne rebase pas une branche partagée.

Quand la branche cible n'a pas divergé, la fusion consiste seulement à avancer son pointeur jusqu'au dernier commit de la branche fusionnée, sans commit de fusion.

J'ouvre les fichiers marqués, je choisis ou combine les versions en comprenant l'intention de chacune, je retire les marqueurs, j'exécute les tests, puis j'indexe et je valide la fusion.

Plus une branche diverge de la principale, plus les conflits sont nombreux et pénibles, et plus le retour d'expérience est tardif. On privilégie des branches courtes, intégrées souvent.

Chapitre 03 · Collaboration et bonnes pratiques
① Pourquoi ② Quoi

Dépôt distant, clone, push, pull

Le dépôt distant

Un remote (par défaut origin) est une copie du dépôt sur un serveur (GitHub, GitLab, Bitbucket). On le clone une fois, puis on synchronise.

CommandeEffet
git clone urlcopie le dépôt et son historique
git fetchrécupère les nouveautés sans modifier votre travail
git pull= fetch + merge (ou rebase)
git pushenvoie vos commits
git push -u origin branchepublie une branche et la suit
shell · cycle d'équipe
git switch main && git pull           # se mettre à jour
git switch -c fix/doublons             # une branche par sujet
# ... modifications, commits ...
git push -u origin fix/doublons        # publier
# -> ouvrir une pull request sur GitHub / GitLab
# -> relecture, CI verte, fusion dans main

Un push est refusé si le distant a des commits que vous n'avez pas : faites d'abord pull (ou fetch puis rebase).

Chapitre 03 · Collaboration et bonnes pratiques
③ Comment ④ Exemple

Pull request, workflows, sécurité

Pull request / merge request
  • Demande de fusion relue par l'équipe : commentaires, CI exécutée automatiquement, approbation.
  • Bonne PR : petite, un sujet, description claire, tests verts.
  • Branches protégées : pas de push direct sur main, relecture obligatoire.
Workflows courants
  • Trunk-based : branches très courtes, intégration continue sur main.
  • GitHub Flow : branche par fonctionnalité + PR.
  • Git Flow : develop, release, hotfix ; plus lourd, pour des versions planifiées.
Bonnes pratiques
  • Messages : impératif, un sujet, pourquoi (« Corrige le doublon des commandes »).
  • Commits atomiques ; tags v1.2.0 pour les versions (SemVer).
  • Jamais de secrets ni de gros binaires ; utiliser .gitignore et des gestionnaires de secrets.
  • Compte protégé : authentification à deux facteurs, commits signés (GPG/SSH).

⑤ Pièges ⑥ Résumé

Pièges et résumé

push --force sur une branche partagée : écrase le travail des autres ; préférer --force-with-lease et seulement sur sa branche.
Pull sans regarder : fusion surprise ; faire un fetch d'abord si besoin.
PR énorme : irrelisible ; découper.
Dépôt public avec secret : des robots les récoltent en quelques minutes.
Ne pas relier PR et ticket : perte de traçabilité (Jira).
  1. clone, fetch, pull, push : synchroniser avec origin.
  2. Branche par sujet → PR relue → CI verte → merge.
  3. Branches protégées, 2FA, commits atomiques, SemVer.
  4. Jamais de secrets ni de force-push sur du partagé.

Chapitre 03 · Collaboration et bonnes pratiques
Ce que le jury peut demander

Questions d'oral — chapitre 03

fetch télécharge les nouveautés du dépôt distant sans toucher à votre branche de travail ; pull fait un fetch puis intègre les changements par merge ou rebase. Fetch permet de regarder avant d'intégrer.

À proposer une fusion qui sera relue par l'équipe, avec discussion, exécution automatique des tests et approbation, avant d'entrer dans la branche principale. Elle améliore la qualité et partage la connaissance.

Une branche par sujet issue de main, des commits atomiques, une pull request relue avec CI verte, des branches protégées, et des tags de version. J'intègre souvent pour limiter les conflits.

Il remplace l'historique distant par le vôtre et peut effacer des commits d'autres personnes. Sur sa propre branche on utilise --force-with-lease, qui vérifie que personne n'a poussé entre-temps.

Un numéro MAJEUR.MINEUR.CORRECTIF : le majeur change en cas de rupture de compatibilité, le mineur pour une fonctionnalité compatible, le correctif pour une correction. On l'associe à des tags Git.
