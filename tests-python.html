Chaque modification demande de rejouer des traitements longs, de comparer des fichiers à l'œil : on oublie des cas et on découvre la casse en production.

Un filet de tests automatiques

Des dizaines de petites vérifications s'exécutent en quelques secondes à chaque changement : si un comportement attendu casse, le test échoue immédiatement et dit lequel.

Un test unitaire vérifie une petite unité de code (une fonction, une classe) isolée du reste, de façon rapide, déterministe et automatique. Il joue trois rôles : détecter les régressions, documenter le comportement attendu et permettre de refactorer sans peur. En Python, l'outil de référence est pytest, à côté du module standard unittest.

Analogie — le contrôle qualité d'une chaîne de montage : chaque pièce passe un gabarit en une seconde ; si une pièce est mal usinée, on le sait avant l'assemblage, pas chez le client.

Premier contact : une fonction et ses trois tests

python · pytest
# prix.py
def prix_ttc(ht, taux=0.20):
    if ht < 0:
        raise ValueError("prix négatif")
    return round(ht * (1 + taux), 2)

# test_prix.py
import pytest
from prix import prix_ttc

def test_cas_nominal():
    assert prix_ttc(100) == 120.0

def test_taux_reduit():
    assert prix_ttc(100, 0.055) == pytest.approx(105.5)

def test_prix_negatif_refuse():
    with pytest.raises(ValueError):
        prix_ttc(-1)
# pytest -q   ->   3 passed in 0.02s

Un test est une fonction test_… qui utilise un simple assert : pytest en explique l'échec (valeur attendue, valeur obtenue). On teste le cas nominal, un cas limite et un cas d'erreur.

5 idées font tout le cours

Tout le cours répond à : comment être sûr qu'un code ou un pipeline fait ce qu'il doit, et qu'il continue de le faire à chaque modification ? Cinq règles suffisent.

Idée 1 · Beaucoup de petits tests, peu de gros

La pyramide des tests : beaucoup de tests unitaires (une fonction seule, rapides), quelques tests d'intégration (plusieurs pièces ensemble, avec une base), très peu de tests de bout en bout (tout le parcours). Plus un test est haut, plus il est lent et fragile.

L'erreur typique : Si l'on n'écrit que des tests de bout en bout, la suite est lente, et quand un test échoue on ne sait pas quelle partie du code est en cause.

La bonne pratique : Tester chaque règle par un test unitaire rapide, et garder quelques tests de bout en bout pour les parcours principaux.

ch. 01 · ch. 04

Idée 2 · Un test = un comportement, en trois temps

Un test vérifie un comportement, en trois temps : Arrange (préparer), Act (appeler), Assert (vérifier). On le nomme d'après ce comportement, et l'on teste aussi les cas limites et les erreurs attendues (pytest.raises).

L'erreur typique : Si un test ne contient aucune assertion, il passe toujours, même quand le code est faux.

La bonne pratique : Terminer chaque test par un assert précis sur le résultat (assert total == 120), ou par pytest.raises pour une erreur attendue.

ch. 01 · ch. 02

Idée 3 · Isoler ce qu'on ne contrôle pas

On isole ce qu'on ne contrôle pas. Une fixture prépare le contexte d'un test ; un double de test (stub, fake, mock) remplace la base, le réseau ou l'horloge. Un test qui dépend de l'extérieur finit par échouer pour de mauvaises raisons.

L'erreur typique : Si un test appelle vraiment le réseau ou une base partagée, il échoue un jour pour une raison qui n'a rien à voir avec le code testé.

La bonne pratique : Remplacer l'appel réseau par un double (monkeypatch ou unittest.mock) qui renvoie une réponse fixe.

ch. 02 · ch. 03

Idée 4 · La donnée se teste aussi

Les données se testent aussi. Une transformation pandas se teste sur un petit DataFrame dont on connaît le résultat ; un contrat de données vérifie le schéma, les types, l'unicité et les valeurs ; un test de propriétés (Hypothesis) génère des cas auxquels on n'avait pas pensé.

L'erreur typique : Si l'on ne teste pas les données reçues, une colonne vide ou mal typée traverse tout le pipeline jusqu'en production.

La bonne pratique : Vérifier les données à l'entrée du pipeline (colonnes, types, valeurs vides) et arrêter le traitement si le contrat n'est pas respecté.

ch. 03

Idée 5 · Un test qui ne tourne pas tout seul n'existe pas

Un test qui ne tourne pas automatiquement n'existe pas. La CI lance les tests à chaque push. La couverture montre le code jamais exécuté par un test (pas que le code est juste). Le TDD écrit le test d'abord, pour préciser le besoin.

L'erreur typique : Si l'on prend 100 % de couverture pour une preuve, on oublie qu'une ligne peut être exécutée par un test sans que son résultat soit jamais vérifié.

La bonne pratique : Se servir de la couverture pour trouver le code jamais testé, et vérifier que chaque test contient de vraies assertions.

Chapitre 01 · Pyramide des tests et bases de pytest
① Pourquoi ② Quoi

Quels tests, pour quel coût ?

Les trois étages
  • Unitaire : une fonction ou une classe, isolée ; milliers, millisecondes.
  • Intégration : plusieurs briques ensemble (code + base, code + fichier) ; dizaines, secondes.
  • Bout en bout (E2E) : le parcours complet, comme un utilisateur ; très peu, lents et fragiles.

Pyramide : beaucoup de tests rapides en bas, peu de tests coûteux en haut. Une pyramide inversée (surtout du E2E) donne une suite lente et instable.

Les qualités d'un bon test : FIRST
  • Fast : rapide.
  • Independent : indépendant des autres, dans n'importe quel ordre.
  • Repeatable : même résultat à chaque exécution, sans réseau ni horloge réelle.
  • Self-validating : réussit ou échoue seul, sans lecture à l'œil.
  • Timely : écrit avec le code (voire avant : TDD).
Arrange / Act / Assert

Arrange : préparer les données. Act : appeler le code testé (une seule action). Assert : vérifier le résultat. Équivalent de Given / When / Then.

③ Comment ④ Exemple

pytest : assertions, erreurs, paramétrisation

python
import pytest

def test_assert_simple():
    assert 0.1 + 0.2 == pytest.approx(0.3)     # flottants : jamais ==

def test_exception():
    with pytest.raises(ZeroDivisionError, match="division"):
        1 / 0

@pytest.mark.parametrize("ht, taux, attendu", [
    (100, 0.20, 120.0),
    (100, 0.055, 105.5),
    (0,   0.20, 0.0),                        # cas limite
])
def test_ttc(ht, taux, attendu):
    assert prix_ttc(ht, taux) == pytest.approx(attendu)

Un test paramétré génère un test par ligne : on voit quel cas échoue.

Découverte et commandes
  • Fichiers test_*.py, fonctions test_*, dossier tests/.
  • pytest lance tout ; -q concis, -x s'arrête au premier échec, -k motif filtre par nom, --lf rejoue les derniers échecs.
  • Marqueurs : @pytest.mark.slow, -m "not slow" ; @pytest.mark.skip, xfail.
pytest ou unittest ?

unittest (standard, classes TestCase, self.assertEqual) fonctionne partout ; pytest exécute aussi les tests unittest, avec des assertions simples et des fixtures puissantes : c'est le choix usuel.

Questions d'oral — chapitre 01

Un test automatique qui vérifie une petite unité de code, comme une fonction, de façon isolée, rapide et déterministe. Il échoue précisément quand le comportement attendu n'est plus respecté.

Chapitre 02 · Fixtures, isolation et mocks
① Pourquoi ② Quoi

Les fixtures : préparer le contexte

Une fixture, c'est quoi

Une fonction décorée par @pytest.fixture qui prépare (et nettoie) ce dont un test a besoin. Le test la demande en paramètre par son nom : pytest l'injecte. Elles remplacent le setUp / tearDown d'unittest.

Portée (scope)
  • function (par défaut) : recréée pour chaque test : isolation maximale.
  • module, session : créée une fois pour un lot de tests : plus rapide, mais risque d'état partagé.
  • conftest.py : fixtures partagées par tout un dossier de tests.
python · conftest.py
import pytest, pandas as pd

@pytest.fixture
def ventes():                                   # données minuscules, lisibles
    return pd.DataFrame({"magasin": ["A", "A", "B"], "montant": [10.0, 20.0, 5.0]})

@pytest.fixture
def base(tmp_path):                             # fixture intégrée : dossier temporaire
    chemin = tmp_path / "test.db"
    connexion = creer_base(chemin)
    yield connexion                             # le test s'exécute ici
    connexion.close()                           # nettoyage après le test

def test_total_par_magasin(ventes):
    assert total_par_magasin(ventes)["A"] == 30.0

yield sépare la préparation du nettoyage. Fixtures intégrées utiles : tmp_path (dossier temporaire), monkeypatch, capsys (sortie console), caplog (journaux).

Doubles de test : stub, fake, mock

Pourquoi remplacer une dépendance

Un test unitaire doit être rapide et déterministe : on remplace ce qui est lent (réseau, base), imprévisible (heure, aléa) ou coûteux (API payante) par un double.

python · unittest.mock
from unittest.mock import patch, Mock

def test_taux_change(monkeypatch):
    with patch("convertisseur.requests.get") as faux_get:          # cible : là où c'est UTILISÉ
        faux_get.return_value = Mock(status_code=200, json=lambda: {"EUR": 0.92})
        assert convertir(100, "USD", "EUR") == 92.0
        faux_get.assert_called_once()                                # le réseau n'est jamais touché

def test_horloge(monkeypatch):
    monkeypatch.setenv("TZ", "UTC")                                  # environnement contrôlé

patch se place là où l'objet est utilisé (convertisseur.requests), pas là où il est défini. Si possible, préférer injecter la dépendance en paramètre : plus simple à tester.

Questions d'oral — chapitre 02

À préparer le contexte d'un test, comme des données ou un fichier temporaire, et à le nettoyer ensuite grâce à yield. Le test la demande par son nom en paramètre, ce qui évite la duplication.

Chapitre 03 · Tester le code de données
① Pourquoi ② Quoi

Tester des transformations pandas

Principe

Une transformation de données est une fonction pure : DataFrame en entrée, DataFrame en sortie. On la teste avec un petit jeu d'exemple (3 à 10 lignes) dont on connaît le résultat attendu, en comparant avec pandas.testing.

python
import pandas as pd
from pandas.testing import assert_frame_equal

def test_nettoyage_supprime_doublons_et_normalise():
    brut = pd.DataFrame({"id": [1, 1, 2], "ville": [" lyon", " lyon", "PARIS"]})
    attendu = pd.DataFrame({"id": [1, 2], "ville": ["Lyon", "Paris"]})
    resultat = nettoyer(brut).reset_index(drop=True)
    assert_frame_equal(resultat, attendu)               # compare valeurs, types, index, colonnes
Ce qu'on vérifie
  • Valeurs, types (dtype), colonnes et leur ordre, index.
  • Cas limites : DataFrame vide, valeurs manquantes (NaN), doublons, texte accentué, très grands nombres.
  • Idempotence : appliquer deux fois la transformation donne le même résultat que la première fois (pipelines rejouables).
  • Conservation : pas de lignes perdues sans raison (len(avant) >= len(apres) ou règle métier explicite).

assert_frame_equal accepte check_dtype=False ou check_like=True (ordre des colonnes ignoré) : à utiliser en conscience, pas pour faire passer un test.

Chapitre 03 · Tester le code de données
③ Comment ④ Exemple

Tests de propriétés, tests de contrat de données, DAG

Tests de propriétés (Hypothesis)

Au lieu de choisir quelques exemples, on énonce une propriété qui doit toujours être vraie et la bibliothèque Hypothesis génère des centaines d'entrées (dont des cas tordus) pour tenter de la réfuter.

python
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_tri_idempotent(xs):
    assert trier(trier(xs)) == trier(xs)          # propriété : trier deux fois = trier une fois

@given(st.lists(st.integers()))
def test_tri_conserve_les_elements(xs):
    assert sorted(trier(xs)) == sorted(xs)

Hypothesis réduit automatiquement un contre-exemple à sa forme minimale : on obtient un cas simple à corriger.

Tests de données et de pipelines
  • Règles de qualité sous forme de tests : clé unique, pas de NaN sur une colonne obligatoire, valeurs dans un ensemble (Qualité des données, Great Expectations).
  • Intégrité d'un DAG Airflow : un test charge le DagBag et vérifie l'absence d'erreur d'import, les dépendances et les valeurs par défaut (Airflow).
  • Test d'intégration : exécuter le pipeline sur un mini jeu de données avec une base SQLite en mémoire ou un conteneur (Docker).
  • Données de test : factices ou anonymisées, jamais la production brute (données sensibles).
PySpark

On teste la logique sur une petite SparkSession locale (master("local[1]")) avec peu de partitions ; les tests sont plus lents : on garde la majorité de la logique en fonctions pures testables sans Spark.

Ce que le jury peut demander

Questions d'oral — chapitre 03

Avec un petit DataFrame d'entrée dont je connais le résultat, comparé au DataFrame attendu par assert_frame_equal, en ajoutant les cas limites : vide, valeurs manquantes, doublons et types.

Un test qui énonce une propriété toujours vraie, par exemple trier deux fois donne le même résultat, et laisse Hypothesis générer de nombreuses entrées pour tenter de la réfuter, en ramenant tout contre-exemple à sa forme minimale.

Parce qu'un pipeline peut être rejoué après un échec : appliquer deux fois la même transformation ne doit pas dupliquer ni corrompre les données.

Avec un test qui charge les DAG et vérifie l'absence d'erreur d'import, la présence des tâches attendues et les dépendances, ce qui détecte les erreurs avant le déploiement.

De petits jeux factices ou anonymisés, versionnés avec le code, qui couvrent les cas limites ; jamais d'extrait brut de production contenant des données personnelles.

Couverture de code et TDD

La couverture

La couverture (pytest-cov) mesure la part du code exécutée par les tests : lignes, et branches (--cov-branch) pour les if. Elle sert à repérer le code non testé.

shell
pytest --cov=monpaquet --cov-branch --cov-report=term-missing
# Name            Stmts  Miss Branch BrPart  Cover   Missing
# prix.py            12     2      4      1    83%   18-19
pytest --cov=monpaquet --cov-fail-under=80      # échoue si < 80 %

Couverture ≠ qualité : un test sans assertion couvre des lignes sans rien vérifier. Un seuil raisonnable (70-85 %) sert de garde-fou, pas d'objectif en soi.

TDD : Red, Green, Refactor
  • Red : écrire d'abord un test qui échoue (il exprime le comportement voulu).
  • Green : écrire le code minimal qui le fait passer.
  • Refactor : améliorer le code, tests au vert en filet de sécurité.
  • Atouts : conception testable, code plus simple, specification vivante. Limite : demande de la discipline.
Autres techniques
  • Test de mutation (mutmut) : on modifie légèrement le code ; si aucun test n'échoue, les tests sont faibles.
  • Tests de non-régression : un test par bug corrigé.
  • Snapshot / golden files : comparer une sortie à une référence validée.

Intégration continue et organisation

Les tests dans la CI

À chaque commit ou pull request, la CI exécute la suite de tests (DevOps, Git). Un test rouge bloque la fusion. Avantages : feedback en quelques minutes, personne ne casse la branche principale sans le savoir.

yaml · GitHub Actions
name: tests
on: [push, pull_request]
jobs:
  pytest:
    runs-on: ubuntu-latest
    strategy: { matrix: { python: ["3.11", "3.12"] } }          # plusieurs versions
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "${{ matrix.python }}" }
      - run: pip install -r requirements.txt pytest pytest-cov
      - run: pytest --cov=monpaquet --cov-fail-under=80
Organiser les tests
  • Un dossier tests/ qui reflète le paquet ; un fichier de test par module.
  • Noms explicites : test_prix_negatif_leve_valueerror.
  • Séparer unitaires (rapides, à chaque commit) et intégration (plus lents, marqueur slow).
  • Tests flaky (qui échouent au hasard) : à corriger ou isoler immédiatement, sinon on ne croit plus la suite.

Tester une API FastAPI avec TestClient et une base jetable : voir API Python. Tester la sécurité : tests de sécurité.

⑤ Pièges ⑥ Résumé

Pièges et résumé

Viser 100 % de couverture : on écrit des tests vides pour atteindre un chiffre.
Tests écrits après coup pour « couvrir » : ils figent les bugs existants.
Suite lente (plus de quelques minutes) : on cesse de la lancer.
Tests flaky tolérés : on ignore les échecs, donc les vrais aussi.
Pas de CI : les tests ne protègent que si on les lance.
  1. Couverture : lignes et branches ; garde-fou, pas preuve de qualité.
  2. TDD : Red, Green, Refactor ; test de mutation pour juger les tests.
  3. CI : tests à chaque commit, rouge = fusion bloquée, matrice de versions.
  4. Tests rapides, nommés, séparés ; flaky traités tout de suite.

Ce que le jury peut demander

Questions d'oral — chapitre 04

La proportion de lignes ou de branches exécutées par les tests. Elle repère le code non testé, mais ne dit pas si les tests vérifient quelque chose : un test sans assertion couvre sans protéger.

Red : écrire un test qui échoue et exprime le comportement voulu ; Green : écrire le code minimal qui le fait passer ; Refactor : améliorer le code en gardant les tests au vert.

À évaluer la qualité des tests : on introduit de petites modifications dans le code ; si aucun test n'échoue, c'est que les tests ne détectent pas ce changement de comportement.

Un workflow exécute pytest avec la couverture à chaque push et pull request, sur plusieurs versions de Python, et un échec bloque la fusion ; les tests lents sont séparés par marqueur.

Le traiter immédiatement : identifier la cause, souvent une dépendance à l'heure, à l'ordre ou au réseau, la corriger ou l'isoler, car il décrédibilise toute la suite.
