Ouvrir la base à chaque application

Chaque client connaît le schéma, les identifiants et le SQL : une modification casse tout le monde, et aucune règle n'est imposée.

Placer une API devant la base

Un serveur unique reçoit des requêtes HTTP, valide, applique les règles, interroge la base et répond en JSON. Les clients ne voient que le contrat de l'API.

Une API (Application Programming Interface) est un contrat d'échange entre programmes. Une API REST l'exprime avec des ressources (URL), des verbes HTTP (GET, POST, PUT, PATCH, DELETE) et des codes de retour (200, 201, 404…). FastAPI est le framework Python qui la construit avec validation et documentation automatiques.

Analogie — le serveur d'un restaurant. Le client ne va pas en cuisine : il commande sur la carte (le contrat), le serveur vérifie la commande, la transmet et rapporte le plat.

5 idées font tout le cours

Tout le cours répond à : comment exposer des données à d'autres programmes avec un contrat clair, fiable et testable ? Cinq règles organisent REST, FastAPI, SQLModel et les tests.

Idée 1 · Le contrat avant le code

Une API REST expose des ressources (des noms au pluriel : /clients, /commandes). On agit dessus avec les verbes HTTP (GET lire, POST créer, PUT ou PATCH modifier, DELETE supprimer) et elle répond par un code de statut (200, 201, 404, 422…) qui dit ce qui s'est passé. Le client ne dépend que de ce contrat.

L'erreur typique : Si l'on crée des adresses comme /getClients ou /deleteClient, l'action est cachée dans le nom au lieu d'être portée par le verbe HTTP : le contrat devient incohérent et difficile à deviner.

La bonne pratique : Une seule ressource /clients : GET /clients/42 lit le client 42, DELETE /clients/42 le supprime ; le verbe dit l'action.

ch. 01 · ch. 02

Idée 2 · Les types sont le contrat exécutable

Avec FastAPI, les types Python et les modèles Pydantic décrivent ce que l'API accepte et renvoie. Ils valident l'entrée (réponse 422 si elle est invalide), convertissent la sortie en JSON et produisent la documentation (OpenAPI, visible sur /docs). On écrit un modèle par usage : un pour créer, un pour lire, un pour modifier.

L'erreur typique : Si la route renvoie directement la ligne de la table, des champs internes (mot de passe haché, identifiants techniques) sortent de l'API.

La bonne pratique : Déclarer un modèle de sortie (response_model=ClientPublic) qui ne contient que les champs à montrer : le mot de passe haché ne peut pas sortir.

ch. 02 · ch. 03

Idée 3 · Sans état, chaque requête se suffit

Le serveur ne garde aucun contexte de session en mémoire entre deux requêtes (les données, elles, sont en base) ; tout ce qu'il faut pour traiter la requête voyage avec elle (jeton, paramètres). C'est ce qui permet de lancer plusieurs instances derrière un répartiteur.

L'erreur typique : Si le serveur garde en mémoire des informations entre deux requêtes, tout se dérègle dès qu'on lance une deuxième instance : la requête suivante arrive sur l'autre instance, qui ne sait rien.

La bonne pratique : Transmettre à chaque requête tout ce qu'il faut (le jeton dans l'en-tête Authorization) et garder les données en base : n'importe quelle instance peut répondre.

ch. 01 · ch. 04

Idée 4 · La base derrière une session

SQLModel relie les classes Python aux tables. Une session est la conversation avec la base : elle regroupe les écritures et ne les enregistre qu'au commit. FastAPI ouvre une session neuve pour chaque requête et la ferme après, grâce à l'injection de dépendances (Depends).

L'erreur typique : Si une seule session est partagée par toute l'application, les écritures de deux requêtes simultanées se mélangent.

La bonne pratique : Déclarer une dépendance get_session qui ouvre une session, la donne à la route, puis la ferme : chaque requête a la sienne.

ch. 03 · ch. 04

Idée 5 · Tester en remplaçant les dépendances

TestClient appelle l'API dans le test, sans lancer de serveur. dependency_overrides remplace une dépendance (par exemple la vraie base) par une version de test. On vérifie les erreurs (404, 422) autant que les succès.

L'erreur typique : Si les tests utilisent la vraie base, ils sont lents, dépendent des données du moment et risquent de les modifier.

La bonne pratique : Remplacer get_session par une session sur une base de test vide, créée pour le test puis jetée.

⑤ Pièges ⑥ Résumé

Pièges de conception

Mettre un verbe dans l'URL (/getClient, /supprimerClient) : le verbe HTTP porte l'action.
Renvoyer 200 pour tout, même une erreur : les clients ne peuvent plus réagir.
Utiliser GET pour modifier : un GET doit être sans effet de bord (mis en cache, pré-chargé).
Confondre PUT et PATCH : PUT remplace tout l'objet, PATCH n'envoie que les champs modifiés.
Faire dépendre une requête de la précédente : le serveur est sans état ; l'identité passe par un jeton à chaque appel.
  1. REST : ressources (noms), verbes HTTP, codes, sans état.
  2. GET lit · POST crée (201) · PUT remplace · PATCH modifie · DELETE supprime (204).
  3. 2xx succès · 4xx faute du client · 5xx faute du serveur.
  4. JSON est le format d'échange standard.

Chapitre 01 · Concepts d'une API REST
Ce que le jury peut demander

Questions d'oral — chapitre 01

Une interface HTTP qui expose des ressources identifiées par des URL. Les verbes HTTP expriment l'action, les codes le résultat, le format est le plus souvent JSON, et le serveur est sans état : chaque requête contient toutes les informations nécessaires.

PUT remplace entièrement la ressource par la représentation envoyée ; PATCH ne modifie que les champs transmis. PUT est idempotent par définition ; PATCH ne l'est pas toujours.

Le serveur ne garde pas de contexte de session entre deux requêtes ; chacune porte ses propres informations, jeton d'authentification compris. On peut ainsi répartir les requêtes sur plusieurs serveurs et monter en charge facilement.

401 si l'appelant n'est pas authentifié, 403 s'il l'est mais n'a pas le droit, 404 si la ressource n'existe pas. Retourner 404 plutôt que 403 peut aussi éviter de révéler l'existence d'une ressource.

REST est simple, cacheable et standard ; GraphQL laisse le client choisir les champs et évite le sur- ou sous-chargement, au prix d'une complexité côté serveur. Pour une API de données classique, REST suffit.

Ce que le jury peut demander

Questions d'oral — chapitre 02

FastAPI s'appuie sur les annotations de type pour valider les données et générer la documentation automatiquement, supporte nativement l'asynchrone (ASGI) et offre de très bonnes performances. Flask est plus minimaliste : validation et documentation sont à ajouter.

À déclarer la structure et les types des données, à les convertir et les valider, et à produire une erreur 422 détaillée. Il garantit que le code reçoit des données conformes et alimente la documentation OpenAPI.

Parce que les champs diffèrent : l'id est généré par la base, le mot de passe ne doit jamais être renvoyé, et les champs sont optionnels en mise à jour. Des schémas distincts évitent les fuites et rendent le contrat explicite.

Avec Swagger UI sur /docs, générée à partir du contrat OpenAPI : on déclenche chaque route depuis le navigateur. En automatique, on utilise Pytest avec le client de test.

Que la requête est bien formée mais que les données ne respectent pas le schéma : type erroné, champ manquant. FastAPI renvoie la liste des champs fautifs sans que le développeur n'écrive de contrôle.

Chapitre 03 · SQLModel : modèles, session et relations
① Pourquoi ② Quoi

SQLModel = SQLAlchemy + Pydantic

L'idée

Une seule classe décrit à la fois la table SQL (SQLAlchemy, l'ORM) et le schéma de validation (Pydantic). table=True en fait une table. Un ORM (Object-Relational Mapping) fait correspondre classes et tables.

Le cycle d'une session
  • engine = create_engine(url) : connexion (SQLite pour tester, MariaDB en projet).
  • SQLModel.metadata.create_all(engine) : crée les tables.
  • with Session(engine) as s: : unité de travail.
  • s.add(obj) puis s.commit() : écrit ; sans commit, rien n'est enregistré.

L'URL de connexion (identifiant, mot de passe) vient de variables d'environnement, jamais du code (Docker, .env).

python · modèle et CRUD
from sqlmodel import SQLModel, Field, Session, create_engine, select

class Client(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    nom: str = Field(index=True)
    ville: str | None = None

engine = create_engine("sqlite:///base.db")
SQLModel.metadata.create_all(engine)

with Session(engine) as s:
    s.add(Client(nom="Durand", ville="Lyon"))
    s.commit()                                   # écrit
    c = s.exec(select(Client).where(Client.ville == "Lyon")).first()
    c.ville = "Paris"; s.add(c); s.commit()      # UPDATE
    s.delete(c); s.commit()                      # DELETE

③ Comment ④ Exemple

Relations : one-to-many et many-to-many

One-to-many

Une équipe a plusieurs héros. Côté « plusieurs » : une clé étrangère equipe_id (foreign_key="equipe.id"). Des Relationship(back_populates=...) des deux côtés donnent la navigation equipe.heros et hero.equipe.

Many-to-many

Un héros dans plusieurs équipes et inversement : il faut une table de liaison (HeroTeamLink) portant les deux clés étrangères, toutes deux clés primaires. Voir la modélisation en Merise (entité associative).

Suppression

ondelete="RESTRICT" empêche de supprimer une équipe encore liée ; "CASCADE" supprime aussi les enfants. À choisir selon la règle métier.

⑤ Pièges ⑥ Résumé

Pièges et résumé

Oublier commit() : les modifications restent en mémoire de la session et sont perdues.

  1. Une classe table=True = table SQL + validation Pydantic.
  2. Engine → create_all → Session → add / commit / exec(select).
  3. 1-N : clé étrangère + Relationship. N-N : table de liaison.
  4. Toujours commit(), with Session, variables d'environnement.

Chapitre 03 · SQLModel : modèles, session et relations
Ce que le jury peut demander

Questions d'oral — chapitre 03

Un ORM fait correspondre des classes Python à des tables : on manipule des objets au lieu d'écrire du SQL. Il réduit le code répétitif, évite certaines injections SQL et rend le modèle versionnable. On garde le SQL pour les requêtes complexes.

Une même classe sert de modèle de table et de schéma Pydantic, ce qui évite de dupliquer les définitions et s'intègre naturellement à FastAPI.

Les changements restent dans la transaction de la session et sont annulés à sa fermeture ; rien n'est écrit en base. Le commit valide la transaction.

Avec une table de liaison portant les clés étrangères des deux tables, qui forment ensemble sa clé primaire. SQLModel la déclare via link_model dans les Relationship.

Parce qu'elle contient des identifiants : on la lit dans des variables d'environnement, hors du dépôt, pour changer de base sans modifier le code et ne pas divulguer de secret.

Chapitre 04 · Organisation, erreurs et tests
① Pourquoi ② Quoi

Injection de dépendances et organisation du projet

Depends : demander ce dont on a besoin

Une dépendance est une fonction que FastAPI exécute avant la route et dont il injecte le résultat. Typiquement la session : ouverte pour la requête, fermée après (yield). Les routes ne créent plus leurs connexions : elles sont testables (on remplace la dépendance).

python
def get_session():
    with Session(engine) as session:
        yield session                 # fermée après la réponse

@router.get("/clients/{id}", response_model=ClientPublic)
def lire(id: int, session: Session = Depends(get_session)):
    client = session.get(Client, id)
    if not client:
        raise HTTPException(404, "Client introuvable")
    return client
Structure recommandée
  • main.py : crée l'app, inclut les routers.
  • routes/ : un APIRouter par ressource (prefix, tags).
  • models/ : tables · schemas/ : entrée/sortie.
  • services/ ou crud/ : logique métier · database.py : engine, session.
  • tests/ · .env · Dockerfile.
Analogie — une cuisine de restaurant : les routes sont les passe-plats, les services les postes, la base le garde-manger. Chaque poste a sa place.

Gérer les erreurs et tester avec Pytest

Erreurs
  • raise HTTPException(status_code=404, detail="…") répond proprement.
  • Traduire les erreurs de base (doublon → 409, clé étrangère → 400/409) au lieu de laisser un 500.
  • Des gestionnaires d'exceptions globaux uniformisent le format des erreurs.
  • Ne jamais renvoyer la trace ni la requête SQL au client.
python · tests
from fastapi.testclient import TestClient
import pytest

@pytest.fixture
def client():
    app.dependency_overrides[get_session] = session_de_test  # SQLite en mémoire
    yield TestClient(app)
    app.dependency_overrides.clear()

def test_creation(client):
    r = client.post("/clients", json={"nom": "Petit", "email": "p@x.fr"})
    assert r.status_code == 201
    assert r.json()["nom"] == "Petit"
Les tests
  • Unitaires : une fonction isolée · intégration : route + base.
  • Fixtures : préparent un client de test et une base jetable (SQLite en mémoire).
  • dependency_overrides remplace la vraie base par la base de test.
  • Couverture (pytest --cov) mesure le code exécuté ; en CI, les tests tournent à chaque push.

Un test se structure en Arrange / Act / Assert : préparer, appeler, vérifier le code HTTP et le corps.

--host 0.0.0.0 est indispensable : avec 127.0.0.1, Uvicorn n'écoute que l'intérieur du conteneur et le port publié ne répond pas.

Compose : l'API et sa base
  • Deux services : api (construit depuis le Dockerfile) et db (image PostgreSQL ou MariaDB, volume nommé).
  • L'URL de connexion vient d'une variable d'environnement : l'hôte est le nom du service db.
  • Le détail des images, volumes, réseaux et healthchecks est dans Docker.
Bonnes pratiques du support
  • Environnements séparés : docker-compose.override.yml en développement, .env.dev et .env.prod, image de production multi-stage.
  • Sécurité : aucun secret dans l'image ; .dockerignore exclut .env, .git, pycache.
  • Optimisation : image officielle slim, --no-cache-dir, COPY requirements.txt avant le code.

⑤ Pièges ⑥ Résumé

Pièges et résumé

Tester contre la vraie base : tests lents, données polluées ; utiliser une base jetable.
Laisser fuir un 500 avec la trace SQL : mapper les erreurs de base en codes 4xx explicites.
Tout dans main.py : routes, modèles et connexion mélangés, impossible à tester.
Tests qui dépendent les uns des autres : chaque test crée ses données (fixtures).
Pas de sécurité : une API publique sans authentification ni limitation expose la base (Sécurité des applications).
  1. Depends(get_session) : session injectée, remplaçable en test.
  2. APIRouter par ressource ; séparer routes, modèles, schémas, services.
  3. HTTPException + mapping des erreurs de base : jamais de trace au client.
  4. Pytest + TestClient + fixtures + base jetable ; couverture en CI.

Questions d'oral — chapitre 04

À fournir aux routes ce dont elles ont besoin (session de base, utilisateur courant) sans qu'elles le construisent. La ressource est créée et libérée par FastAPI, et on peut la remplacer en test.

Un point d'entrée main.py, des routers par ressource, des dossiers pour les modèles de table, les schémas, la logique métier et la connexion à la base, plus les tests et un Dockerfile. Chaque couche a une seule responsabilité.

Avec Pytest et le client de test, en remplaçant la dépendance de session par une base SQLite en mémoire créée par une fixture. Le test envoie la requête et vérifie le code de statut et le corps.

Intercepter l'erreur d'intégrité de la base et la traduire en réponse 409 avec un message clair, au lieu de laisser remonter un 500 qui exposerait des détails internes.

Absence d'authentification, fuite de champs sensibles, injection, absence de limitation de débit, messages d'erreur trop détaillés. On filtre les sorties, on authentifie, on valide, on limite et on journalise.
