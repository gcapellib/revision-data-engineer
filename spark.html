Spark

Distribué et en mémoire, avec une API proche de pandas et du SQL : on décrit toute la chaîne, Spark l'optimise et l'exécute sur le cluster.

Apache Spark est un moteur de calcul distribué qui traite de grands volumes en mémoire, en batch comme en flux, avec des API Python, Scala, Java et SQL.

Analogie — le chef et sa brigade. Tu donnes la recette complète (le plan) ; le chef (driver) la réorganise pour gagner du temps, la répartit entre ses cuisiniers (executors), et chacun travaille sur son bac d'ingrédients (partition) — sans tout ranger au frigo entre deux étapes, contrairement à MapReduce.

Premier contact : cinq lignes de PySpark

python · chiffre d'affaires par magasin
from pyspark.sql import SparkSession, functions as F
spark = SparkSession.builder.master("local[*]").getOrCreate()  # le moteur
ventes = spark.read.parquet("lake/ventes")                     # des milliards de lignes possibles
(ventes.groupBy("store")                                       # comme un GROUP BY
       .agg(F.sum("total").alias("ca"))
       .orderBy(F.desc("ca"))
       .show(3))                                                # l'action qui déclenche tout
# +------+---------+
# |store |       ca|
# |Paris | 1284.60 |
# |Lyon  |  962.40 |
# |Lille |  311.20 |
Ce qu'il faut remarquer

Le même code tourne sur ton portable (local[*]) ou sur 200 machines : seule la configuration change. Rien ne se calcule avant show() : Spark a d'abord construit et optimisé le plan.

Immersion · Essentiel

Présenter Spark en une minute

« Apache Spark est un moteur de calcul distribué en mémoire, né en 2009 à l'université de Berkeley et devenu le standard du traitement de données à grande échelle. Il propose des API Python, Scala, Java et SQL autour d'une abstraction centrale, le DataFrame.

Contrairement à MapReduce qui écrit sur disque entre chaque étape, Spark garde les données intermédiaires en mémoire et utilise l'évaluation paresseuse : il construit tout le plan, l'optimise avec Catalyst, puis l'exécute en parallèle sur les executors. Le même moteur traite le batch, le SQL, le streaming et le machine learning.

Je l'utilise pour les ETL lourds : nettoyer, joindre, agréger et écrire en Parquet partitionné. Je ne l'utilise pas quand les données tiennent sur une machine : pandas ou DuckDB suffisent. »

Le fil du cours · Spark

6 idées font tout le cours

Tout Spark répond à : comment traiter de gros volumes en mémoire sur un cluster, sans écrire soi-même de code distribué ? Six idées expliquent les performances, les pannes et les pièges.

Idée 1 · Rien ne s'exécute avant une action

Spark est paresseux : les transformations (filter, select…) ne font qu'ajouter des étapes à un plan. Seule une action (count, write, show) lance le calcul. Cela permet à l'optimiseur (Catalyst) d'améliorer tout le plan, mais chaque action recalcule tout depuis le début, sauf ce qu'on a mis en cache.

L'erreur typique : Si l'on appelle count() dans une boucle, tout le plan de calcul est réexécuté à chaque tour.

La bonne pratique : Appeler une seule action à la fin, ou mettre en cache (cache()) un résultat intermédiaire réutilisé plusieurs fois.

ch. 01 · ch. 04

Idée 2 · La partition est l'unité de tout

Les données sont découpées en partitions, traitées en parallèle par les executors (les processus de travail) ; le driver coordonne. Trop peu de partitions laisse des cœurs inactifs ; des partitions déséquilibrées créent une tâche qui traîne pendant que les autres attendent.

L'erreur typique : Si les données sont regroupées sur une clé très inégale (un client qui pèse la moitié des lignes), une seule tâche fait l'essentiel du travail pendant que les autres attendent.

La bonne pratique : Repérer la clé trop grosse dans l'interface de Spark, puis la répartir (ajouter un sel à la clé) ou laisser l'AQE de Spark 3 découper les partitions trop grosses.

ch. 01 · ch. 04 · ch. 05 · ch. 06

Idée 3 · Le shuffle est le prix à payer

Une transformation étroite (filter, select) travaille dans sa partition. Une transformation large (groupBy, join, distinct) doit faire passer les données sur le réseau pour regrouper les clés : c'est le shuffle, l'étape la plus chère. Optimiser, c'est d'abord réduire les shuffles.

L'erreur typique : Si l'on joint deux grandes tables sans filtrer avant, ou sans diffuser (broadcast) une petite table, Spark déplace d'énormes volumes sur le réseau.

La bonne pratique : Filtrer et ne garder que les colonnes utiles avant la jointure, et diffuser la petite table (broadcast) à toutes les machines.

ch. 01 · ch. 03 · ch. 04

Idée 4 · Le schéma d'abord, les données sales à part

Un DataFrame est une table typée et répartie. On déclare son schéma au lieu de le laisser deviner, on valide les données, et l'on met les lignes invalides en quarantaine au lieu de les perdre ou de faire échouer tout le traitement.

L'erreur typique : Si l'on laisse Spark deviner le schéma (inferSchema) sur un fichier réel, des colonnes sont mal typées et le fichier est lu deux fois.

La bonne pratique : Déclarer le schéma (StructType) à la lecture, et écrire les lignes qui ne le respectent pas dans un dossier de quarantaine.

ch. 02 · ch. 03 · ch. 06

Idée 5 · Un flux est une table qui ne finit jamais

Le streaming structuré traite un flux comme une table qui grandit sans fin, découpée en micro-lots, avec les mêmes opérations qu'en batch. Le temps de l'événement (quand il s'est produit), les fenêtres et le watermark (le retard maximum accepté) gèrent les données en retard ; le checkpoint enregistre où l'on en est pour reprendre sans perte.

L'erreur typique : Sans watermark, Spark garde en mémoire l'état de toutes les fenêtres, indéfiniment ; sans checkpoint, un redémarrage rejoue des données ou en perd.

La bonne pratique : Poser un watermark (withWatermark('ts', '10 minutes')) et un dossier de checkpoint sur chaque requête de streaming.

ch. 05 · ch. 06

Idée 6 · Rester dans le moteur

Pour rester rapide, on reste dans le moteur de Spark : des fonctions natives plutôt que des UDF Python (fonctions écrites par l'utilisateur), pas de collect() sur de gros volumes, du cache seulement pour ce qui est réutilisé. Tout ce qui sort de la machine virtuelle Java ou ramène les données au driver casse les optimisations.

L'erreur typique : Si l'on ramène des millions de lignes au driver avec collect(), sa mémoire déborde et le job s'arrête.

La bonne pratique : Écrire le résultat avec write vers un fichier ou une table, et n'utiliser collect() que sur un petit résultat (après un limit ou une agrégation).

Chapitre 01 · Le modèle mental
③ Comment ④ Preuve

Paresse : transformations et actions

Transformations — décrivent, ne calculent rien

select, filter, withColumn, groupBy().agg(), join, orderBy. Elles renvoient un nouveau DataFrame et enrichissent le plan (DAG).

Actions — déclenchent le calcul

show, count, collect, first, take, write, toPandas. Spark optimise alors tout le plan d'un coup.

python · mesure du nombre de jobs (Spark 4.2.0)
d2 = (df.filter(F.col("qty") > 3)
        .withColumn("total", F.col("qty") * F.col("unit_price")))
# jobs ajoutés par filter + withColumn : 0
d2.count()   # jobs après un count()    : 2
d2.count()   # jobs après un 2e count() : 4  → tout est RECALCULÉ
Conséquence n°1

Chaque action repart de la source. show() + count() + write sans cache = trois calculs complets, sans aucun avertissement.

Conséquence n°2

La lecture n'est pas totalement paresseuse : inferSchema=True déclenche 2 jobs pour deviner les types. En production : schéma explicite.

Conséquence n°3

Les erreurs de données n'apparaissent qu'à l'action (voir ch. 02), loin de la ligne qui les a causées.

Chapitre 01 · Le modèle mental
③ Comment ⑤ Pièges ⑥ Résumé

Narrow, wide, immuabilité

Transformation étroite (narrow)

filter, withColumn, select : chaque partition est traitée seule, sans réseau. Rapide.

Transformation large (wide)

groupBy, join, orderBy, distinct : il faut rapprocher des lignes de partitions différentes → shuffle (nommé Exchange dans le plan), même principe que le shuffle de MapReduce. C'est le coût principal d'un job.

Immuabilité

d3 = df.withColumn("qty", F.col("qty") * 10) : la somme de df reste 144, celle de d3 vaut 1440. Pas de df['qty'] = … : on réaffecte (df = df.withColumn(…)). C'est ce qui permet à Spark de recalculer une partition perdue à partir de son plan (lignage) : la tolérance aux pannes sans réplication des données intermédiaires.

« Une action = un job. » Faux : count() en a lancé deux.
Plusieurs actions sans cache : la source est relue à chaque fois.
Spark pour 50 Mo : plus lent et plus coûteux que pandas.
Ordre des lignes : jamais garanti après un regroupement ; trier explicitement.
  1. Driver (plan) → gestionnaire (YARN, K8s) → executors (tasks sur partitions).
  2. Transformations paresseuses, actions qui déclenchent ; chaque action recalcule.
  3. Narrow = sans réseau ; wide = shuffle, le coût principal.
  4. DataFrames immuables ; le lignage permet de recalculer une partition perdue.

Chapitre 01 · Le modèle mental
Ce que le jury peut demander

Questions d'oral — chapitre 01

MapReduce écrit sur disque la sortie de chaque étape et de chaque job, et ne voit qu'un map et un reduce à la fois. Spark garde les résultats intermédiaires en mémoire, construit le plan complet de la requête (DAG) et l'optimise globalement (Catalyst) avant d'exécuter : moins d'I/O, moins de shuffles, réutilisation possible via le cache. Le gain est maximal pour les traitements multi-étapes et itératifs (ML).

Les transformations ne calculent rien : elles décrivent un plan. Seule une action déclenche l'exécution. Intérêt : Spark voit toute la chaîne et peut l'optimiser (élaguer les colonnes, pousser les filtres à la source, choisir la jointure). Contrepartie : chaque action recalcule tout si l'on ne met pas en cache, et les erreurs de données apparaissent tard.

Quand les données tiennent confortablement en mémoire d'une machine (quelques Go) : pandas est plus simple, démarre instantanément et va plus vite (mesuré : 0,020 s contre 0,65 s, plus 9 à 32 s de démarrage de session). Spark se justifie quand le volume ou le calcul dépasse une machine, ou pour du streaming. Choisir l'outil proportionné, c'est aussi de l'éco-conception.

Grâce au lignage : un DataFrame immuable connaît la suite de transformations qui l'a produit. Si une partition est perdue, Spark la recalcule à partir de la source et du plan, sans avoir répliqué les données intermédiaires (contrairement à HDFS qui réplique les blocs).

Spark remplace MapReduce (le moteur), pas tout Hadoop : il tourne souvent sur YARN, lit et écrit sur HDFS (ou S3), et partage le Metastore Hive pour les tables. Le concept de shuffle est le même.

Chapitre 02 · DataFrames
① Pourquoi ② Quoi

Un DataFrame, c'est une table typée et distribuée

Un DataFrame = des lignes réparties en partitions + un schéma (noms et types des colonnes). Grâce au schéma, Spark vérifie ton code avant de l'exécuter et optimise le plan.

Analogie — le bon de livraison. Le schéma, c'est la fiche qui accompagne les cartons : « 6 colonnes, celle-ci contient des dates, celle-là des prix ». Sans fiche, l'entrepôt doit ouvrir chaque carton pour deviner (inferSchema) ; avec une fiche fausse, il range mal sans le savoir.
Sans schéma

Tout est lu comme texte, même les quantités et les prix : les calculs deviennent faux ou impossibles.

inferSchema=True

Spark lit les données pour deviner les types (2 jobs avant la moindre action). Coûteux sur un gros fichier, et la devinette peut changer d'un fichier à l'autre.

Schéma explicite (production)

Tu décris les colonnes toi-même : lecture unique, types garantis, contrat clair avec la source.

python · schéma explicite
from pyspark.sql.types import StructType, StructField, IntegerType, DateType, StringType, DecimalType
schema = StructType([
    StructField("order_id",   IntegerType(),     False),
    StructField("date",       DateType(),        True),
    StructField("store",      StringType(),      True),
    StructField("qty",        IntegerType(),     True),
    StructField("unit_price", DecimalType(8, 2), True),   # argent : DECIMAL
])
df = spark.read.csv("ventes.csv", header=True, schema=schema)

Double ou Decimal ? La même somme donne 3155.3999999999996 en double et 3155.40 en decimal. Le double est binaire (comme 0.1 + 0.2 en Python) : jamais pour de l'argent.

« Non-nullable » n'est pas un contrôle : à la lecture d'un fichier, Spark l'ignore. La qualité se vérifie (comptages, règles), elle ne se déclare pas.

    inferSchema relit les données (coût) et peut deviner des types différents d'un fichier à l'autre. Le schéma explicite est un contrat avec la source : types stables, lecture unique, anomalies détectables. C'est une exigence de qualité en production.

           F.round(F.avg("total"), 2).alias("panier_moyen"))
      .orderBy(F.desc("ca"))
      .show())

# tableau croisé : une colonne par produit
clean.groupBy("store").pivot("product").agg(F.sum("qty"))
    Comment Spark l'exécute

    Un groupBy est une transformation large (wide transformation) : agrégation partielle dans chaque partition (comme un combiner MapReduce), puis shuffle par clé, puis agrégation finale. Dans le plan : HashAggregate → Exchange → HashAggregate.

    Pièges
    • Arrondir avec F.round : les sommes de flottants laissent des restes.
    • Un pivot met NULL (pas 0) là où il n'y a aucune ligne.
    • count("*") compte les lignes ; count("col") ignore les NULL.

    Joindre : types, pièges, stratégies physiques

    TypeGarde…
    innerles lignes qui ont une correspondance des deux côtés

    Fenêtres : calculer sur les voisins sans perdre de lignes

    Analogie — le classement d'un championnat. Un groupBy donne « un total par équipe » (une ligne par groupe). Une fonction de fenêtre garde chaque match et ajoute « le rang de ce match dans la saison de l'équipe » : on regarde les lignes voisines sans les fusionner.

            .rowsBetween(Window.unboundedPreceding, Window.currentRow))

     .withColumn("precedent", F.lag("total").over(
                  Window.partitionBy("store").orderBy("date")))

    row_number sur des égalités sans critère de départage (ici order_id) : résultat non déterministe, il peut changer d'une exécution à l'autre.

    Questions d'oral — chapitre 03

    Le broadcast hash join copie la petite table sur chaque executor et construit une table de hachage en mémoire : la grosse table est jointe sur place, sans shuffle. Le sort merge join redistribue les deux tables par clé (deux Exchange), les trie puis les fusionne : adapté à deux grosses tables, mais coûteux en réseau.     ① Pourquoi ③ Comment

    De ton code au plan physique : Catalyst

    Tu écris quoi calculer ; l'optimiseur Catalyst décide comment. Savoir lire son plan, c'est savoir expliquer pourquoi un job est lent.

    1 · Plan logique non résoluton code, tel quel
    2 · Plan analysécolonnes et types vérifiés via le schéma (erreur si colonne inconnue)
    3 · Plan logique optimisérègles : filtres poussés, colonnes élaguées, constantes simplifiées
    4 · Plan physiquechoix concrets : type de jointure, Exchange, puis génération de code (Tungsten)
    python · lire un plan
    df.filter(F.col("store") == "Paris") \
  .groupBy("product").agg(F.sum("qty")).explain()
# == Physical Plan ==   (se lit de BAS en HAUT)
# HashAggregate(keys=[product], functions=[sum(qty)])
# +- Exchange hashpartitioning(product, 200)   ← SHUFFLE
#    +- HashAggregate(... partial_sum(qty))
#       +- FileScan parquet [store,product,qty]  ← column pruning
#          PushedFilters: [EqualTo(store,Paris)] ← predicate pushdown
    Column pruning (élagage de colonnes)

    Seules les colonnes utiles sont lues : la liste entre crochets du FileScan. Énorme gain avec un format colonnes (Parquet).

    Predicate pushdown (filtre poussé à la source)

    Le filtre est appliqué pendant la lecture (PushedFilters) : Parquet saute des blocs entiers grâce à ses statistiques min/max.

    Exchange = shuffle

    Compter les Exchange d'un plan, c'est compter les shuffles : le premier levier d'optimisation. Onglet SQL de l'UI Spark (port 4040) pour le plan visuel de chaque requête.

    Chapitre 04 · Performance
    ③ Comment — les leviers

    Partitions, AQE, cache, UDF, collect

    200 partitions de shuffle par défaut

    spark.sql.shuffle.partitions = 200 : pour 10 clés, 200 tâches presque vides. AQE (Adaptive Query Execution, actif par défaut) mesure les données réelles pendant l'exécution et regroupe les petites partitions (mesuré : 1 au lieu de 200). AQE peut aussi passer à un broadcast join et découper les partitions déséquilibrées (data skew).

    repartition vs coalesce

    repartition(n, col) : redistribue (shuffle complet), pour augmenter le parallélisme ou regrouper par clé avant écriture. coalesce(n) : fusionne des partitions sans shuffle, seulement pour en réduire le nombre (ex. éviter des milliers de petits fichiers en sortie).

    cache() / persist()

    Garde un résultat en mémoire après la première action. Utile seulement s'il est coûteux et relu plusieurs fois (ex. une table nettoyée utilisée par trois agrégations). Sinon il consomme la mémoire des executors pour rien. unpersist() quand c'est fini.

    UDF Python : à éviter

    Une UDF Python sort chaque ligne de la JVM vers un processus Python et l'y ramène (sérialisation), et Catalyst ne peut pas l'optimiser. Mesuré : 4,26 s contre 0,16 s avec la fonction native équivalente. Préférer pyspark.sql.functions ; sinon une pandas UDF (vectorisée avec Arrow).

    collect() et toPandas() rapatrient TOUT le résultat dans la mémoire du driver : sur un gros volume, le driver meurt (OutOfMemory). Toujours après une agrégation, un filtre ou un limit. Pour regarder : show(), take(n).

    Chapitre 05 · Streaming
    ① Pourquoi ② Quoi

    Un flux = une table qui ne finit jamais

    Analogie — le tapis roulant de l'aéroport. Les bagages (événements) arrivent sans fin. Toutes les quelques secondes, Spark prend ce qui est arrivé (un micro-batch), met à jour ses compteurs, et note sur un carnet (le checkpoint) jusqu'où il est allé. S'il s'arrête, il reprend à la bonne page du carnet.
    Le modèle de Structured Streaming

    Le flux est vu comme une table non bornée (unbounded table) à laquelle s'ajoutent des lignes. On écrit les mêmes transformations qu'en batch (filter, groupBy, join) ; Spark les exécute incrémentalement, micro-batch après micro-batch. Seuls changent readStream / writeStream.

    python · un flux de fichiers JSON
    evts = (spark.readStream
          .schema(schema)            # OBLIGATOIRE en streaming
          .json("entree/"))
q = (evts.groupBy("store").count()
         .writeStream
         .outputMode("update")
         .format("console")
         .option("checkpointLocation", "chk/q1")
         .trigger(processingTime="10 seconds")
         .start())
q.awaitTermination()
    Sources

    Fichiers (dossier surveillé), Kafka, socket (tests).

    Puits (sinks)

    Console (debug), fichiers Parquet, Kafka, foreachBatch (écrire chaque lot où l'on veut : base, Delta…).

    Latence

    Micro-batch : de l'ordre de la seconde. Pour la milliseconde, d'autres outils (Flink, Kafka Streams).

    Chapitre 05 · Streaming
    ③ Comment — le temps

    Event time, fenêtres, watermark

    Event time vs processing time

    L'event time est l'heure où l'événement s'est produit (dans la donnée) ; le processing time est l'heure où Spark le traite. Un capteur hors réseau peut envoyer à 10:05 une mesure de 09:58 : on agrège sur l'event time pour un résultat juste.

    Watermark

    Watermark = plus grand event time vu − délai toléré. Tout événement plus ancien que le watermark est considéré trop tard et ignoré ; une fenêtre qui se termine avant le watermark est close et son état peut être libéré. Sans watermark, Spark garderait l'état de toutes les fenêtres pour toujours (mémoire infinie).

    python · comptage par fenêtres d'1 minute, retard toléré 2 minutes
    (evts.withWatermark("ts", "2 minutes")
     .groupBy(F.window("ts", "1 minute"), "store")
     .count())
# plus grand ts vu : 10:05:30 → watermark = 10:03:30
# la fenêtre [10:02, 10:03[ est close ; un événement de 10:02:50 arrivant maintenant est ignoré
    Mode de sortieCe qui est émis à chaque micro-batchUsage
    append (défaut)seulement les lignes définitives ; pour une agrégation : une fenêtre une fois close par le watermarkécrire des fichiers (on ne réécrit pas une ligne déjà écrite)
    updateles lignes modifiées depuis le lot précédenttableaux de bord, bases avec upsert
    completetout le résultat, à chaque lotpetites agrégations (le résultat doit tenir en mémoire)
    Chapitre 05 · Streaming
    ③ Comment ④ Exemple — lire Kafka

    Checkpoint, Kafka et garanties de livraison

    Kafka en 5 idées (voir le cours Kafka)
    • Un topic = un flux nommé, découpé en partitions.
    • Chaque message a un offset (numéro) dans sa partition.
    • L'ordre n'est garanti qu'à l'intérieur d'une partition.
    • Les messages sont conservés (rétention) : on peut les relire.
    • Clé et valeur sont des octets : à décoder.
    Checkpoint

    Dossier où Spark enregistre les offsets déjà traités et l'état des agrégations. Au redémarrage, la requête reprend exactement là. Ne jamais le supprimer « pour rejouer » : on perd la mémoire de la requête. startingOffsets ne sert qu'à la toute première exécution ; ensuite, c'est le checkpoint qui décide.

    python · Kafka → JSON → Parquet
    # paquet requis : spark-sql-kafka-0-10 (même version que Spark)
raw = (spark.readStream.format("kafka")
   .option("kafka.bootstrap.servers", "localhost:9092")
   .option("subscribe", "ventes")
   .option("startingOffsets", "earliest")
   .load())
# colonnes : key, value (binaire), topic, partition, offset, timestamp
msg = raw.select(F.from_json(F.col("value").cast("string"), schema).alias("m"),
                 "partition", "offset")
ok     = msg.filter(F.col("m.order_id").isNotNull()).select("m.*")
rejets = msg.filter(F.col("m.order_id").isNull())   # garder partition + offset
(ok.writeStream.format("parquet")
   .option("path", "lake/ventes")
   .option("checkpointLocation", "chk/ventes")
   .start())

    Message illisible : from_json ne renvoie pas NULL mais une structure dont tous les champs sont NULL. On filtre donc sur un champ obligatoire et on garde partition + offset des rejets pour pouvoir les retrouver dans Kafka (dead letter queue).

    Garanties : avec une source rejouable (Kafka) + checkpoint + un puits idempotent (fichiers Parquet gérés par Spark), le résultat est exactly-once. L'écriture vers Kafka est at-least-once : des doublons sont possibles en cas de reprise, le consommateur doit savoir les éliminer.

    Chapitre 05 · Streaming
    ⑤ Pièges ⑥ Résumé

    À retenir sur le streaming

    Pas de schéma : readStream sur fichiers exige un schéma explicite.
    Agrégation sans watermark : l'état grossit indéfiniment, et le mode append est impossible.
    Supprimer le checkpoint pour « rejouer » : la requête oublie où elle en était (doublons ou trous).
    200 partitions de shuffle à chaque micro-batch : très lent en local → réduire shuffle.partitions.
    Supposer l'ordre global d'un topic Kafka : seulement par partition.
    1. Flux = table non bornée ; mêmes DataFrames, readStream/writeStream, micro-batchs.
    2. Agréger sur l'event time ; watermark = max(event time) − délai : ferme les fenêtres, borne l'état.
    3. Modes : append (définitif), update (changements), complete (tout).
    4. Checkpoint = offsets + état ; ne pas le supprimer ; startingOffsets seulement au 1er lancement.
    5. Kafka : décoder value + from_json, isoler les rejets ; exactly-once vers fichiers, at-least-once vers Kafka.

    Ce que le jury peut demander

    Questions d'oral — chapitre 05

    C'est un seuil de temps calculé comme le plus grand event time observé moins un délai toléré. Il dit à Spark jusqu'où attendre les retardataires : les événements plus anciens sont ignorés, et les fenêtres qui se terminent avant le watermark sont closes. Il borne donc la mémoire de l'état et permet le mode append. C'est un compromis explicite entre exactitude (attendre longtemps) et latence/ressources.

    Source rejouable (Kafka, qui conserve les messages), checkpoint qui mémorise les offsets traités et l'état, et puits idempotent ou transactionnel (Parquet géré par Spark, Delta, upsert sur clé). On obtient l'exactly-once de bout en bout. Vers Kafka, Spark garantit l'at-least-once : on prévoit une déduplication côté consommateur (clé unique).

    Selon la fraîcheur exigée par le métier (vélocité). Un rapport quotidien → batch, plus simple et moins coûteux. Une alerte de fraude, un suivi de stock en direct → streaming. Avec Spark, le code de transformation est le même : on peut commencer en batch et passer en streaming sans tout réécrire.

    Je ne les jette pas : from_json produit une structure de NULL, je les filtre sur un champ obligatoire et je les écris dans une file de rejets (dead letter queue) avec leur partition et leur offset, pour analyse et rejeu. Le volume de rejets devient un indicateur de qualité.

    Chapitre 06 · Synthèse
    Questions transversales

    Ce que le jury peut demander sur l'ensemble

    Structure attendue : besoin (volume, fréquence, utilisateurs) → lecture avec schéma explicite → qualité (NULL, doublons, rejets en quarantaine, comptages de contrôle) → transformations (jointures en broadcast quand possible, agrégations, fenêtres) → écriture Parquet partitionnée → orchestration (Airflow) et supervision (UI Spark, durée, taux de rejet). Chaque choix est justifié par une mesure ou une contrainte.

    Organisation d'un data lake en trois couches : bronze (brut, immuable, rejouable), silver (nettoyé, typé, dédoublonné, conforme), gold (agrégats métier prêts pour la BI et le ML). Avantages : traçabilité, possibilité de recalculer une couche depuis la précédente, séparation des responsabilités. Spark réalise chaque passage.

    Ne pas utiliser Spark si pandas suffit ; lire moins (Parquet, column pruning, predicate pushdown, partition pruning) ; éviter les shuffles inutiles (broadcast, filtrer tôt) ; ne cacher que ce qui est relu ; dimensionner le cluster sur la mesure ; traiter de façon incrémentale (streaming ou partitions nouvelles) plutôt que tout recalculer.

    Le driver exécute le programme et planifie ; les executors sont des JVM qui exécutent les calculs. Une action déclenche un ou plusieurs jobs ; un job est découpé en stages aux frontières de shuffle ; un stage contient une task par partition, exécutée sur un cœur.
