Immersion · 1 / 3

Comment une équipe construit-elle une API Java de qualité industrielle en quelques heures, sans écrire la plomberie (serveur, configuration, connexions) à chaque projet ?

Tout assembler à la main

Serveur d'applications à installer, fichiers XML de configuration, objets créés et reliés manuellement : lent, répétitif et difficile à tester.

Laisser un framework assembler l'application

On déclare les composants ; Spring les crée, les relie (injection de dépendances) et gère leur cycle de vie. Spring Boot ajoute un serveur embarqué et une configuration automatique.

Spring est un conteneur d'inversion de contrôle : ce n'est plus votre code qui crée ses collaborateurs, c'est le framework qui les fournit. Cela rend le code modulaire et testable. Spring Boot démarre un projet complet (serveur Tomcat embarqué, configuration, métriques) avec un minimum de réglages ; le tout se package en un seul JAR exécutable.

Analogie — un chef de chantier : vous dites ce qu'il faut (les composants), il fait arriver chaque corps de métier au bon moment et les met en relation ; vous ne tirez plus les fils vous-même.

Premier contact : une API en moins de vingt lignes

java · Spring Boot
@SpringBootApplication
public class App {
    public static void main(String[] args) { SpringApplication.run(App.class, args); }
}

@RestController
@RequestMapping("/api/clients")
class ClientController {
    private final ClientService service;                  // injecté par Spring
    ClientController(ClientService service) { this.service = service; }

    @GetMapping("/{id}")
    ClientDto lire(@PathVariable Long id) { return service.trouver(id); }
}
// mvn spring-boot:run  ->  GET http://localhost:8080/api/clients/7  ->  {"id":7,"nom":"Durand"}
Ce qu'il faut remarquer

Aucun serveur à installer : Tomcat est embarqué. @SpringBootApplication active l'auto-configuration. Le service est injecté par le constructeur : Spring le crée et le fournit. La sortie en JSON est automatique.

Le fil du cours · Spring & Spring Boot

5 idées font tout le cours

Tout le cours répond à : comment construire une application Java d'entreprise dont les morceaux se branchent, se configurent et se testent sans tout réécrire ? Cinq règles expliquent Spring.

Idée 1 · Le conteneur crée et relie les objets

Inversion de contrôle : on ne crée pas soi-même les objets avec new. On déclare des beans (@Component, @Service, @Repository) ; Spring les crée et leur injecte leurs dépendances, de préférence par le constructeur.

L'erreur typique : Si un service crée lui-même ses dépendances avec new, on ne peut pas les remplacer par un double dans les tests.

La bonne pratique : Recevoir les dépendances par le constructeur : dans un test, on passe un double à la place de la vraie dépendance.

ch. 01 · ch. 02

Idée 2 · Dépendre d'interfaces, pas d'implémentations

Une classe reçoit une interface ; on change l'implémentation (base réelle, double de test, profil) sans toucher au code qui l'utilise.

L'erreur typique : Si une classe dépend directement d'une classe concrète, changer d'implémentation oblige à modifier tout le code qui l'utilise.

La bonne pratique : Faire dépendre la classe d'une interface (ClientRepository) ; Spring injecte l'implémentation choisie selon le contexte ou le profil.

ch. 01 · ch. 04

Idée 3 · Convention plutôt que configuration

Convention plutôt que configuration. Avec Spring Boot, les starters apportent les bonnes dépendances, l'auto-configuration règle ce qui est présent, et la configuration est externe au code (application.yml, profils, variables d'environnement) : on l'adapte sans recompiler.

L'erreur typique : Si le mot de passe de la base est écrit dans le code, il se retrouve dans Git, et il faut recompiler l'application pour le changer.

La bonne pratique : Lire le mot de passe dans une variable d'environnement, référencée dans application.yml : ${DB_PASSWORD}.

ch. 02

Idée 4 · Des couches séparées

On sépare l'application en couches : le contrôleur (HTTP), le service (règles métier, transactions), le repository (accès aux données). Les DTO (objets de transfert) séparent ce que montre l'API des entités de la base ; la validation et les erreurs sont gérées en un seul endroit.

L'erreur typique : Si l'API renvoie directement l'entité JPA, la conversion en JSON peut tourner en boucle entre les relations, et des champs internes sont exposés.

La bonne pratique : Renvoyer un DTO qui ne contient que les champs utiles, construit à partir de l'entité.

ch. 03 · ch. 04

Idée 5 · Les données derrière des repositories et des transactions

Spring Data JPA écrit les requêtes à partir des noms de méthodes (findByEmail). @Transactional rend une opération atomique : tout réussit ou tout est annulé. Attention au chargement paresseux des relations et au problème N+1 (une requête de plus par élément d'une liste).

L'erreur typique : Si l'on parcourt une liste et que chaque élément charge sa relation séparément, on déclenche une requête par ligne (le problème N+1).

La bonne pratique : Charger la relation en une seule requête (JOIN FETCH ou @EntityGraph) et compter les requêtes dans les journaux.

Chapitre 01 · Inversion de contrôle et injection de dépendances
① Pourquoi ② Quoi

Le conteneur Spring et les beans

Pourquoi

Sans framework, une classe crée ses collaborateurs (new ServiceMail()) : elle y est couplée, impossible à tester isolément. Avec l'inversion de contrôle (IoC), elle déclare ce dont elle a besoin et reçoit des instances : c'est l'injection de dépendances (DI).

Vocabulaire
  • Bean : objet créé et géré par le conteneur.
  • ApplicationContext : le conteneur ; il crée, relie et détruit les beans.
  • Scope : singleton (par défaut, une instance), prototype (une par demande), request, session.
  • Profil : jeu de beans actif selon l'environnement (dev, prod).
AnnotationRôle
@Componentbean générique détecté par scan
@Servicebean de la couche métier
@Repositoryaccès aux données (traduit les exceptions)
@Controller / @RestControllercouche web
@Configuration + @Beandéclarer un bean par une méthode
@Autowired / constructeurinjecter une dépendance
Analogie — un restaurant : la cuisine ne choisit pas ses fournisseurs ni ses équipements ; la direction (le conteneur) les fournit selon le contrat.
Chapitre 01 · Inversion de contrôle et injection de dépendances
③ Comment ④ Exemple

Injection par constructeur, interfaces, profils

java
public interface Notifier { void envoyer(String msg); }

@Service @Profile("prod")
class MailNotifier implements Notifier { public void envoyer(String m) { /* SMTP */ } }

@Service @Profile("dev")
class LogNotifier implements Notifier { public void envoyer(String m) { System.out.println(m); } }

@Service
class CommandeService {
    private final Notifier notifier;                    // dépend d'une INTERFACE
    CommandeService(Notifier notifier) { this.notifier = notifier; }   // injection par constructeur
}

Une seule implémentation active selon le profil : le code métier ne change pas.

Trois formes d'injection
  • Par constructeur (recommandée) : dépendances obligatoires, objet immuable (final), testable sans Spring.
  • Par setter : dépendances optionnelles.
  • Par champ (@Autowired sur l'attribut) : à éviter, difficile à tester.
Choisir parmi plusieurs candidats

@Primary (candidat par défaut), @Qualifier("nom") (désigner), profils. Programmer vers une interface (principe d'inversion des dépendances) rend les implémentations interchangeables.

Le fait que ce ne soit plus la classe qui crée et configure ses collaborateurs, mais un conteneur qui les lui fournit. La classe déclare ce dont elle a besoin, ce qui réduit le couplage et facilite les tests.

① Pourquoi ② Quoi

Starters, auto-configuration, JAR exécutable

Ce que Boot apporte
  • Starters : un ajout au pom.xml apporte un ensemble cohérent (spring-boot-starter-web, -data-jpa, -security, -test).
  • Auto-configuration : Boot configure ce qu'il détecte sur le classpath (une base H2 présente → source de données).
  • Serveur embarqué (Tomcat) : on lance un JAR exécutable (java -jar app.jar).
  • Convention plutôt que configuration.
Créer un projet

Spring Initializr (start.spring.io) : on choisit Maven ou Gradle, la version de Java (17 ou plus pour Boot 3), les dépendances ; on obtient un squelette prêt à lancer.

xml · pom.xml (extrait)
<parent>
  <groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-parent</artifactId>
  <version>3.3.0</version>
</parent>
<dependencies>
  <dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-web</artifactId></dependency>
  <dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-data-jpa</artifactId></dependency>
</dependencies>

@SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan : tout ce qui est dans son paquet et ses sous-paquets est détecté.

application.yml et profils

La configuration vit hors du code, dans application.yml (ou .properties), avec un fichier par profil (application-prod.yml) et des variables d'environnement qui priment. Jamais de secret dans le dépôt (gestion des secrets).

Livrer

Chapitre 03 · API REST avec Spring MVC
① Pourquoi ② Quoi

Contrôleurs, DTO, validation

Un contrôleur REST
  • @RestController : retourne des objets sérialisés en JSON (Jackson).
  • @RequestMapping("/api/clients") + @GetMapping, @PostMapping, @PutMapping, @DeleteMapping.
  • @PathVariable (chemin), @RequestParam (requête), @RequestBody (corps JSON).
  • ResponseEntity ou @ResponseStatus pour fixer le code HTTP (201, 204…).
DTO plutôt qu'entité

On n'expose pas l'entité JPA : on retourne un DTO (Data Transfer Object). Cela évite les fuites (mot de passe), les boucles JSON et le couplage avec la base. Des records Java suffisent : record ClientDto(Long id, String nom) {}.

java
record ClientCreate(@NotBlank @Size(max = 60) String nom,
                    @Email String email, @Min(18) int age) {}

@PostMapping
ResponseEntity<ClientDto> creer(@Valid @RequestBody ClientCreate dto) {
    ClientDto cree = service.creer(dto);
    return ResponseEntity.created(URI.create("/api/clients/" + cree.id())).body(cree);   // 201 + Location
}

@Valid déclenche la Bean Validation (@NotBlank, @Email, @Min…) ; une donnée invalide lève une exception traduite en 400. Principes REST et codes de retour : API Python.

Chapitre 03 · API REST avec Spring MVC
③ Comment ④ Exemple

Gestion des erreurs et pagination

Centraliser les erreurs

Un @RestControllerAdvice capture les exceptions et produit une réponse d'erreur uniforme (format RFC 9457 « Problem Details » supporté par Spring). Le détail technique va dans les journaux, pas dans la réponse.

java
@RestControllerAdvice
class ErreursApi {
    @ExceptionHandler(ClientIntrouvable.class)
    ResponseEntity<ProblemDetail> introuvable(ClientIntrouvable e) {
        return ResponseEntity.status(404).body(ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage()));
    }
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ResponseEntity<ProblemDetail> invalide(MethodArgumentNotValidException e) { /* 400 + champs en erreur */ return null; }
}
Autres éléments utiles
  • Pagination : Pageable en paramètre, Page<T> en retour (?page=0&size=20&sort=nom).
  • CORS : autoriser explicitement les origines du front.
  • Documentation : springdoc-openapi génère Swagger UI à partir des contrôleurs.
  • Versionnement d'API (/api/v1).
Sécurité

Spring Security : chaîne de filtres ; authentification par session ou JWT/OAuth 2.0 (Resource Server), autorisation par rôles (@PreAuthorize). Concepts : Authentification ; codage sûr : Applications.

Ce que le jury peut demander

Questions d'oral — chapitre 03

Pour ne pas exposer l'entité de persistance : on contrôle les champs envoyés, on évite les fuites de données et les boucles de sérialisation, et on découple l'API du schéma de la base.

Chapitre 04 · Spring Data JPA, transactions et tests
① Pourquoi ② Quoi

Entités, repositories et requêtes

JPA et Spring Data

JPA est la spécification Java de correspondance objet-relationnel (ORM) ; Hibernate en est l'implémentation. Spring Data JPA génère les repositories à partir d'une interface.

java
@Entity
class Client {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) Long id;
    @Column(nullable = false) String nom;
    String ville;
    @OneToMany(mappedBy = "client") List<Commande> commandes;     // relation 1-N
}

interface ClientRepository extends JpaRepository<Client, Long> {
    List<Client> findByVille(String ville);                       // requête dérivée du nom
    @Query("select c from Client c where c.nom like %:n%")
    List<Client> chercher(@Param("n") String n);
}
Ce que génère Spring Data
  • save, findById, findAll(Pageable), deleteById, count sans écrire de code.
  • Requêtes dérivées : findByVilleAndAgeGreaterThan.
  • JPQL via @Query ; requêtes natives si besoin.
  • Migrations de schéma : Flyway ou Liquibase (pas ddl-auto en production).
Relations et chargement

@OneToMany, @ManyToOne, @ManyToMany ; chargement paresseux (LAZY) par défaut pour les collections. Le problème N+1 (une requête par élément) se règle par join fetch ou un @EntityGraph.

Chapitre 04 · Spring Data JPA, transactions et tests
③ Comment ④ Exemple

Transactions et tests

@Transactional

Une transaction regroupe des opérations qui réussissent toutes ou aucune (propriétés ACID, voir SQL). @Transactional sur une méthode de service ouvre la transaction, la valide à la sortie normale et la annule (rollback) sur une exception non contrôlée.

Une méthode transactionnelle appelée depuis la même classe (this.maMethode()) n'est pas interceptée : l'annotation est ignorée. Elle s'applique via un proxy Spring.

Tester une application Spring
  • Unitaire : JUnit 5 + Mockito (@Mock, @InjectMocks), sans Spring : rapide.
  • Tranche web : @WebMvcTest + MockMvc : on teste le contrôleur seul.
  • Tranche données : @DataJpaTest avec une base H2 ou Testcontainers.
  • Intégration : @SpringBootTest : tout le contexte, plus lent.
java
@WebMvcTest(ClientController.class)
class ClientControllerTest {
    @Autowired MockMvc mvc;
    @MockBean ClientService service;

    @Test void lire_retourne_200() throws Exception {
        given(service.trouver(7L)).willReturn(new ClientDto(7L, "Durand"));
        mvc.perform(get("/api/clients/7"))
           .andExpect(status().isOk())
           .andExpect(jsonPath("$.nom").value("Durand"));
    }

Questions d'oral — chapitre 04

Une couche qui génère les repositories à partir d'interfaces : on obtient CRUD, pagination et requêtes dérivées du nom des méthodes sans écrire d'implémentation, au-dessus de JPA et d'Hibernate.

Charger une liste d'entités puis déclencher une requête supplémentaire par élément pour sa relation paresseuse. On le résout par un join fetch, un EntityGraph ou une requête adaptée.

Sur les méthodes de la couche service, qui représentent une unité de travail métier : la transaction est ouverte au début, validée en cas de succès et annulée sur exception.

Avec @WebMvcTest et MockMvc : on charge seulement la couche web, on remplace le service par un mock, et on vérifie le statut et le corps JSON des réponses.

Parce que les migrations versionnées rendent le schéma reproductible, relu et déployable de façon contrôlée, alors que la génération automatique peut modifier ou détruire le schéma de production.
