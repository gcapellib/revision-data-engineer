Immersion · 1 / 3

Comment stocker un catalogue où chaque produit a des caractéristiques différentes, sans des centaines de colonnes vides ?

En relationnel

Un téléviseur a une diagonale, un t-shirt une taille, un livre un ISBN. Soit une table de 300 colonnes presque toutes à NULL, soit une dizaine de tables et de jointures pour afficher une seule fiche produit.

En documentaire

Chaque produit est un document qui porte exactement ses champs, avec ses avis et ses variantes imbriqués : une fiche = une lecture, sans jointure.

MongoDB est une base de données NoSQL orientée documents : elle stocke des documents au format BSON (JSON binaire typé), regroupés en collections, avec un schéma souple, de la réplication et du sharding natifs.

Analogie — le dossier patient. Plutôt que de répartir la vie d'un patient dans dix registres (identité, consultations, ordonnances), on range tout ce qu'on consulte ensemble dans une même pochette. Chaque pochette peut contenir des pièces différentes.
D'où le nom ?

De l'anglais humongous, « gigantesque » : une base pensée pour de très gros volumes.

Immersion · Essentiel

Présenter MongoDB en une minute

« MongoDB est une base NoSQL orientée documents, publiée en 2009. Elle stocke des documents BSON — du JSON binaire typé — regroupés en collections, avec un schéma souple : deux documents d'une même collection peuvent avoir des champs différents.

On modélise selon les requêtes : ce qui est lu ensemble est imbriqué dans le même document, ce qui est partagé ou non borné est référencé. L'écriture sur un document est atomique ; les transactions multi-documents existent depuis la version 4.0. Elle passe à l'échelle avec les replica sets pour la haute disponibilité et le sharding pour la répartition.

Je la choisis pour des données variées lues par objet entier, comme un catalogue. Pour des données très liées avec des contraintes d'intégrité fortes, je garde une base relationnelle. »

Les 3 mots à placer

Document BSON · imbriquer/référencer · schéma souple

Le choix à justifier

MongoDB plutôt qu'une base relationnelle quand les données se lisent par document entier et que leur forme varie ; pas pour des transactions entre de nombreuses tables.

5 idées font tout le cours

Tout le cours répond à : comment stocker des données à structure variable pour les lire d'un seul coup, sans perdre la fiabilité ? Cinq idées guident chaque choix de modélisation et de code.

Idée 1 · Modéliser selon les lectures

En relationnel, on modélise les données puis on les assemble à la lecture. En base documentaire, on modélise l'usage : ce qui se lit ensemble se stocke ensemble. Une commande et ses lignes forment un seul document.

L'erreur typique : Si l'on recopie un schéma relationnel en collections, chaque lecture doit reconstituer les données avec des $lookup, et l'on perd l'intérêt du modèle documentaire.

La bonne pratique : Lister les écrans et requêtes à servir, et construire un document par lecture principale (la commande avec ses lignes).

ch. 01 · ch. 03

Idée 2 · Imbriquer ou référencer

On imbrique dans le document ce qui lui appartient, reste de taille limitée et se lit avec lui (les lignes d'une commande). On référence par un identifiant ce qui est partagé, volumineux ou qui grossit sans fin (le client, les mesures d'un capteur). Un document ne peut pas dépasser 16 Mo.

L'erreur typique : Si l'on imbrique une liste qui grossit sans limite (toutes les mesures d'un capteur), le document s'alourdit jusqu'à dépasser la limite de 16 Mo.

La bonne pratique : Mettre les mesures d'un capteur dans une collection à part, chaque mesure portant l'identifiant du capteur.

ch. 03 · ch. 04

Idée 3 · Schéma souple ne veut pas dire sans schéma

Sans schéma imposé par la base, c'est l'application qui garantit la forme des données : types précis (Decimal128 pour l'argent, vraies dates), différence entre null (valeur vide) et champ absent, validation par JSON Schema, et un champ schema_version pour faire évoluer les documents.

L'erreur typique : Si l'on stocke un prix en nombre décimal ordinaire (double), les centimes s'arrondissent mal ; et si l'on confond null et champ absent, des requêtes ratent des documents.

La bonne pratique : Stocker les prix en Decimal128, poser une validation JSON Schema sur la collection et toujours écrire les mêmes champs.

ch. 01 · ch. 02 · ch. 03

Idée 4 · Écrire de façon idempotente

Un import doit pouvoir être relancé sans doublon. On utilise l'upsert (mettre à jour si le document existe, sinon le créer) sur une clé métier, un index unique sur cette clé, et des mises à jour ciblées ($set, $inc) plutôt que le remplacement du document entier.

L'erreur typique : Si l'import du lendemain insère une seconde fois les mêmes documents, la collection se remplit de doublons.

La bonne pratique : Importer avec updateOne(..., upsert: true) sur la clé métier, et poser un index unique sur cette clé.

ch. 02

Idée 5 · Sans index, tout est un scan

Sans index, une requête lit toute la collection (COLLSCAN). Un index sur plusieurs champs suit la règle ESR : d'abord les champs testés par égalité, puis ceux du tri, puis les intervalles. Dans une agrégation, on filtre ($match) le plus tôt possible.

L'erreur typique : Si l'on filtre sur un champ sans index, MongoDB lit chaque document de la collection, ce qui devient très lent sur des millions de documents.

La bonne pratique : Créer un index sur le champ filtré, puis vérifier avec explain() que la requête passe en IXSCAN (lecture d'index).

Chapitre 01 · Le modèle documentaire
③ Comment ⑤ Pièges

Quatre spécificités, trois pièges de typage

Les 4 spécificités du documentaire
  1. Deux documents d'une même collection peuvent avoir des champs différents.
  2. Le schéma n'a pas disparu : il est dans le code qui lit et écrit.
  3. On modélise les requêtes (les écrans), pas les entités ; dupliquer est un choix assumé.
  4. Pas d'intégrité référentielle ni de jointure gratuite ; le document est l'unité d'atomicité.
BSON (Binary JSON)

Ce que MongoDB stocke réellement : du JSON binaire et typé (int32, int64, double, Decimal128, Date, ObjectId…). Limite : 16 Mo par document.

1 · null n'est pas « absent ». {remise: null} et {} sont différents, mais la requête {remise: null} renvoie les deux. Pour distinguer : {remise: {$exists: false}} ou {$type: "null"}.
2 · Jamais d'argent en float/double. 0.1 + 0.2 ≠ 0.3 : utiliser Decimal128 ou des centimes en entier.
3 · Les dates sont en UTC. Passer des datetime avec fuseau (datetime.now(timezone.utc)) et ouvrir le client avec tz_aware=True.
Cohérence : CAP

En cas de partition réseau, un système distribué choisit entre cohérence et disponibilité. MongoDB est CP par défaut : si le primaire est isolé, il refuse d'écrire le temps d'élire un remplaçant. Réglable par opération (writeConcern, readConcern, readPreference). Cassandra penche AP.

Quand NE PAS choisir le documentaire

Données très normalisées et reliées (comptabilité, ERP), requêtes imprévisibles et analytiques, besoin de nombreuses transactions multi-entités : rester en relationnel.

Chapitre 01 · Le modèle documentaire

Fiche — Le documentaire

Vocabulaire

Base → collection → document (BSON) → champ. _id = clé (ObjectId). Pas de FK, pas de JOIN gratuit : on imbrique.

Principes
  • Documents d'une collection hétérogènes.
  • Schéma dans le code.
  • Modéliser les requêtes ; dupliquer est assumé.
  • Document = unité d'atomicité ; 16 Mo max.
Pièges de typage

{x: null} matche null et absent → $exists. Argent : Decimal128. Dates : UTC, tz_aware=True.

CAP et choix

MongoDB CP par défaut, réglable (writeConcern…). Relationnel si données très reliées, analytique imprévisible, ERP.

Chapitre 01 · Le modèle documentaire
Ce que le jury peut demander

Questions d'oral — chapitre 01

Quand les données sont variées et évolutives (catalogue de produits aux attributs différents), que l'on connaît les écrans à servir et qu'on veut les lire en une requête sans jointure, et qu'il faut passer à l'échelle horizontalement (sharding). On renonce en échange aux clés étrangères et aux jointures : la cohérence entre collections devient la responsabilité de l'application.

La base n'impose pas de structure : c'est le code qui décide des champs, de leurs types et de leurs valeurs par défaut. Le risque : des documents incohérents (types mélangés, champs absents) ignorés silencieusement par les requêtes. On le maîtrise par des audits, une validation JSON Schema sur le noyau commun et un champ schema_version.

En cas de partition réseau (inévitable), un système distribué doit choisir entre la cohérence (tous voient la même donnée, quitte à refuser des écritures) et la disponibilité (toujours répondre, quitte à diverger). MongoDB est CP par défaut, avec des réglages par opération ; Cassandra est AP.

Un client par processus

MongoClient gère un pool de connexions : on le crée une fois au démarrage, on le partage, on le ferme à l'arrêt. Sa construction est non bloquante : un serveur éteint ne se voit qu'à la première requête, d'où le ping explicite.

Filtres = objets

$eq $ne $gt $gte $lt $lte $in $nin $exists $type $regex ; notation pointée pour les sous-documents ("client.nom") ; une valeur cherchée dans un tableau matche si un élément correspond.

find renvoie un curseur

Paresseux et parcourable une seule fois. Pagination : éviter skip (lit tout ce qui est sauté), préférer {"_id": {"$gt": dernier_id}}.

Modifier, supprimer, importer de façon idempotente

python · mises à jour et import réexécutable
r = db.produits.update_one({"sku": "BAG-01"},

r.matched_count, r.modified_count   # existe ? a changé ?

db.produits.find_one_and_update(
    {"sku": "BAG-01", "stock": {"$gte": 2}},
    {"$inc": {"stock": -2}})

# import idempotent : upsert sur la clé d'identité
from pymongo import UpdateOne
ops = [UpdateOne({"sku": r["sku"]},
                 {"$set": {"prix": r["prix"]},
                  "$setOnInsert": {"cree_le": maintenant}},
                 upsert=True) for r in lignes]
db.produits.bulk_write(ops, ordered=False)   # par tranches de ~1 000
Oublier l'opérateur : update_one(f, {"nom": "x"}) → WriteError. Pour remplacer tout le document : replace_one (qui supprime les champs non fournis).
matched ≠ modified : 1 trouvé, 0 modifié si la valeur était déjà la bonne.
$set, $inc, $push créent les champs absents (c'est ainsi que le schéma évolue).
delete_many({}) vide la collection sans confirmation : compter d'abord avec le même filtre.
Supprimer en production

Suppression logique (soft delete) : {"$set": {"supprime_le": maintenant}}, puis purge automatique par un index TTL (expireAfterSeconds). Erreur E11000 = violation d'index unique (DuplicateKeyError) : on tente l'insertion et on l'attrape, plutôt que de tester l'existence avant.

  1. Un MongoClient par processus, ping au démarrage, URI dans .env.
  2. CRUD : insert_one/many, find/find_one (curseur, ObjectId), update_one/many avec opérateurs, delete_one/many.
  3. Idempotence : bulk_write + UpdateOne(upsert=True) + $setOnInsert.
  4. Atomicité sans transaction : condition métier dans le filtre de find_one_and_update.

Chapitre 02 · CRUD
Ce que le jury peut demander

Questions d'oral — chapitre 02

Avec un upsert sur la clé d'identité métier (un index unique sur sku), regroupé dans un bulk_write : UpdateOne({"sku": …}, {"$set": champs, "$setOnInsert": champs_de_creation}, upsert=True). Relancer l'import met à jour les documents existants et n'en crée pas de nouveaux : il est idempotent.

En mettant la condition métier dans le filtre d'une seule opération atomique : find_one_and_update({"sku": s, "stock": {"$gte": q}}, {"$inc": {"stock": -q}}). Si le stock est insuffisant, rien n'est trouvé ni modifié. Le document étant l'unité d'atomicité, pas besoin de transaction.

Pour garder une trace (audit, restauration, RGPD avec délai), on marque le document (supprime_le) : c'est la suppression logique. Un index TTL purge ensuite automatiquement les documents après le délai voulu.

Chapitre 03 · Modéliser
① Pourquoi ③ Comment

Imbriquer ou référencer : la seule vraie question

Imbriquer (embedding)

Le sous-objet vit dans le document parent (les lignes dans la commande). Une seule lecture, mise à jour atomique. Pour ce qui est lu ensemble, possédé par le parent et borné en taille.

Référencer

On stocke l'_id d'un document d'une autre collection (le client d'une commande). Pour ce qui est partagé entre plusieurs parents, volumineux, non borné ou mis à jour indépendamment.

Question qui décidePlutôt imbriquer si…Plutôt référencer si…
Lu ensemble ?affiché sur le même écranlu séparément
Cardinalité ?1-1, 1-quelques1-beaucoup, 1-« des milliers », n-n
Croissance ?bornéenon bornée (limite 16 Mo par document)
Partagé ?propre au parentutilisé par plusieurs parents
Mises à jour ?rares, avec le parentfréquentes, indépendantes

Dupliquer, c'est normal — à condition de désigner une source de vérité et un processus de propagation. Distinguer le cache (le nom du client dans la commande : à propager s'il change) de l'instantané (le prix au moment de la commande : à figer, jamais propager).

$lookup systématique = modèle relationnel déguisé : on paie les jointures sans les garanties (FK, transactions) du relationnel.

Pourquoi les documents diffèrent

Trois raisons saines (familles métier, évolution du schéma, champ optionnel) et une subie (incohérence à corriger : "prix": "12.5" en texte).

Le bug le plus coûteux

Un champ stocké dans un mauvais type est ignoré silencieusement par les filtres ({prix: {$lt: 20}} ne voit pas le texte). On le débusque avec $type, on audite avec $objectToArray + $group.

Garde-fous

Validation JSON Schema sur le noyau commun (additionalProperties: true), déployée en moderate/warn puis durcie en strict/error. Le code lit toutes les versions, n'écrit que la dernière.

  1. Imbriquer ce qui est lu ensemble et borné ; référencer ce qui est partagé ou non borné.
  2. Dupliquer avec une source de vérité ; cache (propager) vs instantané (figer).
  3. Patterns : extended reference, subset, computed, bucket, outlier, attribute, versioning.
  4. Auditer les types, valider le noyau commun, versionner le schéma.
Chapitre 03 · Modéliser
⑤ Pièges

Les pièges de la modélisation documentaire

Le tableau qui grossit sans limite : imbriquer tous les commentaires ou tous les événements dans un document le rapproche de la limite de 16 Mo et alourdit chaque lecture et chaque index : référencer ou utiliser le pattern bucket.
Imbriquer une donnée partagée et changeante : copier l'adresse d'un fournisseur dans 10 000 produits oblige à 10 000 mises à jour quand elle change : on référence ce qui est partagé et modifié.
Recopier le modèle relationnel : une collection par table et des $lookup partout : on paie MongoDB sans profiter du document, qui se modélise d'après les requêtes.
« Sans schéma » donc sans règles : le schéma est souple, pas absent : un validateur $jsonSchema sur la collection refuse les documents mal formés.
Dupliquer sans plan de mise à jour : toute donnée dupliquée (pattern extended reference) doit avoir une règle claire de mise à jour, sinon les copies divergent.
Chapitre 03 · Modéliser

Fiche — Modélisation documentaire

Imbriquer / référencer

Imbriquer : lu ensemble, possédé, borné (16 Mo). Référencer : partagé, non borné, mis à jour à part. $lookup systématique = relationnel déguisé.

Duplication

Normale avec une source de vérité. Cache (nom du client) : propager. Instantané (prix à la commande) : figer.

Patterns

Extended Reference · Subset · Computed · Bucket · Outlier · Attribute · Schema Versioning.

Schéma souple maîtrisé

Mauvais type = ignoré en silence → $type. Audit par agrégation. JSON Schema sur le noyau commun (moderate puis strict). schema_version.

Chapitre 03 · Modéliser
Ce que le jury peut demander

Questions d'oral — chapitre 03

Je pars des requêtes : ce qui est affiché ensemble et appartient au parent, en quantité bornée, est imbriqué (les lignes d'une commande). Ce qui est partagé entre documents, volumineux, non borné ou mis à jour indépendamment est référencé (le client, les avis par milliers). Je vérifie la limite de 16 Mo et les cardinalités.

En documentaire, c'est un choix assumé pour lire sans jointure, à condition d'identifier une source de vérité et un mécanisme de propagation. Je distingue le cache (à mettre à jour quand la source change) de l'instantané historique (le prix payé, qui ne doit jamais changer).

Audit régulier des champs et de leurs types par agrégation, validation JSON Schema sur les champs obligatoires communs, convention « un champ sans valeur n'est pas écrit » (plutôt que null), champ schema_version et migrations progressives. Le schéma est dans le code : il doit être testé comme du code.

Index : COLLSCAN, IXSCAN et la règle ESR

python · index et mesure
db.produits.create_index([("categorie", 1),   # E · égalité
                          ("stock", -1),      # S · tri
                          ("prix", 1)])      # R · plage
db.produits.create_index("sku", unique=True)
db.produits.create_index("supprime_le", expireAfterSeconds=30*86400) # TTL

plan = db.produits.find({"categorie": "pain", "prix": {"$lt": 3}}) \
                  .sort("stock", -1).explain()
# winningPlan : IXSCAN (index) plutôt que COLLSCAN (tout lire)
# executionStats : totalDocsExamined ≈ nReturned  → ratio proche de 1:1
ESR : Equality, Sort, Range

Dans un index composé, placer d'abord les champs testés en égalité, puis ceux du tri, puis ceux en plage ($lt, $gt). C'est l'ordre des champs qui fait la performance.

Règle du préfixe

L'index {a, b, c} sert les requêtes sur {a} et {a, b}, jamais sur {b} seul.

Index utiles

Unique (identité métier) · partiel (sur une collection hétérogène, ou un unique sur un champ optionnel) · TTL (purge automatique) · requête couverte (tout est dans l'index, aucun document lu).

Perdre son index : $regex non ancré (/pain/ au lieu de /^pain/), tri de directions mixtes non prévu par l'index, tri en mémoire (100 Mo maximum ; au-delà, échec ou débordement sur disque, permis par défaut depuis MongoDB 6.0). Et chaque index coûte à l'écriture : supprimer ceux que $indexStats montre inutilisés.

Pipeline d'agrégation et mise en production

python · chiffre d'affaires par catégorie en 2026
pipeline = [
  {"$match":  {"date": {"$gte": debut_2026}}},          # WHERE (tôt !)
  {"$unwind": "$lignes"},                                # 1 doc par ligne
  {"$group":  {"_id": "$lignes.categorie",               # GROUP BY
               "ca": {"$sum": {"$multiply": ["$lignes.qte", "$lignes.prix"]}}}},
  {"$sort":   {"ca": -1}},                                  # ORDER BY
  {"$project": {"categorie": "$_id", "ca": 1, "_id": 0}} # SELECT
]
for r in db.commandes.aggregate(pipeline): print(r)
Le pipeline d'agrégation

Une suite d'étapes : chacune transforme les documents et les passe à la suivante. $match (filtrer, à placer en premier pour utiliser un index), $group, $unwind (déplier un tableau), $project, $sort, $lookup, $out/$merge (écrire le résultat).

Exploitation
  • Replica set (primaire + secondaires) : haute disponibilité, élection automatique ; exigé pour les transactions multi-documents et les change streams, même à un seul nœud.
  • Sharding : répartition horizontale par clé de shard.
  • Docker : volume nommé (sinon les données disparaissent), image épinglée (mongo:8.0), port publié sur 127.0.0.1.
  • Sécurité : compte applicatif readWrite sur une seule base, jamais root.
  • Sauvegarde : mongodump/mongorestore (BSON, types conservés).
  1. explain : viser IXSCAN et un ratio examinés/rendus proche de 1.
  2. Index composé selon ESR ; règle du préfixe ; index unique, partiel, TTL.
  3. Agrégation : $match d'abord, puis $group, $unwind, $project, $sort.
  4. Replica set pour la disponibilité et les transactions ; sharding pour l'échelle ; volumes et comptes dédiés.

Fiche — Index, agrégation, exploitation

Index

Sans index : COLLSCAN. explain("executionStats") : IXSCAN, examinés ≈ rendus. ESR : égalité, tri, plage. Préfixe : {a,b,c} sert {a}, {a,b}, pas {b}.

Types d'index

Unique (E11000 si doublon) · partiel · TTL (expireAfterSeconds) · composé · requête couverte. Coût à l'écriture : supprimer les inutilisés.

Agrégation

$match (en premier) → $unwind → $group → $sort → $project ; $lookup, $merge.

Exploitation

Replica set (HA, transactions, change streams) ; sharding ; volume Docker nommé ; compte readWrite ; mongodump/mongorestore.

Questions d'oral — chapitre 04

À partir de la requête réelle, selon la règle ESR : d'abord les champs d'égalité, puis ceux du tri, enfin ceux en plage. Je vérifie avec explain("executionStats") qu'on obtient un IXSCAN sans tri en mémoire et que le nombre de documents examinés est proche du nombre de documents rendus. Je tiens compte de la règle du préfixe pour qu'un même index serve plusieurs requêtes.

Le replica set copie les mêmes données sur plusieurs nœuds (un primaire, des secondaires) : haute disponibilité et lecture répartie, avec élection automatique d'un nouveau primaire. Le sharding répartit des données différentes sur plusieurs serveurs selon une clé de shard : passage à l'échelle horizontal. En production, chaque shard est lui-même un replica set.

Avec le pipeline d'agrégation : $match pour le WHERE (placé en premier pour profiter des index), $group avec _id = clé de regroupement et des accumulateurs ($sum, $avg), $sort pour l'ORDER BY, $project pour choisir les champs. $unwind déplie un tableau imbriqué avant le regroupement.
