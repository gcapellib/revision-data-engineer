Comment s'assurer qu'une application que l'on écrit aujourd'hui ne soit pas la prochaine à faire la une pour une faille évitable ?

Réagir après chaque incident

On corrige l'exemple d'attaque, on ajoute un filtre, on oublie la classe de failles : le prochain test d'intrusion retrouve la même erreur sous une autre forme.

Poser des barrières par défaut

On rend la mauvaise pratique difficile : requêtes paramétrées, échappement automatique, liste blanche en entrée, échec fermé, dépendances surveillées, contrôles automatisés dans le pipeline.

Sécuriser une application, c'est traiter chaque donnée venant de l'extérieur comme non fiable, n'accorder que les droits nécessaires, échouer fermé, ne rien exposer par erreur (messages, journaux, configuration), maîtriser ce qu'on embarque (dépendances) et vérifier en continu (revue, tests, DevSecOps).

Analogie — un restaurant : on contrôle les ingrédients à la livraison (validation), on sépare cru et cuit (code et données), on affiche seulement ce qu'il faut en salle (erreurs) et on tient un registre (journaux).

Premier contact : le même code, vulnérable puis corrigé

python · avant / après
# VULNÉRABLE : concaténation -> injection SQL
cur.execute("SELECT * FROM clients WHERE nom = '" + nom + "'")

# CORRIGÉ : requête paramétrée, la donnée n'est jamais du code
cur.execute("SELECT * FROM clients WHERE nom = %s", (nom,))

# validation en liste blanche, côté serveur
if not re.fullmatch(r"[A-Za-zÀ-ÿ' -]{1,60}", nom):
    raise ValueError("nom invalide")
Ce qu'il faut remarquer

La requête paramétrée envoie la structure et les valeurs séparément au moteur SQL : la saisie ne peut plus changer le sens. La validation est un second rempart (défense en profondeur), pas le premier.

5 idées font tout le cours

Tout le cours répond à : comment livrer une application qui reste sûre quand ses entrées, ses dépendances et son réseau sont hostiles ? Cinq idées organisent toutes les pratiques.

Idée 1 · Valider à l'entrée, encoder à la sortie

Toute entrée est validée à la frontière de l'application (type, format, taille, liste de valeurs autorisées). Toute sortie est encodée pour l'endroit où elle va (HTML, ligne de commande) ou passée en paramètre (requête SQL). C'est la parade commune à toutes les injections.

L'erreur typique : Si l'on fait confiance à une saisie parce qu'elle vient d'un formulaire « interne », un attaquant peut envoyer la même requête directement au serveur, sans passer par le formulaire.

La bonne pratique : Valider côté serveur toutes les entrées, y compris celles d'un formulaire interne, comme si elles venaient d'inconnus.

ch. 01 · ch. 03

Idée 2 · Ne rien révéler

On ne révèle rien qui aide l'attaquant. L'utilisateur reçoit une erreur générique ; le détail va dans un journal sans secret ni donnée personnelle ; la configuration est durcie (mode debug coupé, en-têtes de sécurité HTTP activés).

L'erreur typique : Si une erreur affiche la requête SQL ou la version du serveur, l'attaquant apprend la structure de la base et les failles connues de cette version.

La bonne pratique : Renvoyer à l'utilisateur « Une erreur est survenue (réf. 1234) » et écrire le détail dans le journal, sous cette référence.

ch. 02 · ch. 03

Idée 3 · Ce qu'on n'a pas écrit fait aussi partie du code

Le code livré vient en majorité d'ailleurs : bibliothèques, images Docker, actions de la CI. On en tient l'inventaire (SBOM, la liste des composants), on l'analyse (SCA, recherche des failles connues), on fixe les versions et l'on met à jour vite.

L'erreur typique : Si l'on ne tient pas la liste des bibliothèques utilisées, une dépendance vulnérable ou malveillante est installée par le build sans que personne le sache.

La bonne pratique : Générer la liste des dépendances à chaque build et la faire analyser (pip-audit, Dependabot) : une faille connue bloque la livraison.

ch. 02 · ch. 04

Idée 4 · Moins on garde, moins on perd

Moins on garde, moins on peut perdre. On classe les données selon leur sensibilité, on collecte le minimum, on masque, on pseudonymise (remplacer le nom par un numéro), on chiffre. Une API ne renvoie que les champs nécessaires et limite le nombre de requêtes.

L'erreur typique : Si l'API renvoie l'objet utilisateur entier, des données sensibles (comme le mot de passe haché) sortent sans même qu'il y ait d'attaque.

La bonne pratique : Définir pour chaque réponse de l'API un modèle de sortie qui ne liste que les champs utiles.

ch. 03

Idée 5 · Automatiser les contrôles dans le pipeline

DevSecOps : les contrôles de sécurité tournent automatiquement à chaque changement dans le pipeline. SAST analyse le code source, SCA les dépendances, un détecteur cherche les secrets, DAST attaque l'application qui tourne. La revue de code et le cloisonnement du réseau complètent.

L'erreur typique : Si un contrôle de sécurité reste manuel, « à faire avant la mise en production », il est sauté le jour où le délai presse.

La bonne pratique : Mettre ces analyses dans la CI : la fusion est bloquée tant qu'une faille grave n'est pas corrigée.

Chapitre 01 · Coder sûr : validation, injections et sorties
① Pourquoi ② Quoi

Principes de secure coding et validation d'entrée

Trois réflexes
  • Moindre privilège (voir Fondamentaux) : le code et ses comptes n'ont que les droits nécessaires.
  • Défense en profondeur : validation et requêtes paramétrées et droits minimaux.
  • Échec fermé (fail-closed) : en cas d'erreur, refuser, jamais autoriser par défaut.
Valider l'entrée
  • Côté serveur, toujours : la validation du navigateur est contournable.
  • Liste blanche (ce qui est permis) plutôt que liste noire (ce qui est interdit).
  • Type, longueur, plage, format ; normalisation avant contrôle (Unicode, chemins).
  • Rejeter plutôt que « réparer » une donnée invalide.
python · validation avec Pydantic
from pydantic import BaseModel, Field, EmailStr
class Inscription(BaseModel):
    email: EmailStr
    age: int = Field(ge=18, le=120)           # plage
    ville: str = Field(max_length=60, pattern=r"^[A-Za-zÀ-ÿ' -]+$")
# toute entrée hors schéma est rejetée avant d'atteindre la base (FastAPI)

Mass assignment : n'accepter que les champs prévus (schéma d'entrée distinct du modèle de table), pour qu'un client ne puisse pas fixer is_admin.

③ Comment ④ Exemple

Requêtes paramétrées, échappement, CSP

Contre l'injection : séparer code et données
  • Requêtes paramétrées (ou requêtes préparées) : la barrière de référence contre l'injection SQL.
  • ORM (SQLAlchemy, SQLModel) : paramètre par défaut ; le SQL brut concaténé le redevient dangereux.
  • Commandes : éviter shell=True ; passer une liste d'arguments.
  • Mécanisme de l'attaque : Vulnérabilités.
python
# commande : liste d'arguments, pas de shell
subprocess.run(["convert", fichier, "out.png"], check=True)
# SQLModel / ORM : paramètres liés
session.exec(select(Client).where(Client.nom == nom))
Contre le XSS : sortie échappée selon le contexte
  • Échapper à la sortie selon le contexte : HTML, attribut, JavaScript, URL.
  • Moteurs de modèles à échappement automatique (Jinja2 autoescape) ; méfiance envers |safe, innerHTML, dangerouslySetInnerHTML.
  • CSP (Content Security Policy) : l'en-tête Content-Security-Policy: default-src 'self' limite l'origine des scripts, même si une injection passe.
  • Cookies HttpOnly (Authentification).

Une entrée se valide ; une sortie s'échappe. Ce sont deux contrôles différents, à ne pas confondre.

Pièges et résumé

Validation seulement dans le navigateur : contournée par un appel direct.
Liste noire de caractères : contournée par encodage.
Concaténer « juste cette fois » dans une requête SQL.
|safe ou innerHTML pour « que ça s'affiche » : XSS.
Réparer silencieusement une saisie invalide : comportement imprévisible ; rejeter.
  1. Moindre privilège, défense en profondeur, échec fermé.
  2. Validation serveur en liste blanche ; schéma d'entrée distinct du modèle.
  3. Requêtes paramétrées, listes d'arguments, ORM sans SQL concaténé.
  4. Échappement selon le contexte + CSP contre le XSS.

Chapitre 01 · Coder sûr : validation, injections et sorties
Ce que le jury peut demander

Questions d'oral — chapitre 01

En utilisant des requêtes paramétrées ou un ORM qui lie les paramètres, de sorte que la donnée ne soit jamais interprétée comme du code, en validant les entrées en liste blanche et en donnant à l'application un compte de base aux droits minimaux.

Parce que la validation du navigateur peut être contournée en appelant directement l'API. Le serveur est le seul endroit où le contrôle est fiable.

En cas d'erreur ou de cas imprévu, le système refuse l'action au lieu de l'autoriser. Par exemple, si la vérification des droits échoue, l'accès est refusé.

Échapper toute donnée dynamique selon son contexte de sortie, utiliser des modèles à échappement automatique, éviter les API qui injectent du HTML brut et poser une Content Security Policy qui restreint l'origine des scripts.

L'acceptation automatique de tous les champs envoyés par le client, qui lui permet de modifier des champs sensibles comme un rôle. On l'évite avec des schémas d'entrée qui ne listent que les champs autorisés.

Chapitre 02 · Erreurs, journaux, dépendances et revue de code
① Pourquoi ② Quoi

Ne rien exposer : erreurs, logs, configuration

Erreurs
  • À l'utilisateur : un message générique et un identifiant de corrélation.
  • Dans les journaux : le détail technique.
  • Jamais de trace de pile, de requête SQL, de chemin ou de version dans une réponse (débogage désactivé en production).
python
try:
    traiter(commande)
except Exception:
    incident_id = uuid4()
    logger.exception("échec commande %s", incident_id)   # détail dans les logs
    raise HTTPException(500, f"Erreur interne (réf. {incident_id})")   # générique côté client
Journaux sûrs
  • Logger : authentifications, accès refusés, actions sensibles, erreurs ; avec horodatage et identifiant.
  • Jamais : mots de passe, jetons, clés, numéros de carte, données personnelles inutiles (secrets).
  • Injection dans les journaux : neutraliser retours à la ligne et caractères de contrôle d'une donnée loguée.
  • Exploiter ces journaux : détection et réponse.

DEBUG=True en production, une page d'erreur détaillée et un compte administrateur par défaut sont des mauvaises configurations classiques.

Dépendances, en-têtes et configuration

Maîtriser ce qu'on embarque

  • Versions épinglées (requirements.txt verrouillé) et mises à jour régulières.
  • Répondre à une CVE : identifier les composants concernés, mettre à jour, tester, déployer ; sinon atténuer.
  • SBOM : inventaire des composants (voir chapitre 04).

Le code qu'on n'a pas écrit représente l'essentiel de l'application : une CVE chez un tiers est une CVE chez vous.

Chapitre 02 · Erreurs, journaux, dépendances et revue de code
⑤ Pièges ⑥ Résumé

La revue de code de sécurité, pièges et résumé

Méthode en trois passes
  • 1. Vue d'ensemble : que fait le changement ? quelles entrées, sorties, droits ?
  • 2. Suivre la donnée non fiable de sa source (requête, fichier) à son puits (SQL, commande, HTML, fichier).
  • 3. Checklist : secrets, eval, pickle.loads, yaml.load, shell=True, verify=False, MD5/SHA-1, random pour la sécurité, contrôle d'accès manquant.
Lire un diff, rédiger un rapport

On ne lit pas que les lignes modifiées : on regarde le contexte. Le rapport donne pour chaque point : gravité, localisation, explication, correctif proposé. Le code généré par IA se relit comme n'importe quel code.

Message d'erreur détaillé en production : cartographie pour l'attaquant.
Journaliser le mot de passe ou le jeton « pour déboguer ».
Dépendances jamais mises à jour : failles publiques exploitées automatiquement.
Revue qui ne regarde que le style : la sécurité se cherche explicitement.
Faire confiance au code généré par IA sans relecture.
  1. Erreurs génériques côté client, détails dans les journaux ; pas de secret dans les logs.
  2. SCA, versions épinglées, SBOM, réponse rapide aux CVE.
  3. En-têtes : CSP, HSTS, nosniff, frame-ancestors, Referrer-Policy.
  4. Revue en trois passes : vue d'ensemble, source → puits, checklist.

Ce que le jury peut demander

Questions d'oral — chapitre 02

Je renvoie au client un message générique avec un identifiant de corrélation et je consigne le détail technique dans les journaux. Jamais de trace de pile, de requête ni de chemin en production.

Les mots de passe, jetons, clés d'API, numéros de carte et les données personnelles inutiles. Il faut aussi neutraliser les retours à la ligne des données consignées pour éviter l'injection dans les journaux.

En trois passes : comprendre le changement et ses entrées, sorties et droits ; suivre la donnée non fiable de la source au puits ; vérifier une checklist de marqueurs dangereux. Je rédige un rapport avec gravité, localisation et correctif.

À demander au navigateur d'appliquer des protections : limiter les sources de scripts avec la CSP, imposer HTTPS avec HSTS, empêcher le sniffing de type, interdire l'affichage dans un cadre, limiter l'URL transmise.

Chapitre 03 · API, données sensibles et pipelines
① Pourquoi ② Quoi

Sécuriser une API

Surface d'attaque d'une API

Une API expose directement des objets et des fonctions : son contrat est aussi sa surface d'attaque. Le référentiel est l'OWASP API Security Top 10 (édition 2023).

RisqueIdéeParade
BOLA (API1)accès à l'objet d'un autre par son identifiantvérifier le propriétaire à chaque requête
Authentification défaillante (API2)jetons faibles, brute forcevoir Authentification
BOPLA (API3)champs sensibles exposés ou modifiablesschémas de sortie et d'entrée dédiés
Consommation de ressources (API4)requêtes massives, pages géantesrate limiting, pagination bornée
BFLA (API5)appel d'une fonction d'administrationcontrôle d'accès par fonction

Mesures courantes
  • Scopes et rôles (principe : moindre privilège, jetons : OAuth).
  • Limitation de débit : réponse 429 avec Retry-After.
  • Validation de schéma (OpenAPI, Pydantic : API Python).
  • Versioning et dépréciation annoncée ; API gateway (chapitre 04).

Retourner uniquement les champs nécessaires : une réponse qui contient mot_de_passe_hache « parce que le modèle l'a » est une fuite.

Chapitre 03 · API, données sensibles et pipelines
③ Comment ④ Exemple

Données sensibles : classer, minimiser, masquer, pseudonymiser

Classer d'abord

On ne protège bien que ce qu'on a identifié : public, interne, confidentiel, sensible (santé, opinions, biométrie…) ; la classe détermine chiffrement, accès, durée de conservation, journalisation. Le cadre juridique est dans Qualité & gouvernance (RGPD).

Minimiser
  • Ne collecter que le nécessaire ; ne pas copier la donnée dans chaque environnement.
  • Conserver le temps utile, purger ensuite (effacement effectif, sauvegardes comprises) ; un simple « soft delete » ne suffit pas.
  • Données de test : factices ou anonymisées, jamais la production brute.

Chapitre 03 · API, données sensibles et pipelines
⑤ Pièges ⑥ Résumé

Pipelines de données, partage et pièges

Pipelines de données
  • Flux chiffrés (TLS) et authentifiés ; compte de service par pipeline.
  • Intégrité et qualité : schéma validé, contrôles à l'ingestion (Qualité).
  • Cloisonnement : zones brute / nettoyée / consommation, droits distincts, réseaux privés.
  • Audit : qui a lu ou modifié quoi.
Partage et tiers
  • Partager le minimum, sous contrat, avec des droits limités et datés.
  • Transferts hors UE : garanties (décision d'adéquation, clauses contractuelles types) — RGPD.
  • Sous-traitants : contrat, audit, notification des incidents.
Retourner l'objet entier de la base par l'API : fuite de champs.
« Anonymisé » qui ne l'est pas : recoupable par croisement ; c'est de la pseudonymisation.
Copier la production en test : données personnelles exposées.
Rate limiting absent : extraction massive et déni de service.
API « zombie » : ancienne version jamais retirée, sans contrôle.
  1. API : OWASP API Top 10, BOLA en tête ; autorisation par objet et par fonction, rate limiting, schémas.
  2. Classer, minimiser, purger ; masquage, tokenisation, pseudonymisation, anonymisation.
  3. Pseudonymisé ≠ anonymisé : toujours une donnée personnelle.
  4. Pipelines : flux chiffrés, compte par pipeline, zones cloisonnées, audit.

Questions d'oral — chapitre 03

Broken Object Level Authorization : l'API ne vérifie pas que l'objet demandé appartient à l'appelant, ce qui permet de lire l'objet d'un autre en changeant l'identifiant. La parade est de contrôler le propriétaire à chaque requête.

Pour empêcher l'extraction massive de données, le brute force et la saturation du service. La réponse 429 informe le client du moment où il peut réessayer.

La pseudonymisation remplace les identifiants directs par un pseudonyme mais permet de revenir à la personne avec une information supplémentaire : la donnée reste personnelle. L'anonymisation est irréversible, la personne n'est plus identifiable.

Je n'utilise pas la production brute : des données factices ou réellement anonymisées, avec les mêmes volumes et formes, pour ne pas multiplier les copies de données personnelles.

Compte de service dédié aux droits minimaux, flux chiffrés et authentifiés, validation des schémas et de la qualité à l'ingestion, zones cloisonnées avec droits distincts, journalisation d'audit et secrets hors du code.

Chapitre 04 · Réseau, DevSecOps, tests et maturité
① Pourquoi ② Quoi

Protocoles et architecture réseau

Ce que chaque protocole protège (ou non)
  • HTTPS : transport chiffré (TLS, certificats).
  • DNS : sans protection, réponses falsifiables (cache poisoning), exfiltration par tunnel DNS ; DNSSEC authentifie les réponses.
  • SMTP : courriel falsifiable ; SPF, DKIM, DMARC authentifient l'expéditeur.
  • SSH : accès d'administration ; clés plutôt que mots de passe, root interdit, port exposé limité.

Un protocole historique transmet souvent en clair (HTTP, FTP, Telnet, SMTP simple) : on les remplace par leurs versions sécurisées.

Architecture : segmenter
  • Segmentation : réseaux séparés (utilisateurs, serveurs, données) ; un attaquant ne circule pas librement.
  • DMZ : zone tampon pour ce qui est exposé à Internet.
  • Pare-feu en refus par défaut (on n'ouvre que le nécessaire) ; bastion pour l'administration.
  • Zero Trust : pas de confiance liée à l'emplacement ; chaque accès vérifié (identité, appareil, contexte), micro-segmentation, mTLS entre services.
API gateway

Point d'entrée unique devant les API : authentification, rate limiting, WAF, journalisation centralisée, routage. Elle ne remplace pas la sécurité de chaque service.

Tests de sécurité, maturité et résumé

Tests de sécurité automatisés
  • Smoke tests : les routes protégées répondent 401/403 sans jeton ; les en-têtes de sécurité sont présents.
  • Fuzzing léger : entrées aléatoires ou limites pour provoquer des erreurs inattendues (Hypothesis).
  • Non-régression : un test pour chaque faille corrigée, pour qu'elle ne revienne pas.
Maturité et veille
  • OWASP SAMM, BSIMM : évaluer et planifier sa maturité ; feuille de route priorisée par le risque.
  • Veille continue : CERT-FR, avis des éditeurs, GitHub advisories.
  • IA : accélère aussi l'attaque et produit du code à relire.
Un seul contrôle (SAST seul) : chaque outil voit une partie.
Pipeline qui ne bloque jamais : les alertes sont ignorées.
API gateway seule : un service interne sans contrôle reste vulnérable.
Pare-feu en « tout ouvert par défaut ».
SSH exposé avec mot de passe : attaques par force brute en continu.
  1. HTTPS/TLS, DNSSEC, SPF/DKIM/DMARC, SSH par clés.
  2. Segmentation, DMZ, refus par défaut, Zero Trust, API gateway.
  3. SAST, SCA, secrets, DAST, IaC dans le CI ; gates ; SBOM.
  4. Tests de non-régression ; maturité par SAMM ; veille.

Questions d'oral — chapitre 04

Le SAST analyse le code source sans l'exécuter pour y trouver des motifs dangereux. Le DAST attaque l'application en fonctionnement, comme le ferait un attaquant, et détecte des failles visibles à l'exécution. Ils sont complémentaires.

À disposer de l'inventaire exact des composants et versions embarqués. Quand une nouvelle CVE est publiée, on sait immédiatement si l'on est concerné et où.

Aucune confiance accordée du seul fait de l'emplacement réseau : chaque accès est authentifié et autorisé selon l'identité, l'appareil et le contexte, avec micro-segmentation et chiffrement entre services.

Servir de point d'entrée unique qui centralise l'authentification, la limitation de débit, le filtrage et la journalisation devant les API. Elle ne dispense pas chaque service de ses propres contrôles.

En écrivant un test de non-régression qui reproduit l'attaque et qui échoue avant le correctif, puis en l'intégrant au pipeline.
