Immersion · 1 / 3

Comment retrouver en une seconde les 10 meilleurs clients parmi 50 millions de commandes ?

Sans SQL

Il faudrait écrire un programme : ouvrir les fichiers, parcourir chaque commande, additionner par client dans un dictionnaire, trier, gérer la mémoire, les fichiers corrompus, les accès simultanés… et le réécrire pour chaque nouvelle question.

Avec SQL

On décrit le résultat en quelques lignes ; le moteur de la base trouve seul le moyen le plus rapide de l'obtenir (index, ordre des opérations).

SQL (Structured Query Language) est le langage standard pour interroger et manipuler des données organisées en tables reliées entre elles (bases relationnelles).

Analogie — le bibliothécaire. Tu ne parcours pas toi-même les rayons : tu lui dis « les romans policiers parus après 2020, triés par auteur ». Il connaît le classement et va droit au but. SQL est la langue dans laquelle on parle au bibliothécaire ; la base de données est la bibliothèque.
Déclaratif

On dit quoi, pas comment. C'est ce qui rend SQL accessible aux analystes et optimisable par la machine.

Pourquoi il est partout dans la data
  • Les bases transactionnelles des applications (commandes, clients) parlent SQL.
  • Les outils Big Data ont tous ajouté une couche SQL : Hive, Spark SQL, Trino ; les entrepôts cloud aussi (Snowflake, BigQuery, Redshift).
  • La BI (Power BI) et les outils de transformation (dbt) génèrent ou exécutent du SQL.
  • Il figure dans quasiment toutes les offres d'emploi de Data Engineer et d'analyste.
SQL tout au long du pipeline

Les modes passent (NoSQL, Big Data, cloud) ; SQL reste, parce que tout le monde finit par vouloir interroger ses données en tables.

Immersion · Essentiel

Présenter SQL en une minute

« SQL, Structured Query Language, est le langage standard pour interroger et manipuler des données relationnelles, c'est-à-dire organisées en tables reliées par des clés. Il est né chez IBM dans les années 1970, à partir du modèle relationnel d'Edgar Codd, et il est normalisé depuis 1986.

C'est un langage déclaratif : on décrit le résultat voulu et l'optimiseur du moteur choisit comment l'obtenir. C'est ce qui le rend à la fois accessible et performant.

Pour un Data Engineer, il est incontournable : les bases applicatives parlent SQL, et les outils Big Data et cloud l'ont tous adopté — Hive, Spark SQL, Snowflake, BigQuery. Je l'utilise pour extraire, contrôler, transformer et charger les données, et pour concevoir des modèles analytiques.

Ses limites : les données très hétérogènes ou les accès massifs par clé, où une base NoSQL peut être plus adaptée. »

5 idées font tout le cours

Tout le cours répond à : comment obtenir de la base exactement la réponse voulue, vite, et écrire sans jamais l'abîmer ? Cinq règles suffisent à expliquer les résultats inattendus.

Idée 1 · On décrit le résultat, pas le chemin

SQL est déclaratif : on décrit le résultat voulu, et l'optimiseur choisit comment l'obtenir. La requête s'exécute dans un ordre logique (FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY) : c'est pourquoi un alias créé dans le SELECT n'existe pas encore dans le WHERE.

L'erreur typique : Si l'on utilise dans le WHERE un alias défini dans le SELECT, ou si l'on filtre un agrégat avec WHERE au lieu de HAVING, la requête échoue.

La bonne pratique : Répéter l'expression dans le WHERE (ou passer par une sous-requête), et filtrer les agrégats avec HAVING.

ch. 01 · ch. 03 · ch. 05

Idée 2 · NULL n'est pas une valeur

NULL veut dire inconnu, pas zéro ni vide. Toute comparaison avec NULL donne « inconnu », ni vrai ni faux. D'où IS NULL pour le tester, COALESCE pour le remplacer, COUNT(colonne) qui ignore les NULL, et le piège du NOT IN.

L'erreur typique : Si la sous-requête d'un NOT IN contient un seul NULL, la requête ne renvoie aucune ligne, sans aucun message d'erreur.

La bonne pratique : Écrire NOT EXISTS (ou exclure les NULL dans la sous-requête) au lieu de NOT IN.

ch. 01 · ch. 02 · ch. 03

Idée 3 · Toujours savoir à quel grain on est

Le grain, c'est ce que représente une ligne (une commande, une ligne de commande, un client par mois). Une jointure peut multiplier les lignes, un GROUP BY les regroupe, une fonction de fenêtre calcule sans les regrouper. Vérifier le grain avant d'additionner évite de compter deux fois.

L'erreur typique : Si l'on joint commandes et lignes de commande puis qu'on additionne le montant de la commande, chaque commande est comptée autant de fois qu'elle a de lignes.

La bonne pratique : Additionner au bon grain : le montant des lignes dans la table des lignes, ou celui des commandes avant la jointure.

ch. 02 · ch. 03 · ch. 05

Idée 4 · Écrire en tout ou rien, et pouvoir rejouer

On écrit en tout ou rien et l'on peut rejouer. Les transactions ACID annulent tout si une étape échoue ; les contraintes (clé primaire, clé étrangère, UNIQUE, CHECK) refusent les incohérences ; l'UPSERT ou le « supprimer puis réinsérer » rendent un chargement rejouable sans doublon. Avant un UPDATE ou un DELETE, on teste le WHERE avec un SELECT.

L'erreur typique : Si l'on lance un UPDATE sans WHERE, toute la table est modifiée ; et si un chargement est rejoué sans précaution, les lignes sont en double.

La bonne pratique : Lancer d'abord un SELECT avec le même WHERE, puis l'UPDATE dans une transaction, et vérifier le nombre de lignes touchées avant le COMMIT.

ch. 04

Idée 5 · La performance se lit dans le plan

Un index évite de lire toute la table, à condition que le filtre soit sargable : pas de fonction appliquée à la colonne indexée. EXPLAIN montre le chemin choisi par la base. Pour l'analyse : modèle en étoile, vues matérialisées, chargement incrémental.

L'erreur typique : Si l'on écrit WHERE YEAR(date) = 2026, la base ne peut pas utiliser l'index sur la colonne date et lit toute la table.

La bonne pratique : Écrire WHERE date >= '2026-01-01' AND date < '2027-01-01' : la condition porte sur la colonne brute, l'index sert.

Chapitre 01 · Requêter
② Quoi ③ Comment

L'ordre d'écriture n'est pas l'ordre d'exécution

SQL · anatomie d'un SELECT
SELECT   p.categorie, COUNT(*) AS nb      -- 5 · projeter
FROM     produit p                          -- 1 · sources
WHERE    p.prix > 2                         -- 2 · filtrer les LIGNES
GROUP BY p.categorie                        -- 3 · regrouper
HAVING   COUNT(*) >= 3                     -- 4 · filtrer les GROUPES
ORDER BY nb DESC                            -- 6 · trier
LIMIT    5;                                 -- 7 · limiter
Ordre logique

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Conséquence : un alias défini dans le SELECT (nb) est inconnu dans le WHERE (qui s'exécute avant) mais utilisable dans le ORDER BY (qui s'exécute après).

SQL est déclaratif

On décrit le résultat voulu ; l'optimiseur du moteur choisit le plan (ordre des jointures, index). C'est le même principe que Catalyst dans Spark ou le driver de Hive.

Analogie — la commande au restaurant. On dit « une tarte aux pommes pour deux, sans cannelle » ; le chef décide dans quel ordre éplucher, cuire et dresser.

Ce que le jury peut demander

Questions d'oral — chapitre 01

Logiquement : FROM (et jointures), WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT. C'est pour cela qu'un alias du SELECT n'existe pas encore dans le WHERE, et qu'on filtre les lignes avec WHERE mais les groupes avec HAVING. Physiquement, l'optimiseur peut réordonner, tant que le résultat est identique.

NULL signifie « inconnu ». Toute comparaison avec NULL renvoie UNKNOWN et le WHERE ne garde que les conditions vraies : on teste avec IS NULL / IS NOT NULL. Les agrégats ignorent les NULL (sauf COUNT(*)), les opérations arithmétiques propagent le NULL, et COALESCE fournit une valeur par défaut.

DELETE (DML) supprime des lignes, éventuellement filtrées, une par une, journalisées, annulables. TRUNCATE (DDL) vide toute la table d'un coup, très vite. DROP supprime la table elle-même (structure et données).

Chapitre 02 · Jointures et agrégations
② Quoi ③ Comment

Relier les tables : les types de jointure

Clients (A) et commandes (B)
SQL · chiffre d'affaires par client, y compris sans commande
SELECT   c.nom,
         COALESCE(SUM(l.qte * p.prix), 0) AS ca
FROM     client c
LEFT JOIN commande       o ON o.client_id   = c.id
LEFT JOIN ligne_commande l ON l.commande_id = o.id
LEFT JOIN produit        p ON p.id          = l.produit_id
GROUP BY c.nom
ORDER BY ca DESC;
CROSS JOIN = produit cartésien

Toutes les combinaisons : 1 000 × 1 000 = 1 million de lignes. Utile pour générer un calendrier × produits ; catastrophique quand c'est un ON oublié.

Le piège du LEFT JOIN « annulé »

Un filtre sur la table de droite placé dans le WHERE (WHERE o.statut = 'payée') élimine les lignes où o est NULL : le LEFT redevient un INNER. Le mettre dans le ON : ON o.client_id = c.id AND o.statut = 'payée'.

Chapitre 02 · Jointures et agrégations
③ Comment ⑤ Pièges ⑥ Résumé

Agréger : GROUP BY, HAVING

SQL · catégories qui dépassent 1 000 € de CA en 2026
SELECT   p.categorie,
         COUNT(DISTINCT o.id)   AS nb_commandes,
         SUM(l.qte * p.prix)     AS ca
FROM     ligne_commande l
JOIN     produit  p ON p.id = l.produit_id
JOIN     commande o ON o.id = l.commande_id
WHERE    o.date_cmd >= '2026-01-01'      -- lignes
GROUP BY p.categorie
HAVING   SUM(l.qte * p.prix) > 1000;     -- groupes
Règle du GROUP BY

Chaque colonne du SELECT est soit dans le GROUP BY, soit dans un agrégat (COUNT, SUM, AVG, MIN, MAX). Sinon : erreur (ou résultat arbitraire dans les moteurs permissifs).

WHERE vs HAVING

WHERE filtre les lignes avant le regroupement (et peut utiliser un index) ; HAVING filtre les groupes après, sur des agrégats. Filtrer le plus tôt possible : WHERE quand c'est possible.

Jointure 1-N avant agrégation : les lignes du côté « 1 » sont dupliquées → SUM gonflé ; d'où COUNT(DISTINCT o.id) pour compter les commandes.
AVG d'une colonne avec NULL : les NULL sont ignorés (moyenne des valeurs connues), pas comptés comme 0.
Vérifier les volumes : nombre de lignes avant et après chaque jointure.
  1. INNER, LEFT, RIGHT, FULL, CROSS ; filtre de la table de droite d'un LEFT dans le ON.
  2. GROUP BY : colonnes groupées ou agrégées ; WHERE (lignes) avant HAVING (groupes).
  3. Contrôler les volumes : produit cartésien et duplication 1-N faussent les sommes.

Chapitre 02 · Jointures et agrégations
Ce que le jury peut demander

Questions d'oral — chapitre 02

INNER JOIN ne garde que les lignes qui ont une correspondance des deux côtés. LEFT JOIN garde toutes les lignes de la table de gauche et complète par NULL quand il n'y a pas de correspondance : c'est ce qu'il faut pour « tous les clients, même sans commande ». Attention : un filtre sur la table de droite dans le WHERE annule l'effet du LEFT.

WHERE filtre les lignes avant le regroupement et ne peut pas utiliser d'agrégat ; HAVING filtre les groupes après agrégation. Pour la performance, on filtre au maximum dans le WHERE, qui réduit les données avant le GROUP BY et peut s'appuyer sur un index.

Probablement une jointure 1-N ou N-N qui duplique des lignes avant l'agrégation (par exemple joindre les commandes et les paiements multiples), ou une condition de jointure incomplète (produit cartésien partiel). Je compare les volumes avant et après la jointure, j'agrège chaque côté séparément puis je joins les agrégats, ou j'utilise COUNT(DISTINCT …).

Chapitre 03 · Requêtes avancées
② Quoi ④ Exemple

Sous-requêtes : IN, EXISTS et le piège NOT IN

Scalaire

Renvoie une seule valeur, utilisable comme une constante : WHERE prix > (SELECT AVG(prix) FROM produit).

IN

Appartenance à un ensemble : WHERE id IN (SELECT client_id FROM commande).

EXISTS (corrélée)

Teste la présence d'au moins une ligne, sans récupérer les valeurs ; s'arrête dès la première trouvée : WHERE EXISTS (SELECT 1 FROM commande o WHERE o.client_id = c.id).

NOT IN et NULL : WHERE id NOT IN (SELECT client_id FROM commande) renvoie 0 ligne dès qu'un client_id est NULL dans la sous-requête (comparer à NULL donne UNKNOWN). Pour « les clients sans commande », écrire NOT EXISTS ou un LEFT JOIN … WHERE o.id IS NULL (l'anti-jointure).

SQL · CTE : un pipeline lisible, étape par étape
WITH ventes AS (
    SELECT o.client_id, SUM(l.qte * p.prix) AS ca
    FROM commande o
    JOIN ligne_commande l ON l.commande_id = o.id
    JOIN produit p        ON p.id = l.produit_id
    GROUP BY o.client_id
),
moyenne AS (SELECT AVG(ca) AS ca_moy FROM ventes)
SELECT v.client_id, v.ca
FROM   ventes v, moyenne m
WHERE  v.ca > m.ca_moy;          -- meilleurs clients
CTE (Common Table Expression)

Une requête nommée avec WITH, utilisable dans la suite. Elle découpe une transformation complexe en étapes nommées, exactement comme un pipeline : plus lisible, plus testable.

CTE récursive

WITH RECURSIVE : un cas de départ + une partie qui se rappelle elle-même, pour parcourir une hiérarchie (catégories, organigramme, nomenclature d'une recette).

② Quoi ④ Exemple — fonctions de fenêtrage ⑥ Résumé

Fenêtres : enrichir chaque ligne sans la fusionner

Même concept que dans Spark (voir Spark ch. 03) : fonction() OVER (PARTITION BY … ORDER BY … [cadre]). Le GROUP BY réduit les lignes, la fenêtre les conserve.

SQL · top 3 produits par catégorie, évolution mensuelle
SELECT * FROM (
  SELECT categorie, nom, prix,
         DENSE_RANK() OVER (PARTITION BY categorie
                            ORDER BY prix DESC) AS rg
  FROM produit) t
WHERE rg <= 3;     -- on ne peut pas filtrer une fenêtre dans son propre WHERE

SELECT mois, ca,
       ca - LAG(ca) OVER (ORDER BY mois) AS variation,
       SUM(ca) OVER (ORDER BY mois
                     ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cumul
FROM ca_mensuel;
FonctionRôle
ROW_NUMBER()numéro unique 1, 2, 3 (départage obligatoire)
RANK()égalités au même rang, puis saut : 1, 1, 3
DENSE_RANK()égalités au même rang, sans saut : 1, 1, 2
LAG() / LEAD()valeur de la ligne précédente / suivante
SUM() OVERcumul, total glissant, part du total
Usage data engineering

Dédoublonner en gardant la version la plus récente : ROW_NUMBER() OVER (PARTITION BY id ORDER BY maj DESC) = 1. C'est le motif le plus utilisé en production.

  1. Sous-requête scalaire, IN, EXISTS ; NOT IN + NULL = 0 ligne → NOT EXISTS.
  2. CTE = étapes nommées d'un pipeline ; WITH RECURSIVE pour les hiérarchies.
  3. Fenêtres : PARTITION BY + ORDER BY ; ROW_NUMBER pour dédoublonner, LAG pour comparer, SUM OVER pour cumuler.
Chapitre 03 · Requêtes avancées

Fiche — Sous-requêtes, CTE, fenêtres

Sous-requêtes

Scalaire (une valeur), IN (ensemble), EXISTS (présence, corrélée, s'arrête au premier). NOT IN avec un NULL → 0 ligne : préférer NOT EXISTS.

CTE

WITH a AS (…), b AS (…) SELECT … : étapes nommées, lisibles. WITH RECURSIVE : hiérarchies.

Fenêtres

f() OVER (PARTITION BY … ORDER BY … ROWS BETWEEN …) ; ROW_NUMBER 1,2,3 · RANK 1,1,3 · DENSE_RANK 1,1,2 · LAG/LEAD · SUM OVER.

Motif clé

Dédoublonner : ROW_NUMBER() OVER (PARTITION BY id ORDER BY maj DESC) = 1 dans une sous-requête ou une CTE (une fenêtre ne se filtre pas dans son propre WHERE).

Chapitre 03 · Requêtes avancées
Ce que le jury peut demander

Questions d'oral — chapitre 03

Avec une fonction de fenêtre : ROW_NUMBER() OVER (PARTITION BY id_metier ORDER BY date_maj DESC), puis on ne garde que les lignes de rang 1, dans une CTE ou une sous-requête. C'est déterministe si le tri départage les égalités.

Pour découper une transformation complexe en étapes nommées et lisibles, comme les étapes d'un pipeline ; chaque étape se teste séparément. On peut réutiliser une CTE plusieurs fois dans la requête, et la forme récursive permet de parcourir une hiérarchie.

Si la sous-requête contient un NULL, x NOT IN (…, NULL) équivaut à x <> … AND x <> NULL, et la comparaison avec NULL vaut UNKNOWN : aucune ligne ne passe. NOT EXISTS n'a pas ce problème.

Chapitre 04 · Écrire de façon fiable
① Pourquoi ③ Comment

Un pipeline qu'on peut relancer sans casse

SQL · UPSERT (PostgreSQL)
INSERT INTO produit (id, nom, categorie, prix)
VALUES (42, 'Baguette tradition', 'pain', 1.30)
ON CONFLICT (id) DO UPDATE
   SET prix = EXCLUDED.prix,           -- valeur proposée
       nom  = EXCLUDED.nom;
-- standard SQL / autres SGBD : MERGE INTO … WHEN MATCHED THEN UPDATE
--                                      WHEN NOT MATCHED THEN INSERT
Idempotence — le principe central

Exécuter le traitement une ou plusieurs fois donne le même résultat. Un job relancé après un échec (ou deux fois par erreur) ne doit créer ni doublon ni erreur. Moyens : UPSERT sur une clé, ou supprimer puis réinsérer la partition du jour (« delete-insert ») dans une transaction.

Table de staging

On charge d'abord dans une table intermédiaire, on contrôle (comptages, clés, valeurs), puis on bascule dans la table finale en une transaction. La table finale n'est jamais à moitié remplie.

Analogie — l'interrupteur et le bouton « +1 ». Appuyer deux fois sur « allumer » laisse la lumière allumée (idempotent) ; appuyer deux fois sur « ajouter une baguette au panier » en met deux (non idempotent). Un pipeline doit ressembler à l'interrupteur.

Transactions et propriétés ACID

SQL · tout ou rien
BEGIN;
DELETE FROM ventes_jour WHERE jour = '2026-11-17';
INSERT INTO ventes_jour
  SELECT * FROM staging_ventes WHERE jour = '2026-11-17';
COMMIT;      -- ou ROLLBACK en cas d'erreur : rien n'a changé
PropriétéGarantie
Atomicitétout ou rien : jamais d'état à moitié appliqué
Cohérencela base passe d'un état valide à un autre (contraintes respectées)
Isolationles transactions simultanées ne se voient pas à moitié (niveaux : read committed, repeatable read, serializable)
Durabilitéune fois COMMIT, la donnée survit à une panne (journal sur disque)
UPDATE / DELETE

Toujours avec un WHERE testé d'abord en SELECT : un UPDATE sans WHERE modifie toute la table.

Contraintes

PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, CHECK : la base refuse les données incohérentes (intégrité). Une clé unique rend l'UPSERT possible.

Et le Big Data ?

Les fichiers d'un data lake n'ont pas d'ACID natif : c'est ce qu'apportent les formats de tables Delta et Iceberg (transactions, MERGE).

  1. Idempotence : relancer = même résultat (UPSERT, delete-insert de partition).
  2. Staging → contrôles → bascule en une transaction.
  3. ACID : atomicité, cohérence, isolation, durabilité ; BEGIN / COMMIT / ROLLBACK.

Clés étrangères en cascade, transactions et SAVEPOINT

ON DELETE …Effet quand on supprime le parentExemple
RESTRICT / NO ACTIONrefus : erreur de clé étrangère, rien n'est suppriméprotéger le catalogue produits
CASCADEsupprime aussi les enfants, sur plusieurs niveauxles lignes d'une commande supprimée
SET NULLla clé des enfants passe à NULL (colonne nullable obligatoire)garder les commandes d'un client anonymisé
SET DEFAULTla clé prend sa valeur par défaut (refusé par MySQL InnoDB)réaffecter à un client générique

Une cascade est atomique mais silencieuse. Un seul DELETE FROM clients peut vider trois tables (clients → commandes → lignes), sans dire combien de lignes filles ont disparu. Réflexe : BEGIN, supprimer, compter les tables filles, puis COMMIT si c'est conforme, ROLLBACK sinon. Sous SQLite, les clés étrangères sont ignorées sans PRAGMA foreign_keys = ON; à chaque connexion.

SQL · déclarer les actions
CREATE TABLE lignes_commande (
  commande_id INT NOT NULL,
  produit_id  INT NOT NULL,
  FOREIGN KEY (commande_id) REFERENCES commandes(id)
      ON DELETE CASCADE,    -- une ligne sans commande n'existe pas
  FOREIGN KEY (produit_id) REFERENCES produits(id)
      ON DELETE RESTRICT    -- on protège le catalogue
);
SQL · SAVEPOINT : annuler une partie seulement
BEGIN;
DELETE FROM clients WHERE id = 3;          -- cascade OK
SAVEPOINT apres_client;
DELETE FROM produits WHERE stock = 0;    -- échoue : RESTRICT
ROLLBACK TO SAVEPOINT apres_client;      -- annule SEULEMENT le 2e DELETE
COMMIT;                                  -- le 1er DELETE est validé
À retenir

ROLLBACK annule toute la transaction ; ROLLBACK TO SAVEPOINT revient à un point intermédiaire. Même syntaxe sous MySQL, PostgreSQL et SQLite.

Procédures stockées : la logique dans la base

SQL · MySQL / MariaDB
DELIMITER $$                  -- sinon le client coupe au premier ;
CREATE PROCEDURE restocker(IN p_id INT, IN p_qte INT)
BEGIN
  UPDATE produits SET stock = stock + p_qte WHERE id = p_id;
END $$
DELIMITER ;

CALL restocker(1, 50);
-- PostgreSQL : corps entre $$ … $$ (dollar-quoting), langage PL/pgSQL
-- SQLite : aucune procédure stockée, la logique reste en Python
ProcédureFonction
AppelCALL p(...)dans une requête : SELECT f(...)
Retourrien, ou paramètres OUTune valeur (ou une table)
Vocationfaire : écrire, orchestrer une transactioncalculer : renvoyer un résultat
Pourquoi
  • Atomicité côté serveur : « passer une commande » (créer la commande, les lignes, décrémenter le stock) ne peut plus oublier une étape ni le COMMIT.
  • Un seul aller-retour réseau au lieu de cinq.
  • Sécurité : on accorde GRANT EXECUTE sur la procédure sans donner UPDATE sur les tables.
Paramètres

IN (entrée, par défaut), OUT (sortie récupérée par l'appelant), INOUT (les deux). Structures : IF … THEN … END IF, WHILE, variables DECLARE.

Limites
  • Logique métier éparpillée entre application et base : plus dure à versionner, tester, déboguer.
  • Dialecte non portable d'un SGBD à l'autre.
  • À réserver aux opérations transactionnelles critiques, proches des données.

Chapitre 04 · Écrire de façon fiable
Ce que le jury peut demander

Questions d'oral — chapitre 04

Un pipeline qu'on peut relancer autant de fois que nécessaire en obtenant le même état final : indispensable car les jobs échouent et sont rejoués. En SQL : UPSERT sur une clé métier unique, ou suppression puis réinsertion de la partition traitée (le jour, le lot) dans une même transaction, en passant par une table de staging contrôlée.

Atomicité : une transaction s'applique entièrement ou pas du tout. Cohérence : elle fait passer la base d'un état valide à un autre, contraintes respectées. Isolation : les transactions concurrentes ne voient pas les états intermédiaires des autres (selon le niveau d'isolation). Durabilité : ce qui est validé survit aux pannes, grâce au journal.

Un seul DELETE peut supprimer des lignes sur plusieurs niveaux de tables sans le signaler. Je supprime dans une transaction, je compte les lignes restantes des tables filles, puis je valide si le résultat est conforme ou j'annule avec ROLLBACK. SAVEPOINT permet d'annuler seulement une partie.

Pour une opération transactionnelle critique et proche des données, comme passer une commande : l'atomicité est garantie côté serveur, il n'y a qu'un aller-retour réseau et l'on peut accorder le droit EXECUTE sans donner l'accès en écriture aux tables. Je l'évite pour une logique métier qui change souvent, car elle est moins portable et plus difficile à tester.

Pour ne jamais exposer une table finale à moitié chargée ou corrompue : on charge et on contrôle (volumes, unicité des clés, valeurs) dans une zone intermédiaire, puis on bascule en une transaction. En cas de problème, la table finale est intacte et l'on peut analyser la staging.

Chapitre 05 · Performance et analytique
① Pourquoi ③ Comment

Index, EXPLAIN et sargabilité

Sans index : le scan complet

Pour trouver les commandes d'un client, le moteur lit toute la table (Seq Scan). Coût proportionnel à la taille de la table.

L'index (B-tree)

Structure triée qui pointe vers les lignes : la recherche devient logarithmique (Index Scan). Accélère les lectures (WHERE, JOIN, ORDER BY) mais ralentit les écritures (chaque INSERT/UPDATE met l'index à jour) et prend de la place. Indexer : clés étrangères, colonnes filtrées souvent et sélectives.

Analogie — l'index d'un livre. Pour trouver « levain », on ne relit pas les 400 pages : on va à l'index, qui donne la page. Mais chaque nouvelle page écrite oblige à mettre l'index à jour.
SQL · voir le plan
CREATE INDEX idx_cmd_client ON commande(client_id);
EXPLAIN ANALYZE
SELECT * FROM commande WHERE client_id = 42;
-- Index Scan using idx_cmd_client … (actual time=0.02 ms)
Sargabilité (Search ARGument ABLE)

Une fonction appliquée à la colonne indexée empêche d'utiliser l'index : WHERE EXTRACT(YEAR FROM date_cmd) = 2026 → scan complet. Écrire plutôt la condition sur la colonne nue : WHERE date_cmd >= '2026-01-01' AND date_cmd < '2027-01-01'. Idem pour UPPER(nom) ou LIKE '%pain'.

Chapitre 05 · Performance et analytique
③ Comment ④ Exemple

Vues, incrémental, historisation

VIEW

Requête enregistrée, recalculée à chaque appel : simplifie et sécurise l'accès (on expose une vue, pas les tables), sans gain de performance.

MATERIALIZED VIEW

Vue qui stocke son résultat : lecture rapide, mais données figées jusqu'au REFRESH MATERIALIZED VIEW. Idéale pour des agrégats coûteux lus souvent (tableaux de bord).

Traitement incrémental

Ne traiter que les nouvelles lignes : on mémorise la dernière date (ou id) chargée — le high-water mark — et on filtre WHERE maj > :dernier_chargement. Moins de calcul, moins de coût (éco-conception).

SCD — Slowly Changing Dimensions

Comment gérer un attribut qui change (le client déménage) :

  • Type 1 : on écrase l'ancienne valeur — pas d'historique.
  • Type 2 : on ajoute une nouvelle ligne avec des dates de validité (date_debut, date_fin, est_courant) — historique complet ; une vente de 2024 reste rattachée à l'adresse de 2024.
  • Type 3 : une colonne « valeur précédente » (historique limité).
SQL · agréger par période
SELECT DATE_TRUNC('month', date_cmd) AS mois,
       COUNT(*) AS nb
FROM   commande
WHERE  date_cmd >= CURRENT_DATE - INTERVAL '12 months'
GROUP BY 1 ORDER BY 1;

-- sous-totaux à plusieurs niveaux en une requête
SELECT categorie, nom, SUM(prix)
FROM produit GROUP BY ROLLUP (categorie, nom);

Faits et dimensions

La table de faits contient les mesures (quantité, montant) et les clés vers les dimensions, qui décrivent le contexte (quand, quoi, qui, où). La dénormalisation est un choix pour l'analyse, pas une négligence. Variante normalisée : le modèle en flocon.

  2. Vue (recalculée) vs vue matérialisée (stockée, REFRESH).
  3. Incrémental par high-water mark ; SCD 1 (écrase), 2 (historise), 3 (valeur précédente).
  4. OLTP normalisé vs OLAP en étoile (faits + dimensions).
Chapitre 05 · Performance et analytique
⑤ Pièges

Les pièges de la performance et du SQL analytique

Une fonction sur la colonne indexée : WHERE YEAR(date_vente) = 2025 empêche d'utiliser l'index : écrire l'intervalle date_vente >= '2025-01-01' AND date_vente < '2026-01-01' (requête sargable).
Indexer « au cas où » : chaque index accélère certaines lectures mais ralentit tous les INSERT/UPDATE et occupe de la place : on indexe d'après les requêtes réellement lentes.
Croire le plan estimé : EXPLAIN montre des estimations ; EXPLAIN ANALYZE (PostgreSQL) exécute la requête et donne les temps et volumes réels.
Confondre vue et vue matérialisée : une vue relance sa requête à chaque lecture ; une vue matérialisée stocke le résultat et doit être rafraîchie, sinon elle sert des chiffres périmés.
Incrémental naïf : charger « ce qui a changé depuis hier » d'après une date de mise à jour oublie les suppressions et les lignes arrivées en retard : prévoir une fenêtre de recouvrement et un traitement des suppressions.
Grain de la table de faits flou : sans grain défini (une ligne = une vente ? une ligne de ticket ?), les jointures dupliquent les lignes et les sommes sont fausses.

Fiche — Performance et SQL analytique

Index

B-tree : WHERE, JOIN, ORDER BY plus rapides ; INSERT/UPDATE plus lents. Indexer les FK et colonnes filtrées sélectives. EXPLAIN ANALYZE : Seq Scan vs Index Scan. Sargable : pas de fonction sur la colonne indexée.

Vues

VIEW = requête enregistrée, recalculée. MATERIALIZED VIEW = résultat stocké, REFRESH.

Pipelines

Incrémental : high-water mark. SCD1 écrase ; SCD2 ajoute une ligne avec dates de validité ; SCD3 colonne précédente. DATE_TRUNC, ROLLUP, CUBE.

OLTP vs OLAP

OLTP : normalisé, petites transactions, stockage par ligne. OLAP : étoile (faits + dimensions), dénormalisé, gros agrégats, stockage par colonne.

Chapitre 05 · Performance et analytique
Ce que le jury peut demander

Questions d'oral — chapitre 05

EXPLAIN ANALYZE pour voir le plan réel : scans complets sur de grosses tables, estimations de lignes très fausses (statistiques à mettre à jour avec ANALYZE), tris ou jointures coûteux. Puis : index sur les colonnes filtrées et jointes, réécriture sargable des conditions, filtrage plus tôt, agrégats pré-calculés en vue matérialisée si la requête est répétée.

Chaque index occupe de l'espace et doit être mis à jour à chaque INSERT, UPDATE ou DELETE : trop d'index ralentissent les écritures et les chargements. On indexe selon les requêtes réelles : clés étrangères, colonnes de filtre sélectives, colonnes de tri fréquentes.

Une façon d'historiser une dimension : quand un attribut change, on ferme la ligne courante (date de fin) et on insère une nouvelle ligne avec une nouvelle clé technique et une date de début. Les faits passés restent rattachés à la version valable à leur date : on peut analyser « à l'époque ».

Les requêtes analytiques agrègent des millions de faits selon quelques axes (date, produit, client, lieu). L'étoile limite les jointures à une par dimension, rend le modèle compréhensible par les métiers et les outils de BI, et se combine bien avec le stockage en colonnes. La redondance des dimensions est acceptée volontairement, contrairement au modèle OLTP normalisé.
