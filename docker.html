Empaqueter l'application avec son environnement

On construit une image : l'application, son runtime, ses bibliothèques. Chaque machine la lance dans un conteneur isolé, identique partout.

Docker est la plateforme qui construit, distribue et exécute des conteneurs : des processus isolés qui partagent le noyau de la machine hôte. L'isolation vient du noyau Linux : les namespaces (ce que le conteneur voit) et les cgroups (ce qu'il peut consommer).

Analogie — le conteneur maritime. Quel que soit le contenu, la boîte a la même forme : le port, le camion et le bateau savent la manipuler sans l'ouvrir. L'image, c'est le plan de chargement ; le conteneur, la boîte réellement chargée.

docker stop web && docker rm web              # arrêter, supprimer
# docker ps affiche : CONTAINER ID  IMAGE  STATUS  PORTS  NAMES
#   a3f1…  nginx  Up 5 seconds  0.0.0.0:8080->80/tcp  web
Ce qu'il faut remarquer

Aucune installation de nginx : Docker télécharge l'image depuis Docker Hub si elle est absente, crée un conteneur et le lance. -p 8080:80 relie le port 8080 de la machine au port 80 du conteneur. L'image ne change jamais ; le conteneur est jetable.

Présenter Docker en une minute

« Docker est une plateforme de conteneurisation créée en 2013 : elle empaquette une application et ses dépendances dans une image, exécutée en conteneur isolé qui partage le noyau de l'hôte. Le fil du cours · Docker

6 idées font tout le cours

Tout Docker répond à : comment faire tourner une application exactement pareil sur mon poste, celui d'un collègue et le serveur ? Six idées expliquent les commandes, le Dockerfile, les volumes, les réseaux et Compose.

Idée 1 · Un conteneur est un processus isolé

Un conteneur n'est pas une machine virtuelle : c'est un processus qui partage le noyau du système hôte. Le noyau l'isole (les namespaces lui donnent sa propre vue des fichiers, du réseau, des processus) et le limite (les cgroups bornent sa mémoire et son processeur). Il vit tant que son processus principal vit.

L'erreur typique : Si le processus principal se termine (un script qui finit, une erreur au démarrage), le conteneur s'arrête aussitôt, alors qu'on le croit en panne.

La bonne pratique : Lancer en processus principal un programme qui tourne en continu (le serveur web, la base) ; lire docker logs pour comprendre un arrêt.

ch. 01

Idée 2 · L'image est immuable, le conteneur est jetable

L'image est un modèle en lecture seule, fait de couches empilées. Le conteneur est une copie qui tourne, avec une couche inscriptible en plus, perdue quand on supprime le conteneur. On ne répare pas un conteneur : on corrige l'image et l'on relance.

L'erreur typique : Si l'on corrige un problème directement dans un conteneur en production, la correction disparaît au déploiement suivant, car le nouveau conteneur repart de l'image.

La bonne pratique : Corriger le Dockerfile, reconstruire l'image et redéployer : la correction est dans l'image, donc dans chaque nouveau conteneur.

ch. 01 · ch. 02

Idée 3 · Le Dockerfile se lit comme un cache

Chaque instruction du Dockerfile crée une couche, que Docker réutilise (cache) si rien n'a changé avant elle. On place donc en haut ce qui change rarement (les dépendances) et en bas ce qui change souvent (le code). Le multi-stage compile dans une première image et ne garde que le résultat dans une image finale plus petite.

L'erreur typique : Si l'on copie tout le code (COPY . .) avant d'installer les dépendances, la moindre modification du code invalide le cache et relance toute l'installation.

La bonne pratique : Copier d'abord requirements.txt et installer les dépendances, puis copier le code : modifier le code ne relance pas l'installation.

ch. 02

Idée 4 · Les données vivent hors du conteneur

Ce qui doit survivre au conteneur va dehors : dans un volume géré par Docker (les fichiers d'une base de données) ou dans un bind mount, un dossier de l'hôte (le code en développement). Supprimer le conteneur ne touche pas au volume.

L'erreur typique : Si une base de données écrit dans le conteneur au lieu d'un volume, ses données sont perdues dès qu'on supprime le conteneur.

La bonne pratique : Monter un volume nommé sur le dossier de données de la base (pgdata:/var/lib/postgresql/data) : on peut recréer le conteneur sans rien perdre.

ch. 03 · ch. 04

Idée 5 · On se parle par le nom, on publie le minimum

Sur un réseau créé par l'utilisateur (c'est le cas avec Compose), les conteneurs se trouvent par le nom du service. Seul le point d'entrée est publié vers l'extérieur (option -p ou reverse proxy) ; le reste n'est joignable qu'en interne.

L'erreur typique : Si l'API cherche la base à l'adresse localhost, elle la cherche dans son propre conteneur : la connexion est refusée.

La bonne pratique : Dans l'API, se connecter à db:5432 (le nom du service de la base) et ne publier que le port de l'API.

ch. 03 · ch. 04

Idée 6 · Toute l'application dans un fichier

Docker Compose décrit dans un fichier tous les services, leurs réseaux, volumes et variables. La configuration et les secrets viennent de l'environnement (un fichier .env qui n'est pas versionné). Un healthcheck vérifie qu'un service est vraiment prêt, pour démarrer les autres dans le bon ordre.

L'erreur typique : Si un mot de passe est écrit avec ENV dans le Dockerfile, il est enregistré dans l'image et lisible par toute personne qui la récupère.

La bonne pratique : Passer le mot de passe par une variable d'environnement lue dans un fichier .env non versionné, au moment du lancement.

Chapitre 01 · Conteneurs et architecture Docker
① Pourquoi ② Quoi

Un conteneur n'est pas une machine virtuelle

VM contre conteneurs
L'idée

Un conteneur est un processus isolé (ou un petit groupe) qui voit son propre système de fichiers, ses propres processus et son propre réseau, mais partage le noyau de l'hôte. Pas d'OS invité : démarrage en secondes, quelques Mo de plus que l'application.

Comment le noyau isole
  • Namespaces : pid, net, mnt, uts, ipc, user — limitent ce que le processus voit.
  • cgroups : limitent ce qu'il consomme (CPU, mémoire, E/S).
Analogie — une VM, c'est une maison entière par locataire ; un conteneur, un appartement : murs étanches, mais même fondations et même chaudière.

Éphémère, un processus : les pièges du débutant

Confondre image et conteneur. L'image est le plan ; on peut créer 10 conteneurs depuis la même image.
Croire que les données survivent. Supprimer un conteneur supprime sa couche inscriptible : sans volume, tout est perdu (un simple stop ne supprime rien).
Un conteneur sans processus au premier plan s'arrête. Il vit tant que son processus principal tourne.
Penser l'isolation totale. Le noyau est partagé : une faille du noyau touche tous les conteneurs ; ne pas lancer en root sans raison.
  1. Un conteneur = processus isolé (namespaces) et limité (cgroups), noyau partagé.
  2. Image (lecture seule) → conteneur (instance) ; registry = dépôt d'images.
  3. Client → démon : docker run = pull si besoin + create + start.
  4. Éphémère par défaut : données persistantes = volumes (chapitre 03).

Chapitre 01 · Conteneurs et architecture Docker
Ce que le jury peut demander

Questions d'oral — chapitre 01

La VM virtualise le matériel et embarque un système d'exploitation complet géré par un hyperviseur. Le conteneur n'est qu'un processus isolé par le noyau (namespaces et cgroups) qui partage le noyau de l'hôte : plus léger, démarrage rapide, mais isolation moins forte, et même famille de noyau obligatoire.

Une image est un modèle immuable en lecture seule, composé de couches. Un conteneur est une instance en cours d'exécution de cette image, avec une fine couche inscriptible. De la même image on lance autant de conteneurs qu'on veut.

Par les namespaces du noyau Linux (processus, réseau, montages, hostname, utilisateurs) qui limitent ce que le conteneur voit, et par les cgroups qui plafonnent CPU, mémoire et disque.

Pour obtenir un environnement reproductible : même version de Kafka, MongoDB ou Airflow sur chaque poste et en production, installation en une commande, services jetables pour les tests.

Le client interroge le démon ; si l'image est absente, il la télécharge depuis le registry ; il crée un conteneur avec sa couche inscriptible, son réseau et ses namespaces, puis démarre le processus principal de l'image.

Chapitre 02 · Images et Dockerfile
① Pourquoi ② Quoi

Une image = des couches empilées, décrites par un Dockerfile

Le Dockerfile

Un fichier texte, une instruction par ligne, lu de haut en bas. Chaque instruction qui modifie le système de fichiers crée une couche (layer) en lecture seule. Les couches sont mises en cache et partagées entre images.

Les instructions à connaître
  • FROM image de départ · WORKDIR dossier de travail
  • COPY fichiers de l'hôte · RUN commande à la construction
  • ENV variable · EXPOSE port documenté
  • CMD / ENTRYPOINT commande à l'exécution
Analogie — une recette en étapes numérotées. Si l'étape 3 n'a pas changé, on reprend le plat déjà préparé ; on ne refait que ce qui suit la première étape modifiée.
Dockerfile · API Python
FROM python:3.11-slim            # image de base légère
WORKDIR /code
COPY requirements.txt .          # d'abord les dépendances...
RUN pip install --no-cache-dir -r requirements.txt
COPY api/ ./api/                 # ...puis le code (change souvent)
EXPOSE 80
CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "80"]
# docker build -t digicheese-api .   puis   docker run -p 8000:80 digicheese-api
Chapitre 02 · Images et Dockerfile
③ Comment ④ Exemple

Cache, CMD contre ENTRYPOINT, multi-stage

Ordre = cache

Docker réutilise une couche si l'instruction et tout ce qui précède sont inchangés. On place donc ce qui change rarement en haut (dépendances) et ce qui change souvent en bas (code). Copier le code avant pip install relancerait l'installation à chaque modification.

CMD contre ENTRYPOINT
  • CMD : commande par défaut, remplaçable par les arguments de docker run.
  • ENTRYPOINT : exécutable fixe ; les arguments de docker run s'y ajoutent.
  • Forme exec ["a","b"] (sans shell) préférée : le signal d'arrêt atteint le processus.
Dockerfile · multi-stage
FROM python:3.11 AS builder          # étape 1 : outils de build
WORKDIR /code
COPY requirements.txt .
RUN pip install --user -r requirements.txt

FROM python:3.11-slim                # étape 2 : image finale
RUN useradd --create-home app        # utilisateur non root
COPY --from=builder /root/.local /home/app/.local
COPY api/ ./api/
USER app
CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0"]

Le multi-stage ne garde dans l'image finale que ce qui sert à l'exécution : image plus petite, moins de surface d'attaque.

Gérer les images : lister, taguer, publier, auditer

shell
docker search nginx                 # chercher sur Docker Hub
docker images                       # ou docker image ls

docker commit produit une image non reproductible : personne ne sait comment elle a été obtenue. On préfère toujours un Dockerfile versionné.

Moins de paquets = moins de CVE. Docker Scout (ou Trivy) liste les vulnérabilités connues des couches ; docker history montre ce que chaque instruction a ajouté. Voir Vulnérabilités.

Chapitre 02 · Images et Dockerfile
⑤ Pièges ⑥ Résumé

Pièges de construction

Mettre un secret dans l'image (ENV PASSWORD=…) : il reste lisible dans les couches. Utiliser variables d'exécution ou secrets.
Utiliser latest : le contenu change sans prévenir ; épingler une version (python:3.11-slim).
Oublier .dockerignore : .git, .env, pycache partent dans le contexte de build.
RUN séparés pour apt-get update et install : le cache sert un index périmé ; les enchaîner avec &&.
Lancer en root : créer un utilisateur et passer USER.
  1. Dockerfile : FROM, WORKDIR, COPY, RUN, CMD.
  2. Une instruction = une couche, mise en cache : ordre du plus stable au plus changeant.
  3. RUN à la construction ; CMD/ENTRYPOINT à l'exécution.
  4. Multi-stage + utilisateur non root + .dockerignore : image petite et sûre.

Chapitre 02 · Images et Dockerfile
Ce que le jury peut demander

Questions d'oral — chapitre 02

Un Dockerfile liste les instructions de construction. docker build les exécute dans l'ordre : chaque instruction qui modifie le système de fichiers produit une couche en lecture seule, mise en cache, l'ensemble formant l'image.

Pour exploiter le cache : tant que les dépendances ne changent pas, la couche pip install est réutilisée. Copier le code d'abord invaliderait cette couche à chaque modification du code.

CMD fournit une commande par défaut que l'on remplace en passant des arguments à docker run. ENTRYPOINT définit l'exécutable fixe du conteneur, auquel les arguments sont ajoutés ; on combine souvent les deux.

À séparer la construction (compilateurs, outils) de l'exécution : l'image finale ne copie que les artefacts nécessaires. Elle est plus petite, plus rapide à télécharger et expose moins de composants vulnérables.

Image de base minimale et épinglée, utilisateur non root, pas de secret dans les couches, .dockerignore, mises à jour régulières, analyse des vulnérabilités de l'image avant publication.

Chapitre 03 · Volumes et réseaux
① Pourquoi ② Quoi

Persister les données : volume, bind mount, tmpfs

TypeOù vivent les donnéesUsage typique
Volume nomméGéré par Docker (/var/lib/docker/volumes)Base de données : MariaDB, MongoDB
Bind mountUn dossier précis de l'hôteCode source en développement
tmpfsEn mémoire, jamais sur disqueSecrets ou cache temporaire
Pourquoi

La couche inscriptible disparaît avec le conteneur. Un volume a sa propre vie : on supprime et recrée le conteneur, les données restent. Cette séparation permet aussi de mettre à jour l'image sans perdre la base.

shell
docker volume create donnees
docker run -d --name db -v donnees:/var/lib/mysql mariadb:10.6
docker rm -f db                       # le conteneur disparaît...
docker run -d -v donnees:/var/lib/mysql mariadb:10.6   # ...les données restent

③ Comment ④ Exemple

Réseaux : se parler par le nom du service

Les réseaux
  • bridge (défaut) : réseau privé interne à l'hôte.
  • Sur un bridge défini par l'utilisateur, les conteneurs se joignent par leur nom (DNS intégré) ; pas sur le bridge par défaut.
  • host : partage la pile réseau de l'hôte · none : aucun réseau.
Publier un port

-p 8000:80 relie le port 8000 de l'hôte au port 80 du conteneur. Entre conteneurs d'un même réseau, aucune publication n'est nécessaire : l'API joint la base sur db:3306, pas sur localhost.

③ Comment ④ Exemple

IPv4 en bref, pour lire un réseau Docker

Adresse et masque
  • Une adresse IPv4 : 4 octets de 0 à 255 (32 bits), par exemple 172.18.0.5.
  • Le masque sépare la partie réseau (bits à 1) de la partie hôte (bits à 0) : 255.255.255.0 = /24 en notation CIDR.
  • Un /24 contient 2⁸ = 256 adresses, dont 254 utilisables : la première est l'adresse du réseau, la dernière le broadcast.
  • Un bit de masque en plus divise le réseau en deux sous-réseaux et le nombre d'hôtes par deux.

Deux machines sont-elles sur le même réseau ?

On applique un ET logique entre chaque adresse et le masque : si l'adresse réseau obtenue est identique, elles se joignent directement ; sinon il faut passer par un routeur. Exemple : 192.168.1.20/24 et 192.168.1.200/24 → même réseau 192.168.1.0.

shell
docker network ls                     # bridge, host, none par défaut
docker network create app-net         # bridge défini par l'utilisateur
docker run -dit --name c1 --network app-net alpine
docker network inspect app-net        # sous-réseau, ex. 172.19.0.0/16
docker network connect app-net c2     # brancher un conteneur existant
docker network rm app-net

Les adresses privées ne sont pas routées sur Internet : on les réutilise dans chaque réseau local, et Docker en attribue une à chaque conteneur.

Chapitre 03 · Volumes et réseaux
⑤ Pièges ⑥ Résumé

Pièges et réflexes

Utiliser localhost pour joindre un autre conteneur : chaque conteneur a son propre localhost ; utiliser le nom du service.
Publier le port de la base sur l'hôte par habitude : inutile et dangereux.
Oublier le volume d'une base : docker rm efface tout.
Bind mount avec les mauvais droits : l'utilisateur du conteneur n'écrit pas dans le dossier de l'hôte.
docker volume prune sans regarder : supprime les volumes non utilisés, donc des données.
  1. Données durables = volume nommé ; code en développement = bind mount.
  2. Le volume survit au conteneur ; rm du conteneur ne l'efface pas.
  3. Réseau défini par l'utilisateur : résolution par nom, isolation entre réseaux.
  4. -p hôte:conteneur ne sert que pour l'accès depuis l'extérieur.

Chapitre 03 · Volumes et réseaux
Ce que le jury peut demander

Questions d'oral — chapitre 03

Avec un volume nommé monté sur le répertoire de données de la base (par exemple /var/lib/mysql). Il vit indépendamment du conteneur : on peut supprimer et recréer le conteneur, ou changer la version de l'image, sans perdre les données.

Le volume est créé et géré par Docker, portable et indépendant de l'arborescence de l'hôte. Le bind mount expose un chemin précis de l'hôte : pratique en développement pour voir le code modifié en direct, mais dépendant de la machine et de ses droits.

En les plaçant sur le même réseau défini par l'utilisateur : ils se joignent par le nom du service grâce au DNS intégré, sur le port interne. Compose crée ce réseau automatiquement.

Elle publie le port 80 du conteneur sur le port 8000 de l'hôte, ce qui rend le service accessible depuis l'extérieur du réseau Docker, par exemple depuis le navigateur.

Seuls les services qui en ont besoin (l'API) la joignent, via le réseau interne. La publier élargit la surface d'attaque pour rien.

Chapitre 04 · Docker Compose et bonnes pratiques
① Pourquoi ② Quoi

Compose : décrire toute l'application dans un fichier

Le principe

docker-compose.yml décrit les services, leurs images ou builds, ports, volumes, réseaux et variables. Une seule commande les crée tous dans le bon réseau. Compose v2 est intégré : docker compose up.

Configuration hors du code

Un fichier .env (non versionné, listé dans .gitignore) fournit les valeurs ${DB_USER}. On versionne un .env.example sans secret.

Analogie — la partition d'un orchestre : chaque service est un instrument ; le fichier dit qui joue quoi et dans quel ordre.
docker-compose.yml · TP Digicheese (extrait)
services:
  api:
    build: .
    ports: ["8000:80"]
    volumes: ["./api:/code/api"]          # bind mount : code en direct
    environment: [DB_HOST=db, DB_USER=${DB_USER}]
    depends_on:
      db: { condition: service_healthy }   # attend que la base réponde
  db:
    image: mariadb:10.6
    volumes: ["digicheese-data:/var/lib/mysql"]
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
volumes:
  digicheese-data: {}
Chapitre 04 · Docker Compose et bonnes pratiques
③ Comment ④ Exemple

Commandes, démarrage ordonné et usage data

shell
docker compose up -d --build   # créer et lancer
docker compose ps                # état des services
docker compose logs -f api       # suivre les journaux
docker compose exec db mariadb -u admin -p   # shell dans un service
docker compose down              # arrêter et supprimer (garde les volumes)
docker compose down -v           # ... et SUPPRIME les volumes

depends_on seul garantit l'ordre de démarrage, pas que la base soit prête : ajouter un healthcheck et condition: service_healthy.

Dans un projet data
  • Un fichier Compose lance Kafka + Zookeeper, MongoDB, Airflow, Elasticsearch + Kibana, MinIO.
  • Chaque équipier obtient le même environnement en une commande.
  • Les TP sont livrés avec leur Compose : on ne configure plus, on exécute.
Limites

Compose pilote une seule machine. Pour répartir sur plusieurs serveurs, auto-réparation et mises à jour progressives, on passe à Kubernetes.

Un point d'entrée unique : le reverse proxy

Le principe

Un reverse proxy (Caddy, Nginx, Traefik) est le seul service publié sur 80 et 443. Il reçoit toutes les requêtes et les redirige vers le bon conteneur selon le nom de domaine ou le chemin. Il peut aussi gérer le HTTPS : Caddy obtient et renouvelle les certificats automatiquement.

Caddyfile
localhost {
    reverse_proxy /api/* api:8000     # nom du service Compose
    reverse_proxy /*     front:3000
}
Ce qu'il apporte
  • Un seul port ouvert vers l'extérieur ; API, front et outils restent sur le réseau interne.
  • TLS terminé en un seul endroit.
  • Routage, compression, en-têtes de sécurité, mise en cache (Varnish devant WordPress dans les exemples du support).

Le proxy et les services doivent partager le même réseau Docker : le proxy les joint par leur nom de service. Les volumes caddy_data et caddy_config conservent les certificats.

Chapitre 04 · Docker Compose et bonnes pratiques
⑤ Pièges ⑥ Résumé

Pièges et résumé

docker compose down -v par réflexe : efface les volumes, donc la base.
Secrets écrits en dur dans le YAML versionné : utiliser .env ignoré par Git ou des secrets.
depends_on sans healthcheck : l'API démarre avant la base et plante.
Publier tous les ports : n'exposer que l'entrée du système.
latest partout : un pull change silencieusement la version.
  1. Compose = services, volumes, réseaux dans un fichier ; up -d, ps, logs, down.
  2. .env pour la configuration ; jamais de secret versionné.
  3. healthcheck + service_healthy pour un démarrage ordonné fiable.
  4. Compose = une machine ; plusieurs machines = Kubernetes.

Ce que le jury peut demander

Questions d'oral — chapitre 04

À décrire et lancer une application multi-conteneurs dans un seul fichier : services, ports, volumes, réseaux, variables. Une commande crée tout l'environnement, ce qui le rend reproductible pour toute l'équipe.

Dans un fichier .env exclu du dépôt par .gitignore, référencé par ${VARIABLE}, avec un .env.example sans valeur réelle. Pour la production, on préfère les secrets Docker ou un gestionnaire de secrets.

Parce que depends_on ordonne le lancement, pas la disponibilité. La base démarre mais n'accepte pas encore de connexions. On ajoute un healthcheck et condition: service_healthy.

Pour un petit déploiement sur une machine, oui. Pour la haute disponibilité, la montée en charge et les mises à jour sans interruption, on utilise un orchestrateur comme Kubernetes.

Trois services sur un réseau dédié : l'API FastAPI construite depuis un Dockerfile, MariaDB avec volume nommé et healthcheck, Adminer pour l'administration ; configuration par .env, code monté en bind mount, tests dans le conteneur.
